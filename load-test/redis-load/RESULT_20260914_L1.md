# Redis 장애 × 낮은 부하 — L1 1회, **무효**(컨테이너 실행 지연), L2 미실행

> 계획: [`PLAN_20260914.md`](PLAN_20260914.md) — 실행 전에 고정했고 결과를 본 뒤 바꾸지 않았다.
> 원본: `evidence/20260914-132129/` (L1), 보충 `evidence/20260914-stallprobe/`(무부하 지연 프로브, §5).
>
> **결론 한 줄**: 구간별 **평균** 요청 수는 목표와 같았지만 요청이 예정 시각보다 크게 늦게 나갔다(생성기 전송 지연 p95 최대 8.2 s,
> 최대 10.7 s — 사전 기준 §6-1은 p95 ≤ 100 ms). **계획한 요청 간격을 지키지 못했으므로 부하 조건을 달성한 실행으로 보지 않는다.**
> 지연은 다섯 생성기 컨테이너에서 같은 시각에 났고, 부하 없이도 컨테이너 쪽에서 같은 크기의 실행 지연이 관측됐다(§5).
> **컨테이너 실행 지연이 공통으로 관측됐고 Docker/가상화 계층을 의심하지만, 원인은 미확정이다.**
> 사전 기준에 따라 실행을 무효로 하고 **L2는 돌리지 않았다.** 같은 환경에서 부하 실험을 반복하지 않는다.

## 1. 조건

| | |
| --- | --- |
| 명령 | `bash load-test/redis-load/run_load_outage.sh L1` |
| 계획한 부하 | `/api` 생성기 4개(컨테이너=IP 4개) × 0.8 req/s, 조회·refresh(없는 토큰) 번갈아 = 3.2 req/s + liveness 1 req/s |
| 구간 | warm 20 s / baseline 90 s / Redis 중단 60 s / 복구 관찰 150 s |
| backend | 이미지 `sha256:3559175f…`, `compose.observe.yml`(Tomcat 스레드 지표만 켬). timeout·rate limit·보안 설정 불변 |
| 알림 | Prometheus·Alertmanager 미기동(외부 발송 없음) |
| 환경 | Windows 11 + Docker Desktop(WSL2) 한 대에 생성기·backend·Redis·PostgreSQL·Kafka. `docker info` NCPU·메모리는 metadata |

**첫 시도는 도구 결함으로 사전 확인에서 멈췄다(증거 디렉터리 생성 전).** `curl … | grep -q`에서 grep이 먼저 끝나 curl이 쓰기 오류로
죽고 `pipefail`이 실패로 봤다 — 지표는 있었다. 파일로 받은 뒤 grep하도록 고쳐 다시 실행했다.

## 2. 생성기 자체 기록 — 평균 요청 수는 같았고, 발행 시각이 크게 밀렸다

| 구간 | 경로 | 구간 평균 req/s (계획) | 생성기 전송 지연 p95 / 최대 (ms) | 생성기 오류 |
| --- | --- | --- | --- | --- |
| baseline | 조회 / refresh / liveness | 1.60 (1.60) / 1.60 (1.60) / 1.00 (1.00) | 6,972 / 10,732 · 8,221 / 10,721 · 6,722 / 10,721 | 0 |
| outage | 조회 / refresh / liveness | 1.60 / 1.60 / 1.00 | 4,497 / 9,496 · 5,746 / 10,746 · 0 / 1,035 | 0 |
| reconnect | 조회 / refresh / liveness | 1.60 / 1.60 / 1.00 | 738 / 10,736 · 1 / 9,487 · 0 / 109 | 0 |
| recovery_tail | 조회 / refresh / liveness | 1.59 / 1.62 / 1.00 | 229 / 2,729 · 9 / 1,479 · 729 / 2,729 | 0 |

- **구간 평균 요청 수는 "예정 시각"으로 센 값이다.** 늦게 나간 요청도 결국 보냈으므로 합계는 계획과 같지만, **실제로 나간 순간이 몰렸다.**
  이 표를 "계획한 요청 간격을 준수했다"거나 "부하 조건을 달성했다"는 근거로 쓰지 않는다.
- **생성기 오류**(클라이언트 timeout·연결 오류·HTTP 파싱 오류) 0건, 컨테이너 종료 코드 전부 0.
- 생성기 CPU 평균 0.1%(최대 0.5%) — 생성기 프로세스가 CPU를 다 써서 밀린 것은 아니다.

## 3. 판정

- **실행 무효** — §6-1 생성기 전송 지연 기준 위반(모든 구간). 그래서 §6-3의 "올리지 않는 조건"도 [6]으로 해당한다.
- **L2·L3는 실행하지 않았다.** 무효 실행의 수치로 "올려도 된다"를 판단하지 않는다.

## 4. 지연이 서버 부하가 아니라 실행 환경 쪽에서 관측됐다고 보는 근거

1. **동시성**: 1초 넘게 밀린 요청이 +40~80 s·+120 s·+180 s·+260 s 부근에 몰렸고, 매번 **생성기 5개 전부**(Redis를 안 쓰는 liveness 생성기 포함)에서 났다.
2. **컨테이너 안 표본기도 늦었다**: 2초 주기 표본기 간격이 **+59 s에 12.7 s**, +266 s에 4.7 s였다.
3. **호스트 쪽 루프는 늦지 않았다**: 호스트에서 도는 `docker stats` 루프에는 8초 넘는 간격이 없었다.
4. **시계 차이가 아니다**: 호스트와 컨테이너 시계 차이는 약 0.24~0.37 s(3회 측정).
5. **서버가 한가했다**: backend CPU 평균 0.3~0.5%, Tomcat busy 스레드는 baseline 최대 1.

→ **컨테이너 실행 지연이 공통으로 관측됐다. Docker/가상화 계층을 의심하지만 원인은 미확정이다**
(가상화 스케줄링·호스트 전원 설정·다른 프로세스 중 무엇인지 확인하지 않았다).
같은 지연이 backend 컨테이너에도 걸렸다면 그 시간의 응답 시간도 오염됐을 수 있다.

## 5. 무부하 지연 프로브 (보충, `evidence/20260914-stallprobe/`)

L1 직후, **부하도 Redis 중단도 없이** 300초 동안 100 ms sleep을 반복해 200 ms 넘게 늦게 깬 경우만 기록했다.
컨테이너(Docker Desktop, 생성기와 같은 이미지)와 Windows 호스트 Python에서 **동시에** 돌렸다. 스택은 유휴 기동 상태.

| 위치 | 200 ms 넘는 초과 | 내역 |
| --- | --- | --- |
| 컨테이너 | **6건** | **10,760 · 10,757 · 10,767 ms**(약 30초 간격으로 세 번), 770 · 2,727 · 1,076 ms |
| 호스트 | **0건** | — |

- **부하 없이도 컨테이너 쪽에서 약 10.8 s의 실행 지연이 났다** — L1의 생성기 전송 지연 최대(10.7 s)·표본기 간격(12.7 s)과 같은 크기다.
- 호스트 프로세스는 늦지 않았으므로 Windows 전체가 멈춘 것은 아니다. **컨테이너 쪽 지연의 원인은 확인하지 않았다.**
- 1회 5분 관찰이다. 지연 빈도가 늘 이런지는 모른다.
- 같은 폴더에 L1 지연의 시간 분포(`L1_lag_by_time.txt`), 표본 간격(`L1_gaps.txt`), 시계 차이(`clock_offset.txt`)와 분석 스크립트를 남겼다.

## 6. 무효 실행에서 기록만 해 두는 수치 — **성능 결론으로 쓰지 않는다**

아래는 무효 실행의 원본을 집계한 값이다. 컨테이너 실행 지연이 응답 시간·표본에 섞였을 수 있어 **판정·성능 결론·다음 실험의 기준값으로 쓰지 않는다.**
다음에 유효한 실행이 생기면 확인할 **질문**으로만 남긴다.

| 구간 | 조회 p50/p95/최대 (ms) | refresh p50/p95/최대 (ms) | Tomcat busy 평균/최대 | 처리 중 요청 최대 | JVM 스레드 최대 | backend CPU 평균 |
| --- | --- | --- | --- | --- | --- | --- |
| baseline | 7 / 11 / 15 (200+헤더) | 5 / 10 / 13 (401) | 1.0 / 1 | 1 | 58 | 0.5% |
| outage | 2,005 / 2,896 / 12,751 | 4,005 / 5,039 / 5,041 | 9.4 / 25 | 25 | 104 | 0.4% |
| reconnect | 2,005 / 2,008 / 2,114 | 4,004 / 4,113 / 14,739 | 6.5 / 18 | 18 | 105 | 0.4% |
| recovery_tail | 4 / 6 / 7 (200+헤더) | 3 / 5 / 5 (401) | 1.1 / 2 | 2 | 105 | 0.3% |

남겨 두는 질문(확인 안 함):
- 장애 전환 순간 요청 3건이 12.75 s·12.75 s·14.74 s였다. 조회 2건의 종료 시각(04:24:01.9Z)이 Lettuce 재연결 시도 시작(04:24:01.925Z)과 겹친다 —
  전환 순간의 동작인지, 컨테이너 실행 지연이 섞인 것인지 모른다.
- Tomcat 현재 스레드(10 → 26)와 JVM 스레드(58 → 105)가 recovery_tail까지 유지됐다(busy는 1~2). 늘어난 스레드가 무엇인지 보지 않았다.
- 처리 중 요청 최대 25는 계획서의 이론값(약 10)과 다르다.

## 7. 다시 측정한다면

**이번에 확인한 것은 "이 Docker 환경에서 계획한 요청 간격으로 측정하지 못했다"까지다.** 지연 원인이 확인되지 않았으므로
**다른 환경이 반드시 필요하다고 단정하지 않는다.** 선택지는 둘이다:

- **(가) 같은 환경에서 지연 원인을 먼저 확인한다** — 부하 없이 `stallprobe.py`를 반복하며 Docker Desktop 설정·호스트 전원 설정·다른 프로세스와의 관계를
  하나씩 바꿔 본다. 원인을 찾아 프로브가 0건이 되면 같은 계획으로 L1부터.
- **(나) 다른 실행 환경에서 측정한다** — 예: Linux 호스트, 서버와 생성기 분리, NTP 시계 동기화.
  - rate limit이 IP 기준이라 생성기 쪽도 IP를 여럿 써야 한다(한 IP로 3.2 req/s면 429로 바뀐다).
  - 지금 `run_load_outage.sh`는 생성기가 backend와 같은 Docker 네트워크에 있다고 가정한다(`--network`, `backend:8080`) — 분리하려면 호스트·포트 인자가 필요하다.

어느 쪽이든 공통:
1. **시작 전 무부하 지연 프로브 5분**(§5 방식)을 생성기와 서버 환경 **양쪽에서** 돌려 **0건**일 때만 시작한다.
2. L1이 §6을 전부 만족하면 L2, 다시 만족하면 L3. **L3를 넘기지 않는다.**
3. §6의 질문(전환 순간 긴 응답, 늘어난 스레드)을 그 유효한 실행에서 확인한다.

## 8. 쓰지 않을 표현

- "계획한 요청 간격을 준수했다"·"부하 조건을 달성했다" — 전송 지연이 기준을 크게 넘었다.
- "Docker Desktop VM 정지가 원인" — 원인은 미확정이다.
- "부하 중에도 문제없다"·"스레드 고갈 없음"·"fail-open은 2초" — 무효 1회의 수치다.
- 이 수치로 처리량·임계치·회복 시간을 말하지 않는다.
