# Redis 장애 × 낮은 부하 — 제한된 검증 계획 (roadmap 3b)

> **실행 전에 고정한 조건이다.** 결과를 본 뒤 이 문서의 수치를 바꾸지 않는다. 바꿔야 하면 새 계획으로 적는다.
> 목적은 **최대 처리량이나 고갈 한계를 찾는 것이 아니다.** 낮은 부하에서 정상 → Redis 중단 → 복구가
> 요청 처리·자원에 무엇을 남기는지 관측한다.

## 1. 질문

1. Redis 중단 중 일반 조회(fail-open)와 Redis 필수 경로(fail-closed)의 응답 시간·오류·timeout은 어떻게 달라지는가
2. 그동안 서버에서 **실제로 관측되는** 처리 중 요청 수·Tomcat 스레드·CPU·메모리는 어떻게 움직이는가
3. Redis가 돌아온 뒤 응답 시간과 자원 사용이 **기준 구간 수준으로 돌아오는가**

## 2. 바꾸지 않는 것

- 회로 차단기·timeout(`REDIS_TIMEOUT` 2s)·rate limit(60/분, IP 기준)·보안 정책 — **그대로**
- 관측을 위해 **실험용 backend 컨테이너에만** `SERVER_TOMCAT_MBEANREGISTRY_ENABLED=true`를 준다
  (`load-test/redis-load/compose.observe.yml`). Tomcat 스레드 지표를 내보내는 설정일 뿐 요청 처리 경로는 바꾸지 않는다.
- Prometheus·Alertmanager는 **띄우지 않는다** — 외부 알림 발송 가능성을 없앤다. 지표는 actuator를 직접 긁는다.

## 3. 부하

| 항목 | 값 | 이유 |
| --- | --- | --- |
| 모델 | **개방형**(도착률 고정) — 응답이 느려져도 보내는 속도를 줄이지 않는다 | 폐쇄형은 느려지면 부하가 스스로 줄어 장애 영향을 가린다 |
| `/api` 생성기 1개의 요청률 | **0.8 req/s**, 조회(`GET /api/vehicles`)·refresh(`POST /api/auth/refresh`, 없는 토큰)를 번갈아 | rate limit이 **IP당 60/분**이다. 생성기마다 컨테이너(=IP)를 따로 두고 48/분으로 한도 아래에 둔다 — 정책을 바꾸지 않고 429를 피한다 |
| 대조 경로 | 생성기 1개, `GET /actuator/health/liveness` **1 req/s** | Redis를 안 쓰는 경로 — 서버 전체가 느려졌는지 가른다 |
| 단계 | L1 = `/api` 생성기 **4개(3.2 req/s)** → L2 = **8개(6.4)** → L3 = **12개(9.6)** | **L3를 넘기지 않는다** |
| 클라이언트 timeout | 15 s | 서버 쪽 Redis timeout(2s)보다 충분히 길어 서버가 낸 결과를 본다 |
| 연결 | 요청마다 새 연결 | 재연결 중 연결 재사용 오류가 결과를 섞지 않게 |
| 생성기 위치 | backend와 같은 Docker 네트워크의 컨테이너(프로젝트 이미지의 Python 3.11, 표준 라이브러리만) | 새 도구·이미지를 받지 않는다 |

**단계별 이론상 동시 처리 중 요청**(장애 중, 조회 2s·refresh 4s 가정): L1 약 10 / L2 약 19 / L3 약 29.
Tomcat 기본 최대 스레드 200보다 훨씬 낮다 — **이 실험은 고갈을 재현하도록 설계되지 않았다.** 관측값이 이 계산과 맞는지를 본다.

## 4. 한 번의 실행 (단계마다 1회)

| 구간 | 길이 | 판정에 쓰나 |
| --- | --- | --- |
| warm | 20 s | 제외 |
| baseline | 90 s | 기준 |
| outage | `docker stop telemetry-redis` 완료 ~ 60 s 뒤 기동 명령 | 비교 |
| reconnect | 기동 명령 ~ +60 s | 관찰(Lettuce 재연결 대기 포함) |
| recovery_tail | 실행 마지막 60 s (기동 명령 +90 s ~ +150 s) | **복구 판정** |

단계 사이 휴식 120 s. 실행 순서·시각·호스트 정보는 evidence metadata에 남긴다.

## 5. 기록하는 것

- 요청 1건당: 생성기·경로·**예정 시각·실제 전송 시각(생성기 지연)**·종료 시각·HTTP·오류 코드·timeout/연결 오류
- 2 s마다 actuator: `tomcat_threads_busy_threads`·`tomcat_threads_current_threads`·`tomcat_threads_config_max_threads`,
  `http_server_requests_active_seconds_active_count`(처리 중 요청), `jvm_threads_live_threads`·`jvm_threads_states_threads`,
  `process_cpu_usage`, `jvm_memory_used_bytes{area="heap"}`, 긁는 데 걸린 시간
- 2 s마다 `docker stats`: backend·redis·생성기 컨테이너 CPU·메모리
- backend의 Lettuce 재연결 로그

## 6. 판정 기준

### 6-1. 실행이 유효한가 (생성기 한계와 서버 한계 구분)

- 생성기 지연(실제 전송 − 예정) **p95 ≤ 100 ms, 최대 ≤ 1000 ms** — 넘으면 **생성기 한계**로 보고 그 실행은 무효, 단계를 올리지 않는다
- baseline의 실제 요청률이 예정의 **±10%** 안
- 생성기 컨테이너 CPU가 지속적으로 높으면(평균 > 50%) 무효 표시

### 6-2. 예상 응답 (다르면 "예상 밖")

| 구간 | 조회 | refresh(없는 토큰) | liveness |
| --- | --- | --- | --- |
| baseline·recovery_tail | 200 + `X-RateLimit-Remaining` | 401 | 200 |
| outage | 200, 헤더 없음(fail-open) | 503 `REDIS_UNAVAILABLE` | 200 |
| reconnect | 위 둘 중 하나 | 위 둘 중 하나 | 200 |

### 6-3. 다음 단계로 올리지 않는 조건 (하나라도)

1. 어느 구간이든 클라이언트 timeout(15 s) 또는 연결 오류 1건 이상
2. baseline 또는 recovery_tail에서 예상 밖 응답 > 1%
3. recovery_tail p95 > max(baseline p95 × 2, baseline p95 + 200 ms) — 경로별
4. recovery_tail의 Tomcat busy 스레드 최대 > baseline 최대 + 5, 또는 처리 중 요청 최대 > baseline 최대 + 5
5. 어느 구간이든 backend CPU(`process_cpu_usage`) 평균 > 70%
6. 6-1 무효
7. outage에서 liveness p95 > 500 ms — Redis와 무관한 경로까지 느려졌다

### 6-4. 쓰지 않을 표현

- 각 단계 **1회**라 "안정적"·"문제없음"이라고 쓰지 않는다
- 관측하지 않은 스레드 고갈·큐 적체를 추정으로 확정하지 않는다
- 이 결과로 운영 처리량·임계치를 말하지 않는다

## 7. 이 환경에서 유효하지 않을 수 있는 이유 (실행 전 인지)

- 호스트 한 대(Windows + Docker Desktop/WSL2)에 생성기·backend·Redis·DB가 같이 있다 — 서로 CPU를 뺏는다
- Tomcat 요청 대기열(accept queue) 길이는 직접 지표가 없다 — 클라이언트 지연과 서버 처리 중 요청 수의 차이로만 간접 관찰한다
