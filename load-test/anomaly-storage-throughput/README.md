# 이상 알림 저장 처리량 측정

`bash measure.sh [부하 지속 초] [샘플 수] [차량 수]` (기본 120 / 12 / 100)

## 무엇을 재나

`anomaly-storage-group`(Kafka → PostgreSQL 알림 저장)이 **초당 몇 건을 처리하는가.**

부하를 걸어 lag을 쌓고, **부하를 끊은 뒤** lag 감소 속도를 샘플링한다.
유입이 0이므로 lag 감소분이 곧 처리량이다.

## 왜 만들었나

두 개의 다른 실험에서 같은 증상이 나왔는데 그때마다 "느리다"고만 적고 넘어갔다.

- PostgreSQL 60초 장애: 200초를 기다려도 lag 3,693 잔존 (`../anomaly-dlq-idempotency/`)
- 리밸런싱 3→1→3: 부하 정지 후 따라잡는 데 **13분** (`../rebalance-redelivery/`)

재보니 **49 msg/s**였고, 같은 부하의 알림 발생량이 193 msg/s라 **유입의 1/4**만
처리하고 있었다. lag이 계속 쌓이는 게 정상 동작이었던 셈이다.

## 결과 (2026-09-05)

`RESULT_20260905_batching.md`. 요약:

| | 부하 중 lag | 부하 정지 직후 |
| --- | ---: | ---: |
| 배치화 전 (100대) | 20,128 | 203초 뒤에도 11,213 (49 msg/s) |
| 배치화 후 (100대) | **238** | **0** |
| 배치화 후 (400대) | **268** | **0** |

배치 리스너 + 배치당 트랜잭션 1건으로 바꿨다. 저장 경로(InfluxDB)에서 같은 이유로
같은 수정을 한 적이 있다(ADR-011) — 알림 경로는 그때 같이 고치지 않았었다.

## 주의

- **`down -v`로 시작한다.** 남겨야 할 데이터가 있으면 돌리지 마라.
- **배치화 후에는 이 스크립트의 드레인 샘플링이 의미가 없다.** lag이 안 쌓이므로
  잴 백로그가 없다. 그때는 "부하 중 lag"과 "저장 건수/시간"으로 읽어라.
- **차량 수를 늘려 상한을 재려면 시뮬레이터를 여러 프로세스로 띄워야 한다.**
  단일 프로세스는 GIL 때문에 약 1,000-1,250 msg/s에서 먼저 막힌다(ADR-015).
