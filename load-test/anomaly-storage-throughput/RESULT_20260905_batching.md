# 이상 알림 저장 처리량 — 배치화 전후 (2026-09-05)

두 번의 다른 실험에서 같은 증상을 봤다. PostgreSQL 60초 장애 실험에서는 200초를
기다려도 lag 3,693이 남았고(`load-test/anomaly-dlq-idempotency/`), 리밸런싱 실험에서는
부하를 끊은 뒤 따라잡는 데 **13분**이 걸렸다(`load-test/rebalance-redelivery/`).
두 번 다 "느리다"고 적기만 하고 **얼마나 느린지는 재지 않았다.**

**결론: 49 msg/s였다. 배치화 후 같은 부하를 lag 238로 소화한다.**

절차: `bash measure.sh [부하 지속 초] [샘플 수] [차량 수]`

---

## 재는 방법

부하를 걸어 lag을 쌓고, **부하를 끊은 뒤** lag 감소 속도를 샘플링한다.
유입이 0이므로 lag 감소분이 곧 처리량이다.

## 수정 전 — 49 msg/s

100대 / 0.2초 / 이상률 0.3으로 120초. 부하 중 lag이 **20,128**까지 쌓였다.
부하를 끊고 15초 간격으로 12번 샘플링:

```
+17초  lag=19330  (55 msg/s)
+34초  lag=18565  (51 msg/s)
+50초  lag=17811  (50 msg/s)
...
+203초 lag=11213  (53 msg/s)
```

**평균 49 msg/s**, 편차도 거의 없다(43~55). 203초를 드레인하고도 lag이 11,213 남았다.

같은 구간의 알림 발생량은 약 **193 msg/s**였다(저장 11,892 + 잔여 lag 11,213 ÷ 120초).
즉 **유입의 1/4밖에 처리하지 못한다.** lag이 계속 쌓이는 게 정상 동작이었던 셈이다.

### 왜 느렸나

`consumeAnomalyAlerts`가 **레코드 단위 리스너 + `MANUAL_IMMEDIATE`**였다.
알림 한 건마다:

1. `@Transactional save()` → PostgreSQL 커밋 1회(= WAL fsync)
2. `acknowledgment.acknowledge()` → Kafka offset 커밋 1회(브로커 왕복)

초당 200건이면 초당 fsync 200회 + 브로커 왕복 200회다.
저장 경로(InfluxDB)에서 **똑같은 이유로** 처리량이 8 msg/s까지 떨어진 적이 있고,
배치화로 복구했다(ADR-011). 알림 경로는 그때 같이 고치지 않았다.

## 수정 — 배치 리스너 + 배치당 트랜잭션 1건

저장 경로와 같은 모양으로 맞췄다.

- `consumeAnomalyAlerts`를 배치 리스너로(`telemetryBatchListenerContainerFactory`)
- `AnomalyService.toEntity()`를 **트랜잭션 밖으로** 분리 — 잘못된 타임스탬프 하나가
  트랜잭션 안에서 터지면 같은 배치의 정상 알림 수천 건까지 롤백된다.
  파싱 실패는 레코드별로 격리해 그 한 건만 DLQ로 보낸다
  (`TelemetryRepository.toPoint()`를 뺀 것과 같은 이유).
- `AnomalyService.saveAll()`이 배치를 **한 트랜잭션**으로 저장 → 커밋 1회
- offset 커밋도 배치당 1회

### 함께 바뀐 것 — DB 장애 시 동작

예전에는 DB 장애로 저장이 실패하면 **곧바로 DLQ로 보내고 offset을 커밋**했다.
배치에서 그러면 수천 건이 한꺼번에 DLQ로 간다. 이제는 offset을 커밋하지 않고 예외를
던져 `KafkaConfig`의 **180초 재시도 예산**에 맡긴다. 소진되면
`DeadLetterPublishingRecoverer`가 처리한다.

텔레메트리 경로와 같은 정책이 됐다. Runbook에 "알림 경로는 재시도 예산을 타지 않는데
의도인지 미검토"라고 적어뒀던 항목이 이걸로 정리됐다.

## 수정 후

| 부하 | 부하 중 lag | 부하 정지 직후 lag | 저장 건수 |
| --- | ---: | ---: | ---: |
| 100대 (수정 전) | **20,128** | 20,157 → 203초 뒤 11,213 | 49 msg/s로 드레인 |
| 100대 (수정 후) | **238** | **0** | 23,113 (≈193 msg/s, 유입 전량) |
| 400대 (수정 후) | **268** | **0** | 47,639 (≈301 msg/s, 유입 전량) |

같은 100대 부하에서 lag이 **20,128 → 238**이 됐고, 부하를 끊자마자 0이다.
드레인 속도를 잴 백로그 자체가 생기지 않는다.

부하를 4배(400대)로 올려도 lag 268로 유입을 전량 소화했다.
그 구간의 알림 발생량이 약 **301 msg/s**이므로 **수정 전 49 msg/s의 6배 이상**이다.

## 남은 것

- **상한을 못 찾았다.** 400대에서도 lag이 안 쌓여서 한계치가 나오지 않았다.
  차량을 더 늘려도 시뮬레이터가 단일 프로세스당 약 1,000-1,250 msg/s에서 먼저
  막히므로(ADR-015), 상한을 재려면 시뮬레이터를 여러 프로세스로 띄워야 한다.
- **배치 크기를 튜닝하지 않았다.** `max.poll.records`(2,000)를 저장 경로와 공유한다.
  알림은 건당 처리 비용이 다르므로 최적값이 다를 수 있다.
- **DB 장애 시 재시도로 바뀐 동작을 실측하지 않았다.** PostgreSQL 장애를 다시 주입해
  DLQ가 실제로 줄었는지 확인해야 한다(예전 실측: 60초 장애에 DLQ 9건).
- **`findByEventId`는 여전히 건당 1회다.** `INSERT … RETURNING`으로 합치면 쿼리가
  절반이 되지만, 배치화만으로 유입을 전량 소화하므로 지금은 필요 없다.
- 각 조건 1회 실행이다.
