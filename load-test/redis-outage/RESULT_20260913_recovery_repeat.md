# Redis 회복 지연 — 30초·90초 반복 측정과 원인

> 상태: **30초·90초 각 3회 완료(2026-09-13).** 조건별 3회 관측이며 안정성 보장이 아니다.
>
> **결론 한 줄**: **6회에서 앱 경로 회복이 Lettuce `Reconnected` 로그와 겹쳤고, 재연결 대기가 회복 지연의 주요 후보다.**
> Redis 자체는 매번 기동 약 1.5초 뒤 응답했다. 30초는 +4·+24·+6초, 90초는 +25·+34·+34초로 흩어졌다.
> **원인은 확정하지 않았다** — 겹침은 관측이고, 90초가 30초 상한의 배수라 생긴 위상 효과도 배제하지 못했다(§2-4).

## 0. 무엇을 구분하나

| 시각 | 무엇으로 재나 |
| --- | --- |
| 기동 명령 | `docker start` 호출 직전 (`timeline.txt`의 `start_cmd_ms`) — **모든 시각의 기준 0** |
| Redis 응답 가능 | 컨테이너 안 `redis-cli ping`이 PONG을 돌려준 **명령 종료** 시각 (v2 2회차부터. 이전은 §3 참고) |
| backend 재연결 | backend 로그 `ReconnectionHandler - Reconnected to redis` (docker 타임스탬프) |
| 경로별 회복 | 경로마다 **마지막 실패 응답 종료 ~ 첫 성공 응답 종료** 구간 (`recovery_window.sh`) |

**한 경로의 회복으로 다른 경로의 회복을 추정하지 않는다.** 각 경로가 자기 폴러를 가진 v2 실행만
경로별 구간을 온전히 갖는다. v1 30초 실행은 조회·진단·로그인에 탐침 공백이 있어 상한만 있다(§3).

### 1-1. 조건별로 모으면

| 조건 | 앱 경로 회복(기동 명령 기준, 첫 성공 응답) | 재연결 로그 |
| --- | --- | --- |
| 30초 × 3 | **약 +4s**(v1, 일부 경로 상한) / **+24.1s** / **+6.0~6.8s** | +3.2 / +24.1 / +5.9 |
| 90초 × 3 | **+23.5~25.7s**(v1) / **+34.3~34.5s** / **+34.2~35.5s** | +25.2 / +34.3 / +34.2 |

**6회 모두 경로 회복 구간이 `Reconnected` 로그 시각과 겹쳤다.** 다섯 경로는 한 실행 안에서 1~2초 폭으로 함께 회복했다 —
재연결 하나에 같이 묶인다. **Redis는 매번 +1.5s 안팎에 응답했다** — 앱이 503을 낸 나머지 시간 동안 재연결 성공 로그는 없었고,
재연결 대기가 그 시간의 주요 후보다.

조건: 같은 backend 이미지 `sha256:1dade0e5…`, Kafka 기동 상태, 무부하(탐침만). v2는 경로 폴러가 연속이라
장애 중 요청 수가 v1보다 많다 — 재연결 주기는 요청과 무관하게 돈다(아래 §2)는 전제로 비교한다.

**30초 두 번이 4초와 24초로 갈렸다.** 그래서 "중단이 길면 회복이 늦다"는 설명은 성립하지 않는다.

## 2. 원인 — 증거로 설명되는 부분

**관측**: 6회 모두 경로 회복 구간이 `Reconnected` 로그 시각과 겹쳤다. 아래는 그 사이의 대기를 설명하는 **후보**다 —
재연결 시각을 바꿔 회복이 따라 움직이는지는 검증하지 않았다.

1. **Lettuce 재연결 시도 간격이 벌어진다.** 로그상 시도 간격이 수 초 → 약 10초 → 20초 → **30초**로 늘었다
   (v1 90초 실행: 02:33:28 → 02:33:58 → 02:34:02 → 02:34:32). 이 간격 안에서 Redis가 살아나면
   다음 시도까지 기다린다. v1 90초는 기동 5초 전 시도가 실패해 30초 뒤(+25.2s)에 붙었다.

   **상한 30초는 사용 버전의 기본값이다.** runtimeClasspath의 `io.lettuce:lettuce-core:6.3.2.RELEASE`
   (`./gradlew dependencyInsight --dependency lettuce-core --configuration runtimeClasspath`, Spring Boot 3.2.5 관리 버전)에서
   `DefaultClientResources.DEFAULT_RECONNECT_DELAY`가 `Delay.exponential()`이고, `Delay`의 정적 초기값이
   하한 `Duration.ZERO`·상한 `Duration.ofSeconds(30)`·밑 2·단위 `MILLISECONDS`다(Gradle 캐시 jar를 `javap -c -constants`로 확인).
   앱 코드에는 `ClientResources`·`reconnectDelay` 설정이 없다. 개선 이미지 90초 실행(`140039`)에서도 실패 로그 뒤 다음 시도까지
   30.1s·30.0s였다(05:01:47.78→05:02:17.87, 05:02:21.84→05:02:51.87). **실행 중인 컨테이너 안의 jar는 직접 열어보지 않았다** —
   같은 Gradle 설정으로 빌드했다는 전제다.
2. **기동 직후 시도도 실패할 수 있다.** v2 30초 1회차에서 +7.7s 시도가 이름 해석 실패(`redis`)로 끝났다 —
   `docker start`는 +1.4s에 끝났는데도. backend JVM 설정은 `networkaddress.cache.negative.ttl=10`이고
   (**컨테이너 안 `java.security`에서 확인**), 직전의 실제 조회 실패(`Name or service not known`)가
   기동 명령 0.6초 전이라 +7.7s는 그 10초 창 안이다. **그래서 캐시된 실패였을 가능성이 크다.**
   근거는 로그 메시지 형태(실제 조회 실패는 사유가 붙고, 이 시도는 호스트명만 찍혔다)와 시각이며,
   **캐시 적중을 직접 관측하지는 않았다** — 추론으로 둔다.

3. **기동 명령과 거의 동시에 온 시도는 실제 DNS 조회로 실패했다.** v2 90초 1회차에서 기동 명령 +0.3s에 시도가
   시작됐고, 컨테이너가 네트워크에 붙기 전이라 **4초 뒤 `Name or service not known`**(사유가 붙은 실제 조회 실패)으로
   끝났다. 다음 시도가 30초 뒤(+34.3s)였다. Redis PONG 응답은 +1.5s였다 — **Redis가 응답한 뒤 33초 동안 앱은 503**.

4. **90초 세 번은 모두 기동 명령 근처(−5.1s, +0.3s, +0.2s)의 시도가 실패하고 30초 뒤에 붙었다.** 시도 간격이 30초에
   이른 뒤라면, 중단 시간 90초가 **30초의 배수**라 시도 위상이 매번 기동 시각 근처에 떨어졌을 수 있다.
   **확인하지 않은 가설이다** — 그래서 "90초 중단은 약 25~35초 늦게 회복한다"로 일반화하지 않는다.
   확인하려면 30의 배수가 아닌 중단 시간(예: 75초·105초)으로 같은 측정을 반복해야 한다 — **이번에는 추가하지 않는다**(백로그).

**DNS 실패를 일반화하지 않는다.** 기동 근처 시도가 이름 해석 실패로 끝난 것은 6회 중 4회(1회는 캐시 추정)이고,
나머지는 `No route`(v1 30초)·connection timeout(`132128`)이었다. DNS 실패는 **개별 시도가 실패한 사유**로 관찰됐을 뿐,
회복 지연 전체를 설명하는 원인으로 보지 않는다 — 실패 뒤 남는 대기는 위 1의 재연결 간격이다.

**미확정으로 남기는 것**: 각 대기가 지수 증가의 몇 번째 값인지(시도 횟수가 언제 초기화되는지)는 로그와 대조하지 않았다.
시도 시각이 실행마다 어디에 떨어지는지는 **정지 시각과 연결 두 개의 시도 일정**에 달려 있어 예측하지 않았다.

## 3. 측정 방법의 한계

- v1 두 실행은 회복 탐침이 장애 회차 뒤에 시작돼 공백이 있다. 90초는 전 경로가 공백 전에 실패를 남겨
  구간이 온전하고, 30초는 조회·진단·로그인이 상한만 있다.
- v2 30초 1회차의 Redis PONG(+0.1s)은 `docker exec` **시작** 시각이라 하한이다. 2회차부터 종료 시각도 남긴다.
- 폴러 간격은 요청 시간(장애 중 2~4s) + 1s라 구간 폭이 수 초다.
