# Redis 장애 알림 — 왜 복구 뒤에야 울리나, 무엇을 고쳤나

> 상태: **완료(2026-09-13)** — 기존 실행 분석, 기존 규칙 반복 4회, 개선 검증 3회(짧은 장애·30초·90초 각 1회). 결론은 §7, 정책 결정은 §7-4.
> 결과는 조건별 관측이며 안정성 보장이 아니다.

## 0. 이 알림이 무엇을 알리는지 — 먼저 정의

| | 기존 규칙 (`increase(...[5m]) > 0`, `for: 1m`) |
| --- | --- |
| 참이 되는 조건 | **최근 5분 안에** Redis 때문에 거부·무제한 통과된 요청이 있었다 |
| firing | 그 조건이 1분 넘게 이어진 뒤 |
| 해제 | **마지막 증가가 5분 창에서 빠진 뒤** |
| 실제 성격 | "진행 중인 장애"가 아니라 **"최근 5분 내 발생 이력"에 1분 확인을 더한 것** |

**목표 정의(이번 작업)**: 알림은 **요청 처리에서 관찰한 Redis 영향이 진행 중**임을 알린다 — 그런 영향이 약 1분 이상 이어지면
진행 중에 firing하고, 실패 요청이 멈추면 약 1분 안에 해제한다. **Redis 자체의 가용성 감시나 장애 지속 시간 측정이 아니다**(§7-4 결정).

**짧은 장애는 알림으로 전달되지 않을 수 있다(검증에서 확인, §6-2).** 처음에는 "1분보다 짧은 장애는 복구 직후 짧게 firing했다
해제되는 이력으로 남는다"고 적었는데 **발송 기준으로는 틀렸다.** 30초 중단 검증에서 firing이 평가 한 번(15초)만 이어지고
해제됐고, Alertmanager의 첫 발송 대기(`group_wait: 30s`)가 끝나기 전이라 **로컬 수신기에 아무것도 오지 않았다.**
그런 장애는 Prometheus의 `ALERTS` 이력과 지표에만 남는다. 짧은 장애까지 사람에게 알려야 한다면 이 규칙이 아니라
별도의 "최근 발생 이력" 규칙이나 대시보드가 필요하다 — **추가하지 않기로 결정했다**(수용, §7-4).

**탐지 한계(규칙을 어떻게 바꿔도 남는다)**: 두 카운터는 **Redis를 쓰는 요청이 실패할 때만** 오른다.
Redis가 죽어 있어도 그동안 그런 요청이 없으면 0에 머물고 알림도 없다. 이 알림은 "Redis가 내려갔다"가 아니라
"Redis 때문에 요청이 거부·무제한 통과되고 있다"를 알린다.

## 1. 지연을 이루는 단계

| 단계 | 크기 | 근거 |
| --- | --- | --- |
| 요청 → 카운터 증가 | 요청 종료 시점. fail-open은 Redis timeout(2s) 뒤, 진단은 두 인터셉터라 2s·4s | 코드 |
| 증가 → 첫 scrape | 0~15s | `scrape_interval: 15s` |
| **새 시계열 첫 값** | **scrape 1회(15s) 이상 추가** — `increase()`는 직전 샘플이 없는 첫 값을 증가로 안 센다 | TSDB 원본 §2 |
| scrape → 규칙 평가(pending) | 0~15s | `evaluation_interval: 15s` |
| pending → firing | **60s** | `for: 1m` |
| firing → Alertmanager 발송 | `group_wait: 30s` | 설정. 발송 시각은 §4에서 측정 |
| 마지막 증가 → 해제 | **약 300s** + 평가 정렬 | `[5m]` 창 §2 |
| 해제 → resolved 발송 | 다음 `group_interval: 5m` 경계까지 | 설정. §4에서 측정 |

거부 알림이 늦은 것은 첫 거부가 진단(4s)·로그인(2s) 요청 **종료** 시점에 올라 +5.8s scrape를 놓쳤기 때문이다.

## 3. 원인 정리

1. **`for: 1m`**이 firing의 가장 큰 고정 지연이다(60s). 30초 장애는 이것만으로 복구 뒤 firing이 확정된다.
2. **새 시계열 첫 값 누락**이 15~30s를 더한다 — backend 기동 뒤 첫 장애, 또는 새 경로가 처음 실패할 때마다.
3. **`[5m]` 창**이 해제를 마지막 실패 후 약 5분으로 만든다. "진행 중" 알림으로 읽으면 복구 뒤 5분간 거짓 경보다.

## 4. 반복 측정 — 기존 규칙, v2 도구 (Prometheus 평가 + 로컬 수신기 발송)

알림 경로: Prometheus → **실험 전용 Alertmanager**(`alertmanager-exp.yml`, 타이밍 값은 운영 설정과 동일) →
**로컬 수신기**(`alert_sink.py`). 외부 전송 없음. 시각은 중지 완료 기준.

| 실행 | 시계열 상태 | pending | firing | 수신기 firing | firing→발송 | 해제(추정) | 수신기 resolved | 해제→발송 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 30초 `130228` | **새로 생김**(backend 재시작 직후) | +36.0 | +96.0 | +141 | **45s** | +351 | +441 | **90s** |
| 90초 `131217` | 있음 | +17.6 | +77.6 | +153 | **75s** | +422.6 | +453 | **30s** |
| 30초 `132128` | 있음 | +21.7 | +81.7 | +127 | **45s** | +336.7 | +427 | **90s** |
| 90초 `132920` | 있음 | +14.9 | +74.9 | +120 | **45s** | +419.9 | **+720** | **300s** |

90초 `132920`은 **해제(+419.9s)가 300초 경계(+420s, firing 발송 +120s 뒤)를 약 0.1초 차이로 놓쳐** resolved 발송이
다음 경계(+720s)까지 밀렸다 — 해제 뒤 5분. 같은 실행에서 firing은 앱 경로 회복(+123.7s)보다 **앞섰다**(시계열이 이미 있었고
실패 구간이 길었다). 즉 기존 규칙도 **길고, 시계열이 이미 있는 장애**에서는 진행 중 firing이 가능했다.

- **새 시계열 효과가 다시 보였다.** 새로 생긴 상태의 30초 실행은 첫 scrape(+13.0s)에서 증가가 안 보여 pending +36s,
  시계열이 있던 두 실행은 첫 scrape에서 바로 보여 pending +17.6s·+21.7s였다.
- **firing 발송은 firing 평가 뒤 45s가 2회, 75s가 1회였다.** 45s는 `group_wait: 30s`보다 15s 길고, 그 15s가 어디서
  왔는지는 확인하지 않았다. 75s(90초 실행)는 직전 실행의 resolved 발송에서 정확히 300초 뒤였지만 **다음 30초 실행에서는 그렇게 되지 않아**
  한 번의 관측으로만 둔다 — 원인 미확인.
- **resolved 발송은 세 실행 모두 firing 발송 뒤 정확히 300초**(`group_interval: 5m`)였다. 그래서 해제→발송은
  해제 시각이 그 경계에서 얼마나 떨어져 있느냐에 따라 30~90s로 달라졌다.
- **규칙을 고쳐도 발송 쪽 지연은 그대로다**: firing 발송은 평가 뒤 약 45s 이상, resolved는 firing 발송 뒤 300초 경계를 기다린다.
  해제가 빨라지면 **resolved 알림은 오히려 300초 경계까지 더 오래 기다리게 된다**(§6-3: 해제 +190.6s → resolved 발송 +416s).

## 5. 개선안 — **검증 실행 전에 적은 가설과 성공 기준**

### 5-1. 바꾸는 것 (최소 변경)

| | 기존 | 개선 |
| --- | --- | --- |
| 알림이 보는 카운터 | 경로별 `telemetry_*_total{route}` — **첫 실패에서 시계열 생성** | 경로 합계 `telemetry_redis_unavailable_all_total`·`telemetry_ratelimit_failopen_all_total` — **기동 시 0으로 등록**, 라벨 없음 |
| 창 | `[5m]` | **`[1m]`** — 실패가 멈추면 약 1분 뒤 거짓이 된다("진행 중" 정의) |
| `for` | 1m | **1m 유지** — 확인 구간을 없애지 않는다 |
| 임계 | `> 0` | `> 0` 유지 |

경로별 카운터는 "어디서"를 보는 용도로 **그대로 둔다.**
`[1m]`은 scrape 주기(15s)의 4배라 창 안에 샘플이 최소 4개 들어간다 — 더 짧으면 샘플 부족으로 값이 끊긴다.

**고르지 않은 것**: `for` 제거·단축(짧은 실패 한 번에도 발송), 임계 상향(`increase()`가 보간해 소수가 나오므로
"2건 이상" 같은 임계는 흔들린다), 경로별 시계열을 기동 시 전부 0으로 등록(경로 목록을 따라가야 하고 새 경로에서 구멍이 다시 열린다),
Alertmanager `group_wait`·`group_interval` 조정(이번 범위 밖 — 측정만 한다).

### 5-2. 예상 (요청이 계속 들어오는 조건)

- 첫 실패 종료 → 다음 scrape(≤15s)에서 **바로 보이는 증가** → 다음 평가(≤15s) pending → 60s 뒤 firing.
  즉 **firing ≈ 첫 실패 + 75~90s**.
- 해제 ≈ 마지막 증가 scrape + 60s + 평가 정렬(≤15s) → **마지막 실패 후 약 75~90s**. 기존은 약 300s.
- 앱 경로가 실패하는 시간 = 중단 + 재연결 지연(이번 측정에서 +3~34s)이라, **30초 중단도 재연결이 늦으면 실패 중에 firing할 수 있다.**
  이건 규칙이 아니라 재연결 시각에 달렸다 — 판정은 "실패 구간 안에 firing했는가"로 한다.
- **실패 1건짜리 짧은 장애**: `increase(...[1m]) > 0`이 참인 시간이 약 60s라 `for: 1m`과 겹친다. firing 여부는 **예측하지 않고 기록만** 한다.

### 5-3. 성공 기준

| # | 기준 | 적용 |
| --- | --- | --- |
| S1 | 합계 카운터가 첫 실패 직후 scrape에서 **보이는 증가**로 잡힌다(새 시계열 0) | 전 실행 |
| S2 | 실패 구간이 90s보다 긴 실행에서 **firing 평가가 앱 경로 첫 성공 응답보다 앞선다** | 90초 |
| S3 | **해제(추정)가 마지막 증가 scrape + 90s 이내** | 전 실행 |
| S4 | 짧은 장애에서도 S3을 만족한다. firing 여부는 기록만 | 짧은 장애 |

Alertmanager 발송 지연은 성공 기준에 넣지 않는다 — 규칙과 별개로 그룹 주기에 달렸다(§4). 각 조건 1회 관측이다.

## 6. 개선 검증 — 새 규칙 + 기동 시 0 등록 (backend 이미지 `sha256:3559175f…`, 규칙 sha `426da98e…`)

알림 경로와 도구는 §4와 같다(v2, 실험 전용 Alertmanager + 로컬 수신기, 외부 전송 없음). 시각은 중지 완료 기준.

### 6-1. 짧은 장애 — 실패 요청 1건 (`evidence/20260913-135542`, 모드 `blip`)

Redis 중지 → 로그인 1회(503) → 즉시 기동 → 20초 뒤 경로별 1회 확인(전부 성공). 거부 합계 1, fail-open 합계 0.

| scrape | 경로별 `unavailable` | 합계 `unavailable_all` |
| --- | --- | --- |
| −0.9s | (없음) | 0 |
| **+14.1s** | 1 — **새 시계열, 보이는 증가 0** | 1 — **보이는 증가 1** |

| | RedisUnavailableRejections |
| --- | --- |
| pending | **+22.0s** ~ +52.0s |
| firing | **없음** — 참인 시간 약 45s가 `for: 1m`에 못 미쳤다 |
| 해제 | +67s 평가에서 거짓(마지막 증가 scrape +14.1s의 직전 샘플 −0.9s가 `[1m]` 창에서 빠짐) |
| 로컬 수신기 | 0건 |

- **S1 충족 — 같은 실행 안에서 두 카운터가 갈렸다.** 경로별 카운터는 기존과 똑같이 첫 증가를 못 봤고, 기동 시 0으로 등록된 합계는 봤다.
  기존 규칙이었으면 이 1건은 pending조차 되지 않았다.
- **S4 충족** — 마지막 증가 scrape 후 약 53s에 거짓.
- **실패 1건짜리 장애는 발송되지 않았다.** `for: 1m`이 거른 것이다. 이 결과는 1회 관측이며, 실패 시각이 scrape에 가까우면
  참인 시간이 60s를 넘어 firing할 수도 있다 — **"한 건이면 절대 안 울린다"로 읽지 않는다.**

### 6-2. 30초 중단 (`evidence/20260913-135755`)

중단 30.1s. 앱 경로 회복: 기동 명령 기준 +6.0~6.9s(재연결 +6.0s) → 중지 완료 기준 **실패 구간 약 +37s까지**. 429 0건.

| | 두 알림 모두 |
| --- | --- |
| 첫 보이는 증가(합계) | **+17.1s** (첫 실패 뒤 첫 scrape) |
| pending | +25.0s |
| firing | **+85.0s — 평가 1회뿐** |
| 해제(추정) | **+100.0s** — 마지막 증가 scrape(+47.1s) 뒤 약 53s |
| 로컬 수신기 | **0건** — firing이 `group_wait` 30s보다 먼저 끝났다 |

- **S1·S3 충족.** 기존 규칙의 30초 실행은 해제가 마지막 증가 뒤 약 300s였다(§2·§4).
- firing은 앱 경로 회복(+37s) **뒤**였다 — 실패 구간이 `for: 1m`보다 짧으면 규칙을 어떻게 잡아도 진행 중 firing은 안 된다.
- **발송 0건이 이번 검증의 가장 중요한 발견이다.** 새 규칙은 해제가 빨라진 대신, 짧은 장애의 firing이 발송 대기보다 짧아져
  **알림 자체가 사라질 수 있다.** 기존 규칙에서는 해제가 늦어 firing이 5분 넘게 이어졌으므로 이런 일이 없었다.
  즉 "진행 중" 의미를 얻은 대가로 **짧은 장애의 발송을 잃었다.** Alertmanager 내부 상태(그룹·nflog)는 보지 않았고,
  수신기 로그와 `api/v2/alerts`가 비어 있는 것으로 판단했다.
- 조회 범위 주의: 이 실행의 요약(`summary.txt`)에 거부 알림 pending이 −110s로 찍혔는데 **직전 짧은 장애 실행의 샘플**이다.
  위 표는 `alert_timeline.sh <dir> <stop_done_ms> <stop_done_s−5>`로 이번 실행만 잘랐다.

## 7. 결론

### 7-1. 무엇이 나아졌나 — Prometheus 평가 기준

| | 기존 규칙 | 새 규칙 |
| --- | --- | --- |
| 첫 증가를 보나 | **시계열 상태에 따라 다름** — 새로 생기면 1~2 scrape 늦음(v1 90초·v2 30초 1회차) | **항상 봄**(짧은 장애에서 같은 실행 안 비교, §6-1) |
| 90초 중단 firing | +74.9~+110.9s(4회) | +70.6s(1회) — **실패 중** |
| 해제 | 마지막 증가 뒤 약 300s | **마지막 증가 뒤 약 53s**(3회 모두) |
| 알림의 뜻 | 최근 5분 내 발생 이력 | **요청 영향 진행 중**(최근 1분 동안 계속) |

기존 규칙도 **시계열이 이미 있고 실패가 긴** 90초 실행에서는 실패 중에 firing했다(+74.9s). 새 규칙이 확실히 바꾼 것은
**firing이 시계열 상태에 좌우되지 않게 된 것**과 **해제가 5분에서 약 1분으로 줄어든 것**이다. 90초 firing 시각 자체는 비슷하다.

### 7-2. 무엇을 잃었나 — 발송 기준

- **짧은 장애는 발송되지 않을 수 있다.** 30초 중단에서 firing이 평가 1회로 끝나 `group_wait: 30s` 전에 풀렸고 수신기 0건(§6-2).
  기존 규칙은 firing이 5분 넘게 이어져 이런 일이 없었다.
- **resolved 발송은 여전히 최대 5분 늦다**(`group_interval: 5m`). 규칙으로는 못 바꾼다.

### 7-3. 여전히 남은 한계

- **요청이 없으면 울리지 않는다** — 카운터는 Redis를 쓰는 요청이 실패할 때만 오른다. Redis 자체 상태를 보는 신호가 아니다.
- **실패 구간이 `for: 1m` + 탐지(최대 약 30s)보다 짧으면 진행 중 firing은 불가능하다.**
- 각 조건 1회 관측이다. firing 발송 45s 중 15s의 출처, 75s가 나온 1회의 원인은 확인하지 않았다(§4).

### 7-4. 결정 (2026-09-13)

1. **짧은 장애(실패 1건·30초 수준)가 발송되지 않는 것을 이번 범위에서 수용한다.** 별도 "최근 발생 이력" 알림은 추가하지 않는다.
   그런 장애는 경로별·합계 카운터, 대시보드, 로그, Prometheus `ALERTS` 이력으로 조회한다.
2. **두 알림은 "요청 처리에서 관찰한 Redis 영향" 알림이다.** Redis 자체의 가용성 감시도, 장애 지속 시간의 측정도 아니다 —
   firing 수신은 Redis가 응답한 뒤였고(§6-4), 해제는 마지막 실패 요청 뒤 약 1분이다. **요청이 없을 때의 장애 탐지는 백로그**(`docs/roadmap.md` 3c).
3. **Alertmanager `group_wait`·`group_interval`은 바꾸지 않는다.** firing 수신이 앱 회복 뒤일 수 있다는 한계(§6-4)를 그대로 둔다.
4. 규칙 파일은 검증한 그대로다(sha `426da98e…`) — 이 결정은 정의와 문서만 바꿨다.
