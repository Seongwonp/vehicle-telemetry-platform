## 90초 중단 — `evidence/20260913-113206/`

### 경로별 응답

| 경로 | 기준(Redis 정상) | **중단 중** (4회) | 정책 |
| --- | --- | --- | --- |
| 일반 조회 `GET /api/vehicles` | 200 · 0.54s | **200** · 2.02s | fail-open |
| 미인증 조회 | 403 · 0.03s | **403** · 0.01~0.03s | 인증 유지 |

| refresh(없는 토큰) | 401 · 0.02s | **503 `REDIS_UNAVAILABLE`** · 4.02~4.03s | fail-closed |
| liveness | 200 | **200** · 0.02s | |
| readiness | 200 | **200** · 0.01~0.02s | redis 제외 반영 |

**refresh도 4초다.** 진단과 같은 이유로, 일반 rate limit 인터셉터(fail-open, 2초)를 먼저 지나고
토큰 저장소(2초)에서 다시 막힌다. 그래서 `/api/auth/refresh`도 `failopen`과 `redis_unavailable`에
**동시에 오른다.**

### 회복 — 기동 명령 기준, **응답 종료 시각**으로 계산

`bash load-test/redis-outage/recovery_window.sh evidence/20260913-113206` (원본 `probes.csv`에서 재계산)

| 경로 | 판정 | 마지막 실패 응답 종료 | 첫 성공 응답 종료 |
| --- | --- | --- | --- |
| 일반 조회 | 200 + `X-RateLimit-Remaining` 재등장(제한 재적용) | +23.5s | **+25.5s** |
| 진단 | 503 아님(404) | +19.6s | **+25.1s** |
| 로그인 | 200 | +23.6s | **+25.7s** |
| refresh | 401(없는 토큰을 저장소가 정상 거부) | +19.5s | **+25.1s** |
| 종합 health | 200 | +23.8s | **+25.7s** |
| Redis 자체 | `redis-cli ping` = PONG | — | **+9.0s** |

- **다섯 경로가 +23.5~+25.7s 사이에 함께 회복했다.** Redis가 PONG을 돌려준 뒤 **약 15~16초 동안 앱은 계속 503**이었다.
  재연결이 늦은 것으로 보이나 **Lettuce 재연결 주기를 직접 재지는 않았다.**
- 해상도: 한 경로의 "마지막 실패 종료 ~ 첫 성공 종료" 사이 어딘가에서 회복했다는 것까지다.

> **측정 방법 정정 (같은 날)**: 처음에는 탐침 **시작** 시각으로 표를 만들어 refresh·진단이 +21.7s로
> 로그인(+25.5s)보다 먼저 회복한 것처럼 보였다. 장애 중 2~4초 걸리는 요청의 시작 시각이라 생긴 착시였다.
> 봉인된 `summary.txt`·`recovery.csv`는 그대로 두고, 이후 실행의 요약은 위 계산을 쓰도록 스크립트를 고쳤다.
- 중단 전에 받은 **refresh 토큰은 재기동 뒤에도 유효했다**(200). Redis가 종료 시 저장한 RDB를 다시 읽은 것으로 보이며,
  **영속성 설정을 따로 검증한 것은 아니다**(compose는 `--requirepass`만 준다).

### 알림 — 중지 완료 기준

| | RedisUnavailableRejections | RateLimitFailingOpen |
| --- | --- | --- |
| pending | +54s | +76s |
| **firing** (= Alertmanager 수신) | **+120s** | **+138s** |
| **해제** (Prometheus inactive, Alertmanager 활성 목록에서 사라짐) | **+436s** | **+436s** |

참고: Redis 기동 완료 +93s, 앱 경로 회복 약 +115s. 알림 표본 간격은 장애 중 약 22~25초, 복구 후 15초.

**읽는 법:**

1. **두 알림 모두 Redis가 돌아온 뒤에 firing됐다.** `for: 1m` + scrape/평가 15초 + 아래 2번 때문이다.
   이 조건에서 **90초짜리 중단의 알림은 "지금 장애 중"이 아니라 "방금 장애가 있었다"로 도착한다.**
2. **새로 생긴 카운터의 첫 증가는 `increase()`에 안 잡혔다.** fail-open 카운터는 첫 장애 요청에서
   시계열이 생기는데, 장애 시작 +28초 표본에서 `increase(...[5m])`가 `nodata`였다(`alerts.csv`).
   그래서 fail-open 알림이 거부 알림보다 약 20초 늦었다.
3. **해제는 마지막 증가 후 약 5분 20초였다.** `increase(...[5m])` 창이 비워질 때까지 참이기 때문이다.
   누적값을 `> 0`으로 비교하지 않으므로 **해제가 실제로 일어났다** — 이번 실행이 그 확인이다.
4. Alertmanager 수신·해제는 **로컬 활성 목록**으로만 확인했다. **외부 수신자 전송은 검증 범위 밖이다.**

## 30초 중단 — `evidence/20260913-114124/`

중단 30.25초. 진단 차량 ID `DG30-114128`(90초 실행과 다르다). 429 **0건**.

### 경로별 응답

| 경로 | 기준 | **중단 중** | 비고 |
| --- | --- | --- | --- |
| 일반 조회 | 200 · 0.01s | **200** · 2.01~2.03s (2회) | fail-open |
| 미인증 조회 | 403 | **403** · 0.01s | |
| 진단 | 404 · 0.03s | **503 `REDIS_UNAVAILABLE`** · 4.01~4.02s (2회) | |
| 로그인(맞는 비밀번호) | 200 | **503 `REDIS_UNAVAILABLE`** · 2.01s (2회) | |
| 로그인(틀린 비밀번호) | **401** · 0.18s | **503 `REDIS_UNAVAILABLE`** · 2.01s (1회) | |
| refresh(없는 토큰) | 401 · 0.01s | **503** · 4.01s (1회) | 2회차는 기동 뒤라 401 |
| liveness / readiness | 200 / 200 | **200 / 200** | |
| 종합 health | 200 | **503** · 2.02s (1회) | 2회차는 기동 뒤라 200 |

장애 회차가 둘뿐이라 2회차 후반 탐침은 **Redis 기동 뒤에** 나갔다(표의 "기동 뒤" 칸). 원본에서 시각으로 가를 수 있다.

### 회복 — 기동 명령 기준, 응답 종료 시각

| 경로 | 마지막 실패 응답 종료 | 첫 성공 응답 종료 |
| --- | --- | --- |
| refresh | (기동 뒤 실패 없음) | **+4.3s** |
| 종합 health | (기동 뒤 실패 없음) | **+6.5s** |
| 로그인 | +3.5s | +10.9s |
| 진단 | +0.8s | +10.8s |
| 일반 조회 | −5.1s | +10.7s |

로그인·진단·조회는 +3.5s 이후 +10.7s까지 **탐침이 없었다** — 회복 탐침이 진행 중이던 장애 회차가 끝난 뒤에야
시작됐기 때문이다. 그래서 이 셋의 +10.7~10.9s는 **상한일 뿐**이다. 같은 Redis 연결을 쓰는 refresh가 +4.3s에 성공했고
로그인이 +3.5s에 실패했으므로, **공유 연결의 회복은 +3.5~+4.3s 사이로 본다.**
연결 공유는 Spring Data Redis Lettuce 기본 구성에 기댄 판단이며 **따로 확인하지 않았다.**
요약 파일의 `redis_ping +10.6s`도 같은 이유로 상한이다.

중단 전 refresh 토큰은 이번에도 재기동 뒤 유효했다(200).

### 알림 — 중지 완료 기준

| | RateLimitFailingOpen | RedisUnavailableRejections |
| --- | --- | --- |
| pending | +38s | +46s |
| **firing** (= Alertmanager 수신) | **+101s** | **+119s** |
| **해제** (Prometheus inactive, Alertmanager 활성 목록에서 사라짐) | **+360s** | **+360s** |

Redis 기동 완료 +33s. **30초 중단에서도 두 알림 모두 복구 뒤에 firing됐다.**

**90초 실행과 순서가 반대다** — 이번에는 fail-open 알림이 먼저 pending이었다. 같은 backend 프로세스라 fail-open
카운터 시계열이 90초 실행 때 이미 생겨 있었고, 기준 구간 `increase`가 `nodata`가 아니라 `0`이었다(`alerts.csv` 첫 줄).
90초 실행의 "첫 증가가 안 잡혀 20초 늦었다"는 해석과 **어긋나지 않지만, 통제한 비교는 아니다.**

## 두 실행을 나란히

| | 30초 중단 | 90초 중단 |
| --- | --- | --- |
| 앱 경로 회복(기동 명령 기준) | **약 +4s** | **약 +25s** |
| 알림 firing | 복구 뒤 | 복구 뒤 |
| 알림 해제 | 마지막 증가 후 약 5분 반 | 마지막 증가 후 약 5분 20초 |
| 429 | 0 | 0 |

**중단이 길 때 회복이 크게 늦었다.** Lettuce가 재연결 간격을 점점 늘리는 방식이라면 설명이 되고, 2026-09-12의
8초·30초 차이와도 모순되지 않는다. **하지만 재연결 주기를 재지 않았고 조건별 1회뿐이라 원인으로 적지 않는다.**
확인하려면 같은 조건 3회 + backend의 Lettuce 재연결 로그(`ConnectionWatchdog`) 시각을 함께 남겨야 한다.
