# 기존 환경의 InfluxDB 보존 기간 변경 — 언제 실제로 지워지는가 (2026-09-07)

| 항목 | 값 |
| --- | --- |
| **검증 상태** | **부분 검증** — 1회 |
| 적용 범위 | 단일 Docker Compose(dev), InfluxDB 2.x 단독 기동, **검사 주기를 60초로 낮춘 조건**(운영 기본값은 30분) |
| 코드 상태 | `1b3f79d` + 작업 트리 변경 |
| 실행 명령 | `bash load-test/retention-migration/run_migration.sh` |
| 원본 증거 | `evidence/20260907-101130/` (checksums 포함) |
| 관련 문서 | [`docs/data-retention.md`](../../docs/data-retention.md), [Runbook](../../docs/runbook/influxdb-retention-change.md) |

[`docs/data-retention.md`](../../docs/data-retention.md) 5절에 **"기존 환경의 버킷 보존
변경 절차가 이 저장소 어디에도 없다"**가 미해결로 남아 있었다. 텔레메트리에 GPS가 들어
있으므로 "90일로 설정했다"와 "90일 넘은 위치정보가 실제로 없다"는 **다른 말**이고,
개인정보 처리에는 후자가 필요하다. 그 차이를 재려고 만든 실험이다.

## 결과

| 질문 | 답 | 근거 |
| --- | --- | --- |
| 설정을 바꾸면 **즉시** 지워지나 | **아니오** | 변경 직후 400행 그대로. t+1s·23s·44s 모두 400 |
| 그럼 언제 | **t+65초** | 검사 주기(60초)의 다음 회차 |
| 삭제 중 **쓰기가 막히나** | **아니오** | 프로브 쓰기 실패 **0건**, 최근 행 200 → 220 계속 증가 |
| **되돌리면 복구되나** | **아니오** | 무기한으로 되돌린 뒤에도 **0행** |
| 최근 데이터도 지워지나 | **아니오** | 90일 이내 행은 그대로 |

**핵심은 세 번째와 네 번째다.**

- 삭제는 **온라인으로 일어난다** — 서비스를 멈추지 않는다.
- **되돌릴 수 없다.** 보존을 줄이는 순간부터 다음 검사 주기 안에 초과분이 사라지고,
  설정을 되돌려도 데이터는 돌아오지 않는다. 즉 이 작업은 **일방향**이다.

## 시간 축 (원본: `evidence/.../retention_timeline.csv`)

```
t+1s    90일초과=400  최근=200  쓰기=ok
t+23s   90일초과=400  최근=201  쓰기=ok
t+44s   90일초과=400  최근=202  쓰기=ok
t+65s   90일초과=  0  최근=203  쓰기=ok   ← 검사 주기가 돌면서 삭제
...
t+403s  90일초과=  0  최근=219  쓰기=ok
```

## 주의 — "65초"를 그대로 인용하면 안 된다

이 실험은 **검사 주기를 60초로 낮춰서** 돌렸다(`INFLUXD_STORAGE_RETENTION_CHECK_INTERVAL`).
**InfluxDB 2.x 기본값은 30분**이고 이 프로젝트의 compose는 그 값을 설정하지 않는다.
따라서 운영 환경에서는 **최대 30분까지 초과 데이터가 남아 있을 수 있다.**

즉 이 실험이 증명한 것은 "65초 만에 지워진다"가 아니라
**"설정 변경과 실제 삭제가 분리되어 있고, 그 간격은 검사 주기다"**이다.

## 방법에서 막혔던 것 넷 — 도구의 함정이 대부분이었다

측정 자체보다 **스크립트를 실제로 돌아가게 만드는 데** 시간이 더 걸렸다. 네 번 조용히
죽었고, 넷 다 `set -euo pipefail`과 결합해 **로그 한 줄 없이** 끝났다.

1. **`influx bucket update`는 `--org`를 안 받는다.** `list`·`write`·`query`는 받는다.
   공통 헬퍼로 모든 명령에 `--org`를 붙였더니 이 명령만 실패했다.
2. **`--name`은 대상 선택이 아니라 "새 이름 설정"이다.** 대상 지정은 **`--id`뿐**이라
   버킷 ID를 먼저 조회해야 한다. Runbook에 이 단계를 넣은 이유다.
3. **Git Bash의 경로 변환.** `docker exec ... --file /tmp/seed.lp`의 컨테이너 경로가
   `C:/Users/.../Temp/seed.lp`로 바뀐다. `MSYS_NO_PATHCONV=1`을 붙이면 이번엔
   **호스트 쪽 경로**까지 변환이 꺼져 `D:\tmp\...`를 찾는다. 한쪽만 끌 수 없어
   **파일 경로를 주고받지 않고 stdin으로** 넣는 방식으로 바꿨다.
4. **`| head -N`이 SIGPIPE로 스크립트를 죽였다.** 쓰기는 **이미 성공한 뒤**라 데이터는
   들어가 있고 로그만 멈춰서, 원인을 찾는 데 가장 오래 걸렸다.

그리고 다섯 번째는 Flux 문법이었다 — **`range(stop: now)`는 400 오류**다.
`now`는 함수라 `now()`여야 한다. 첫 조회(`-120d ~ -91d`)는 통과하고 두 번째만 죽어서
"주입은 됐는데 로그가 안 나오는" 모양이 됐다.

**공통 교훈**: `pipefail` 아래에서는 실패가 로그를 남기지 않는다. 실행 직후
증거 디렉터리와 로그가 **진행되는지** 확인하고 다음으로 넘어가야 한다.

## 부수적으로 확인된 것

`docker-compose.yml`의 `INFLUXDB_RETENTION=90d`는 **새로 만드는 버킷에는 제대로 걸린다**
— 초기 보존이 `2160h0m0s`(=90일)로 확인됐다. 어제 넣은 설정이 실제로 동작한다.

## 이 문서의 한계

- **1회다.**
- 검사 주기 60초 조건 **하나**에서만 봤다. 기본값 30분에서의 실제 삭제 지연은 **미측정**.
- 데이터가 **600행**뿐이다. 수억 행 규모에서 삭제가 얼마나 걸리는지, 그때도 쓰기가
  안 막히는지는 **미측정**이다. 실제 운영 데이터는 이보다 훨씬 크다.
- 삭제 중 **조회** 성능은 안 봤다(쓰기만 봤다).
- shard group duration(24시간)과의 상호작용을 안 봤다 — InfluxDB는 shard 단위로 지우므로
  **경계에 걸친 데이터가 언제 사라지는지**는 이 실험으로 답할 수 없다.
