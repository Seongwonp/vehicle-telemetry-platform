# 엔드투엔드 추적 — 한 레코드를 앱까지 따라간다

```bash
bash load-test/e2e-trace/run_scenario.sh          # 마커 20건, 0.5초 간격
bash load-test/e2e-trace/run_scenario.sh 50 0.2   # 마커 50건, 0.2초 간격
```

## 무엇을 재나

지금까지의 정합성 대조는 **단계별 총량**을 맞췄다("발행 162,402 = 토픽 162,402 =
행 162,402"). 총량 대조는 유실을 잡지만 두 가지를 못 본다.

1. **어느 단계에서 얼마나 늦는지.**
2. **저장 경로에서 갈라지는 경로의 누락.** WebSocket 브로드캐스트는 저장과 다른
   가지라, 거기서 빠져도 총량은 그대로 맞는다. 2026-09-05에 이상 알림 쪽에서
   정확히 이런 결함(중복 브로드캐스트)을 찾았는데, 총량 대조로는 안 보였다.

그래서 **표식 차량 한 대**로 소수의 레코드를 흘리고 개별 레코드를 5단계에서 확인한다.

```
MQTT 발행(PUBACK) → Kafka 레코드 → InfluxDB 포인트 → REST 응답 → WebSocket 프레임
```

## 식별자는 차량 ID + 타임스탬프다

payload에 표식 필드를 넣을 수 없다 — 스키마가 고정이고 Bean Validation이 막는다.
대신 **차량 ID + 타임스탬프**를 식별자로 쓴다. 저장 경로의 포인트 키와 같은 조합이라
InfluxDB에서 그대로 조회된다. 마커는 서로 다른 ms를 갖게 만든다(같은 ms면 InfluxDB에서
덮어써진다 — 2026-09-05 ms 충돌 측정).

## 지연 값의 한계를 먼저 적는다

- **WebSocket 지연**은 같은 프로세스에서 발행 시각과 수신 시각을 재므로 시계 오차가 없다.
- **REST 가시성 지연**은 0.5초 폴링이라 **분해능이 500ms**다. 그보다 작은 값은 못 잰다.
- **Kafka·InfluxDB는 도착 여부만** 본다. 컨테이너 시각과 브로커 타임스탬프를 섞으면
  음수 지연이 나온다(실제로 겪었다).

그래서 도구 이미지를 따로 만든다(`Dockerfile`) — MQTT·Kafka·InfluxDB·REST·WebSocket을
**한 프로세스**가 다 해야 시계가 하나로 유지된다.

## 주의

- **배경 부하를 함께 돌린다.** 빈 파이프라인의 지연은 운영에서 볼 값이 아니다.
  마커는 배경(`SIM-*`)과 다른 차량 ID를 쓴다.
- 자격 증명은 `.env`에서 읽어 **환경변수로만** 넘긴다. 출력·증거에 남기지 않는다.
- 마커 차량은 스크립트가 REST로 등록한다. WebSocket 구독 인가(`VehicleAccessService`)가
  등록된 차량만 허용하기 때문이다.
- **`down -v`로 시작한다.**
