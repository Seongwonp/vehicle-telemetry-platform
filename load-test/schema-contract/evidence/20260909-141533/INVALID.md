# 이 실행은 무효다 — 차량 ID가 계약을 위반해서 **PASS 칸까지 못 믿는다**

19칸 중 **15칸이 PASS**로 보였다. 그런데 그중 6칸이 거짓이었다.

주입기가 차량 ID를 `<prefix>-KAFKA-01` 형태로 만들었는데 **21자**다.
계약의 `vehicle_id` 상한은 **20자**(`^[A-Z0-9-]{4,20}$`)라, Kafka 열은 payload 내용과
무관하게 전부 거부됐다. MQTT 쪽(`-MQTT-01`)은 정확히 20자라 통과했다.

| Kafka 열 | 표면 | 실제 |
| --- | --- | --- |
| 저장 기대 3칸 | FAIL | 정상 payload인데 **ID 때문에** 거부 |
| 거부 기대 6칸 | PASS | **시나리오가 아니라 ID 길이 때문에** 거부 — 거짓 PASS |

**FAIL 3칸이 없었으면 이 실행을 성공으로 읽었을 것이다.** 원인을 확정한 것은 판정표가
아니라 DLQ 헤더였다: `PAYLOAD_VALIDATION_FAILED: vehicleId must match "^[A-Z0-9-]{4,20}$"`.

**고친 것**: 입구 코드를 한 글자(M/K)로 줄이고, `inject_contract_cases.py`에
`check_id()` 길이 가드를 넣어 계약 밖 ID를 만들면 즉시 중단하게 했다.
판정 스크립트(`run_e2e.sh`)도 같은 ID 형식을 쓰도록 맞췄다.

**여기서 남길 교훈**: 판정이 PASS를 돌려주는 것과 그 PASS가 옳은 것은 다르다.
그래서 이후 실행에서는 **DLQ 사유를 레코드마다 귀속**시킨다
(`collect_dlq_attribution.sh`).

유효한 최종 실행은 `../20260909-145736`이다.
