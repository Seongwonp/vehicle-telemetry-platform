# 정수 필드(`rpm`) 경계 — 하나는 조용히 잘려서 저장된다 (2026-09-08)

| 항목 | 값 |
| --- | --- |
| **검증 상태** | **부분 검증(각 조건 1회)** |
| 적용 범위 | dev(평문) 프로파일, 파티션 3, 유형당 대조군 100건 |
| 코드 상태 | `e969462` + 작업 트리(`inject_poison.py`에 세 유형 추가) |
| 실행 명령 | `TYPES="rpm_overflow rpm_float rpm_infinity" bash load-test/poison-message/run_scenario.sh 100` |
| 원본 증거 | `evidence/20260908-215336/` (COMPLETE) |

`rpm`은 `int`이고 `toPoint()`에서 `finite()` 검사를 **거치지 않는다**(정수는 Infinity가
될 수 없으니 맞다). 그래서 double 필드들과 **다른 경로**일 텐데, 그 경로를 확인한 적이 없었다.

## 결과 — 셋 중 하나가 다르다

| 유형 | 대조군 저장/주입 | 독성의 종착지 | 어디서 걸렸나 |
| --- | ---: | --- | --- |
| `rpm: 99999999999` | 100 / 100 | DLQ(`permanent`) | 역직렬화 — int 범위 초과 |
| `rpm: 1e309` | 100 / 100 | DLQ(`permanent`) | 역직렬화 — int 범위 초과 |
| **`rpm: 2000.7`** | **101 / 100** | **저장됨** | **아무 데서도 안 걸린다** |

토픽 303건, DLQ **2건**(둘 다 `JsonMappingException` / `permanent`, `unknown` 0).
대조군은 세 유형 모두 전량 저장 — **독성이 정상 레코드를 막지 않는다.**

### 같은 리터럴이 필드 타입에 따라 다른 문에서 걸린다

`1e309`는 `speed`(double)에서는 `Double.POSITIVE_INFINITY`로 **파싱에 성공**해서
`toPoint()`의 `finite()`까지 갔다(2026-09-06·09-08). 같은 리터럴이 `rpm`(int)에서는
**역직렬화 단계에서** 잘린다.

```
Numeric value (1e309) out of range of int (-2147483648 - 2147483647)
 ... (through reference chain: com.telemetry.domain.VehicleTelemetry["rpm"])
```

결과(DLQ, `permanent`)는 같지만 **막는 문이 다르다.** `finite()`가 int 필드를 지켜주고
있다고 생각하면 틀린 것이다 — int 필드는 Jackson이 먼저 막는다.

### `rpm: 2000.7`은 2000으로 잘려서 저장된다 — 신호가 하나도 없다

101/100이 나왔다. 독성 레코드가 **저장됐다는 뜻**이다. 저장된 값을 확인했다.

```flux
from(bucket: "telemetry") |> range(start: -2h)
  |> filter(fn: (r) => r._field == "rpm" and r.vehicle_id == "POISON-RPM-FLOAT")
  |> group() |> distinct(column: "_value")
→ 2000   (단 하나)
```

행이 101개인데 서로 다른 `rpm` 값이 **하나뿐**이다. 즉 독성 레코드의 `2000.7`이
**2000이 됐다.** Jackson의 `ACCEPT_FLOAT_AS_INT`가 기본 활성이라 소수점을 잘라내고,
그 뒤로는 아무도 이상을 모른다 — **DLQ 0, 에러 로그 0, 카운터 변화 0.**
행 수가 맞으므로 정합성 대조(토픽 수 = 행 수)로도 안 잡힌다.

이 프로젝트에서 **조용한 값 변형**은 이걸로 세 번째다.

| | 무엇이 사라졌나 | 조치 |
| --- | --- | --- |
| `WritePrecision.S` 시절 | 같은 초의 뒤 포인트가 앞 포인트를 덮어씀 | 밀리초로 고침 |
| `speed: 1e309` | **필드 하나가 통째로** | `finite()` 추가 → DLQ |
| `rpm: 2000.7` | 소수점 이하 | **고치지 않는다(아래)** |

## 고치지 않기로 한다

이유 넷이다.

1. **손실의 크기가 1 rpm 미만으로 한정된다.** `speed: 1e309`는 필드가 통째로 사라져서
   "값이 없다"와 "0이다"를 구분할 수 없었다. 여기서는 값이 있고 오차가 1 미만이다.
2. **데이터 스펙이 `rpm`을 정수로 정의한다**(`"rpm": 2400`). 소수점이 붙은 rpm은
   스펙 위반이고, 그걸 보내는 장치는 아직 없다.
3. **이상 감지는 영향을 받지 않는다.** 룰은 `anomaly-detector/rules.py`에서
   **원본 JSON을 Python으로 파싱해** 평가한다(`("rpm", lambda v: v > 6000, ...)`).
   `6000.9`는 감지 시점에 `6000.9`라 정상적으로 걸린다. 잘리는 것은 **InfluxDB에
   저장되는 값뿐**이다.
4. **막으려면 `ACCEPT_FLOAT_AS_INT`를 꺼야 하는데** 그러면 `"rpm": 2000.0`처럼
   의미가 같은 형태까지 DLQ로 간다. 지금 들어오지도 않는 입력을 막으려고
   정상 입력의 수용 범위를 좁히는 거래다.

**대신 기록해두는 것**: 저장된 데이터로 사후 분석을 할 때는 `rpm`이 이미 잘려 있다.
`6000.9`로 감지된 이상이 저장 데이터에서는 `6000`이라 **룰을 다시 돌리면 안 걸린다.**
"감지 시점의 값"과 "저장된 값"이 다를 수 있다는 뜻이고, 이건 rpm에만 해당한다
(double 필드는 그대로 저장된다).

## 이 문서의 한계

- **각 조건 1회**다. 예외 클래스로 갈리는 결정적 동작이라 회차 변동 요소는 적다.
- `2000.7` 하나만 넣었다. 반올림이 아니라 **버림**인지는 값 하나로 판단했다
  (2000.7 → 2000이므로 버림이지만, 음수나 `.5` 경계는 안 봤다).
- 다른 정수 경로(`dtc_codes` 배열, `timestamp` 문자열)는 이번 범위 밖이다.
- MQTT 경로로는 주입하지 않았다. 같은 `ObjectMapper`를 쓴다는 코드 근거만 있다.
- `ACCEPT_FLOAT_AS_INT`를 껐을 때 실제로 어떻게 되는지는 **확인하지 않았다**(끄지 않기로 해서).
