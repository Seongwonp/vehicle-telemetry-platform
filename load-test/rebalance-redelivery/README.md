# 리밸런싱 구간 재전달 측정

`bash run_scenario.sh`

## 무엇을 재나

컨슈머 인스턴스가 붙었다 떨어질 때 도는 **리밸런싱 구간에서 몇 건이 재전달되는가**,
그리고 그 재전달이 **저장을 중복시키는가**.

강제 종료(`docker kill`) 시 재전달은 따로 쟀다(`load-test/storage-integrity/`).
이쪽은 실제 운영에서 훨씬 흔하다 — 배포, 스케일 조정, OOM kill이 전부 리밸런싱이다.

대상은 `anomaly-detector`다. 이 프로젝트에서 실제로 여러 인스턴스로 도는 유일한
컨슈머 그룹이고(`replicas: 3`), 파티션 3개에 1:1로 배정돼 있어 인스턴스 수를 바꾸면
반드시 리밸런싱이 돈다. 시나리오는 **3 → 1 → 3**이다.

## 정답 기준 = 토픽의 고유 `event_id` 수

재전달이 생기면 같은 원본 메시지가 다시 처리되어 **같은 event_id가 여러 번 발행**된다.
따라서 `토픽 메시지 수 − 고유 event_id 수`가 곧 재전달량이다.

그 값을 세 곳에서 독립적으로 확인한다 — 토픽 초과분, `count_events.py`의 중복 발행분,
그리고 백엔드 지표 `telemetry_anomaly_stored{result="duplicate"}`.

## 주의

- **`down -v`로 시작한다.** 남겨야 할 데이터가 있으면 돌리지 마라.
- **리밸런싱이 실제로 돌았는지 반드시 확인하라.** 결과의 "리밸런싱 로그 건수"가 0이면
  이 측정은 아무 의미가 없다. 문구는 클라이언트마다 다르다 — `anomaly-detector`는
  kafka-python이라 `Revoking previously assigned partitions`이고, Java 문구로 grep하면
  0이 나온다(처음에 그렇게 재서 잘못된 결론을 낼 뻔했다).
- 스케일 다운으로 사라진 컨테이너의 로그는 함께 사라지므로, 리밸런싱 횟수는 **하한**이다.
- `anomaly-storage-group` 드레인이 오래 걸린다(실측 13분). 끝까지 기다려야 한다.
