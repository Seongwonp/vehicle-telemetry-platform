# 이상 알림 DLQ 재처리 멱등성

`vehicle-anomaly-alerts-dlq`를 재처리했을 때 PostgreSQL에 알림이 **중복 저장되는지**를
잰다. `bash run_scenario.sh [장애 지속 초]` (기본 60초).

## 왜 따로 재야 했나

텔레메트리 DLQ 재처리는 멱등이 확인돼 있다 — InfluxDB 포인트 identity가
(measurement, 태그, ms 타임스탬프)라 같은 메시지를 다시 써도 덮어써진다
(`load-test/storage-integrity/`). **알림은 `INSERT`라 같은 보장이 없다.**
Runbook(`docs/runbook/dlq-reprocessing.md`)이 운영자에게 재처리를 지시하는
경로라서, 중복이 나면 문서가 사고를 유도하게 된다.

## 정답 기준 = 토픽의 고유 `event_id` 수

메시지 수가 아니다. 저장이 `ON CONFLICT (event_id) DO NOTHING`이라 설계상
"같은 event_id는 한 행"이고, 그래서 대조식은 **행 수 == 토픽의 고유 event_id 수**다.

`count_events.py`가 이 기준을 만들면서 같이 재는 것이 하나 더 있다 —
**내용이 다른데 event_id가 같은 경우**. 이건 중복의 반대편이고,
서로 다른 이상이 한 행으로 합쳐지는 것이라 **알림 유실**이다. 더 나쁘다.

## 측정이 의미를 가지려면

재처리 대상 중 **이미 저장돼 있는 것이 몇 건인가**를 먼저 봐야 한다. 0건이면
중복이 날 기회 자체가 없어서 "중복이 안 났다"가 아무것도 증명하지 못한다.
`dlq_event_ids.py` + psql로 이 값을 먼저 찍고, 0이면 스크립트가 경고한다.

실측에서는 DLQ 9건 중 **3건이 이미 저장돼 있었다** — 서버 커밋은 끝났는데 연결이
끊겨 클라이언트만 실패로 본 경우다. 즉 재처리는 "혹시"가 아니라 **반드시**
중복 INSERT를 시도한다.

## 재처리를 두 번 돌린다

2회차는 일부러 **다른 커서 그룹**으로 돌려 같은 레코드를 다시 읽게 한다.
운영자가 "아까 먹었나?" 하고 한 번 더 실행하는 상황이고, 여기서 안전하지 않으면
Runbook이 틀린 것이다.

## 결과 (2026-09-05)

`RESULT_20260905_alert_replay.md`. 요약:

- **행 중복 0건.** 두 번 돌려도 행이 늘지 않았고, 행 수가 정답 기준과 정확히 일치했다.
- **알림 중복은 있었다.** 컨슈머가 `insertIfAbsent` 반환값을 버리고 무조건
  브로드캐스트해서, 재처리 때마다 같은 알림이 다시 나갔다. 고쳤고 재측정으로 확인했다.
- **PostgreSQL 장애는 DLQ를 거의 안 만든다.** 컨슈머가 30초씩 멈춘다
  (HikariCP `connectionTimeout`). 60초 장애에 DLQ 9건.

## 주의

- 스크립트가 시작할 때 **`down -v`로 볼륨을 지운다.** 남겨야 할 데이터가 있으면 돌리지 마라.
- Git Bash에서는 컨테이너 경로 인자가 `W:/`로 바뀐다. 스크립트가 `MSYS_NO_PATHCONV=1`과
  `pwd -W`로 처리한다 — 직접 `docker run`을 칠 때는 같은 처리가 필요하다.
- PostgreSQL 장애 뒤 드레인은 오래 걸린다(실측 5분 이상). 드레인을 덜 기다리면
  행 수와 고유 event_id 수를 서로 다른 시점에 재게 되어 측정이 오염된다.
