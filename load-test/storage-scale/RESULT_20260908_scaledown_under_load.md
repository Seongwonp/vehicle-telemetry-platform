2026-09-07~08에 스케일 다운이 **약 45초짜리**임을 3회 쟀는데 **전부 무부하**였다.
Runbook에는 "부하 중에 내리면 그 파티션의 지연이 그만큼 튄다"고 적어뒀지만
그건 **추론이었다.** 부하를 걸고 다시 쟀다.

## 결과 — 격리는 되고, 대가는 6개 파티션의 완전 정지다

| | 1회차 | 2회차 | 3회차 |
| --- | ---: | ---: | ---: |
| 스케일 다운 | t=208s | t=202s | t=249s |
| `down` 반환 | 11초 | 8초 | 11초 |
| 멤버 9 → 3 관측 | 다운 후 **46초** | 다운 후 **52초** | 다운 후 **54초** |
| 동시 정지 파티션 | (계측 결함, 아래) | **6개** (t=219~245) | **6개** (t=269~295) |
| 발행 정지 후 드레인 | 182초 | 81초 | 93초 |
| **유실** | **0** (8,180,533) | **0** (8,083,729) | **0** (8,359,159) |

토픽 총 offset과 InfluxDB 행 수가 **3회 모두 정확히 일치**한다. 지연이지 유실이 아니다.

재할당은 명령 시점 기준 **46~54초**다. `down` 자체가 부하 중에는 8~11초 걸리므로
(무부하 때는 3~5초) 컨테이너가 실제로 멈춘 뒤부터는 약 35~44초이고, 이는
`session.timeout.ms`(45,000ms)와 같은 자리다. **표본 간격이 약 9초라 그보다 세밀한
비교는 할 수 없다.**

### 파티션별로 보면 두 그룹이 정확히 갈린다

평균 lag(다운 = t+0s 기준):

| 경과 | 제거된 인스턴스가 쥔 6개 | 주 backend의 3개 |
| ---: | ---: | ---: |
| 다운 직전 | 7,137 / 54,313 | 2,244 / 1,268 |
| +8~11s | 75,188 / 58,440 | 13,079 / **1,268** |
| +20s | 109,408 / 94,236 | **1,812** / **1,467** |
| +29s | 144,191 / 129,470 | **2,220** / **1,403** |
| +38s | 177,952 / 164,104 | 12,891 / 6,631 |
| +43s | — / 199,501 | — / **1,324** |
| +46~52s | 재할당 — 주 backend가 전부 인수 | 142,103 / 135,050 |

(각 칸은 `1회차 / 2회차`)

**죽은 인스턴스가 쥔 6개는 25배로 쌓이는데, 살아있는 backend의 3개는 평평하다.**
2회차에서는 주 backend의 3개가 1,268 → 1,324로 사실상 변화가 없다 —
자기 파티션은 계속 따라잡고 있었다는 뜻이다. **장애 격리는 성립한다.**

정지 구간에 6개 파티션에 쌓인 양은 파티션당 약 **17만 건**(1회차 7,137 → 177,952),
합치면 약 **100만 건**이다. 재할당 후 주 backend가 그걸 통째로 인수한다.

### 유실은 0이다

두 회차 모두 토픽 총 offset과 InfluxDB 행 수가 **정확히 일치**한다.
지연이지 유실이 아니라는 것이 숫자로 확인됐다.

## 계측이 이 현상을 못 잡고 있었다 — 1회차의 진짜 수확

처음에 넣은 지표는 **"무소유 파티션 수"**(`CONSUMER-ID`가 `-`인 파티션)였다.
1회차 내내 **끝까지 0**이었다.

**정적 멤버십에서는 인스턴스를 내려도 소유자가 `-`가 되지 않는다.**
죽은 멤버가 `session.timeout.ms`까지 소유권을 그대로 들고 있다 — 그게 정적 멤버십의
정의다. `--describe` 출력만 보면 9개 파티션 전부 주인이 있고 멀쩡해 보인다.

> **"소유자가 있다"는 "소비되고 있다"를 뜻하지 않는다.**

1회차는 파티션별 lag 원본을 직접 열어서 결론을 냈다. 그 뒤 지표를
**`current_offset`이 직전 표본 대비 안 움직인 파티션 수**로 바꿨고, 2회차에서
정확히 **6개**가 t=219~245 구간에 잡혔다(재할당 직후 0으로 돌아간다).

운영에서도 같은 함정이 있다. 스케일 다운 직후 `kafka-consumer-groups --describe`를
보고 "파티션 주인이 다 있으니 정상"이라고 판단하면 **틀린다.** lag이나 offset 진행을
봐야 한다.

## 이 문서의 한계

- **3회 채웠다.** 유실 0은 3/3, 정지 파티션 6개는 계측을 고친 2·3회차에서 확인했다
  (1회차는 지표가 잘못돼 원본 lag을 직접 읽어 판단했다).
- 재할당 시각은 표본 간격(약 9초)만큼의 해상도밖에 없다. 정확히 언제인지 재려면
  더 촘촘히 찍어야 한다.
- 드레인 시간(182 / 81 / 93초)은 **정지 시점에 남아 있던 백로그 크기에 비례**한다
  (총 lag 3.07M / 1.72M / 2.0M). 실험 조건의 성질이 아니므로 인용하지 마라.
- 프로듀서를 **Kafka에 직접** 넣었다. MQTT 수집 경로를 거치는 실제 부하와는 다르다.
- 파티션 9, 인스턴스 3은 실험용이다. 운영 기본값은 파티션 3, 인스턴스 1이고
  **그 구성에서는 스케일 다운 자체가 없다.**
- 정지 구간에 쌓인 양은 **발행 속도에 비례**한다. 여기 수치는 이 부하에서의 값이다.
