# 정적 멤버십 대조군 — 끄면 45초가 9초가 된다 (2026-09-09)

| 항목 | 값 |
| --- | --- |
| **검증 상태** | **부분 검증** — 켠 쪽 3회, **끈 쪽 1회**. 그리고 **끄는 것의 대가는 안 쟀다**(아래) |
| 적용 범위 | dev(평문) 프로파일, 파티션 9, 인스턴스 3(수집 1 + 저장 2), 프로듀서 2프로세스 |
| 코드 상태 | 작업 트리(`KafkaConfig.staticMembershipOffWhenBlank` 신규) |
| 실행 명령 | `STATIC_MEMBERSHIP=off WARMUP_SEC=60 OBSERVE_SEC=150 bash load-test/storage-scale/run_scaledown_under_load.sh 9 2` |
| 원본 증거 | `evidence/20260909-001140` (COMPLETE). 켠 쪽은 `-220507`, `-221713`, `-235532` |

정적 멤버십(`group.instance.id`)은 12시간 soak test에서 겪은 **리밸런싱 폭풍**을 피하려고
켰다. 근거는 있었지만 **끈 상태와 비교한 적이 없었다.** 그리고 켠 대가(스케일 다운 45초)를
2026-09-07~08에 쟀는데, 그게 정말 정적 멤버십 때문인지도 확인한 적이 없다.

## 결과 — 대가는 정확히 정적 멤버십 때문이었다

| | 정적 멤버십 **ON** (3회) | 정적 멤버십 **OFF** (1회) |
| --- | ---: | ---: |
| `down` 반환 | 8 / 11 / 11초 | 9초 |
| **멤버 9 → 3** | 다운 후 **46 / 52 / 54초** | 다운 후 **9초** |
| **동시 정지 파티션** | **6개** (약 26초간 관측) | **0개** |
| 유실 | **0** (3/3) | **0** |
| 발행 정지 후 드레인 | 182 / 81 / 93초 | 60초 |

**끄면 정지 구간이 사라진다.** 멤버가 3으로 돌아온 t=199s는 `down`이 반환한 t=199s와 같다 —
즉 **컨테이너가 멈추는 즉시 재할당된다.** 켠 상태에서 6개 파티션이 26초 넘게 아무도
소비하지 않던 것이 여기서는 **한 표본도 안 잡힌다.**

메커니즘은 예상대로다. 정적 멤버가 아닌 컨슈머는 종료할 때 **LeaveGroup을 보낸다.**
정적 멤버는 안 보내고 `session.timeout.ms`(45,000ms)를 기다린다 — 그게 재시작을
리밸런싱 없이 넘기려는 기능의 요점이다.

### 정적 멤버십이 실제로 꺼진 것을 세 가지로 확인했다

1. `CONSUMER-ID`가 `consumer-telemetry-storage-group-1-<uuid>` 형식이다.
   켠 상태에서는 `telemetry-backend-consumer-0-<uuid>`처럼 `group.instance.id`가 앞에 붙는다.
2. `kafka-consumer-groups --describe --members` 출력에 **`GROUP-INSTANCE-ID` 컬럼이 없다.**
3. backend 로그에 `KafkaConfig`가 남긴 경고가 찍혔다 —
   `group.instance.id가 비어 있어 정적 멤버십을 끕니다`.

## 끄는 방법을 만들면서 배운 것

**Kafka는 `group.instance.id`에 빈 문자열을 허용하지 않는다**(`NonEmptyString` 검증).
그래서 설정만으로는 끌 수가 없었고, 끄려면 `application.yml`에서 줄을 지우고 다시
빌드해야 했다. 대조군을 만들 수 없던 이유가 그거다.

`KafkaConfig.staticMembershipOffWhenBlank`(`DefaultKafkaConsumerFactoryCustomizer`)에서
**빈 값이면 속성을 제거**하도록 했다. 이제 `GROUP_INSTANCE_ID_BASE=`로 끌 수 있다.
compose에서는 `${GROUP_INSTANCE_ID_BASE-기본값}`으로 받는다 — **`:-`가 아니라 `-`**여야
빈 값이 기본값으로 되돌아가지 않는다.

회귀는 `KafkaConsumerContractTest` 2건이 막는다(빈 값 → 속성 없음, 값 있음 → 유지).
커스터마이저 조건을 `if (false)`로 무력화했을 때 실패하는 것을 확인했다.

## ⚠ 이 대조군이 보여주지 않는 것 — 끄는 것의 대가

**이 실험은 끄는 것의 이득만 봤다.** 정적 멤버십을 켠 이유는 스케일 다운을 느리게
하려는 게 아니라 **리밸런싱 폭풍을 피하려는 것**이었다. 그 폭풍은
`max.poll.interval.ms`(5분)를 넘기는 GC 정지나 순단에서 시작하고,
`concurrency=3`인 컨슈머 여럿이 동시에 그 경로를 타면
"MemberIdRequiredException → group is already rebalancing"에 갇힌다(12시간 soak test).

**그 상황은 이번에 재현하지 않았다.** 따라서 이 문서는 **"끄는 게 낫다"는 근거가 아니다.**
읽어야 할 결론은 하나다 — **스케일 다운의 45초는 정적 멤버십의 대가가 맞다.**
그 대가를 감수할지는 리밸런싱 폭풍의 위험과 견줘야 하고, **그 반대편은 아직 안 쟀다.**

## 이 문서의 한계

- **끈 쪽은 1회**다. 켠 쪽은 3회.
- **끄는 것의 대가(리밸런싱 폭풍) 미측정.** 위 경고 참고. 재현하려면
  `max.poll.interval.ms`를 넘기는 정지를 주입해야 하고 회당 5분 이상 걸린다.
- 부하는 Kafka에 직접 발행했다. MQTT 수집 경로를 거치는 실제 부하와는 다르다.
- 재할당 시각의 해상도는 표본 간격(약 9초)뿐이다. "9초"는 그 안에서의 관측이고
  실제로는 더 빠를 수 있다.
- 정적 멤버십을 끈 상태에서 **인스턴스를 늘릴 때**의 동작은 안 봤다(내릴 때만 봤다).
