## 1. 무엇이 막고 있었나 — 두 개의 고정된 식별자

백엔드는 **MQTT 수집**과 **Kafka→InfluxDB 저장**을 겸한다. 저장 처리량을 늘리려고
통째로 복제하면 두 군데가 동시에 부딪힌다.

| | 고정값 | 복제하면 |
| --- | --- | --- |
| MQTT `client-id` | `telemetry-backend` (`cleanSession=false`) | 같은 id로 두 번 붙어 **브로커가 앞 세션을 끊는다.** 두 인스턴스가 서로를 끊는다 |
| Kafka `group.instance.id` | `telemetry-backend-consumer` | 정적 멤버 id가 겹쳐 **뒤에 온 인스턴스가 앞의 멤버를 밀어낸다**(fencing) |

그래서 naive에서는 인스턴스가 3개인데 **멤버는 3 그대로**다 — 파티션을 나눠 갖는 게
아니라 **뺏는다.** 처리 용량은 하나도 안 는다.

스케일 인 직후 시계열에 `members=2`가 한 번 찍힌다(`scaled-in/2`). 밀려난 멤버가
빠지고 원본이 아직 재가입하기 전 구간이고, 다음 표본에서 3으로 복구된다.

## 2. 역할을 나누니 9개가 됐다

`mqtt.ingest.enabled=false`로 수집을 끄고 `group.instance.id`만 인스턴스별로 갈랐다.

```
baseline    members=3   (인스턴스 1)
scaled-out  members=9   (인스턴스 3 × concurrency 3)  ← 8개 표본 내내 Stable
```

**다만 파티션이 3개라 9개 멤버 중 3개만 일하고 6개는 유휴다.** 멤버 수가 늘었다는 것은
"확장 가능한 구조가 됐다"는 뜻이지 "3배 빨라졌다"가 아니다. 실제로 lag은 두 모드 모두
100대 초반으로 비슷했다 — **이 부하(약 250 msg/s)에서는 1 인스턴스로 충분해서
용량 차이가 드러나지 않는다.** 처리량 이득을 보려면 파티션을 늘리고 유입을 올려야 한다.

## 3. naive의 정량 수치는 신뢰할 수 없다

naive에서 토픽(133,220)이 PUBACK(132,051)보다 1,169건 많고, 행(133,158)이 PUBACK보다
많다. **발행한 것보다 고유 키가 많을 수는 없다.**

브로커 카운터를 보면 이유가 보인다 — `telemetry_mqtt_broker_messages_received`가
**155,801**로 PUBACK보다 23,750 많다. 연결 경합으로 세션이 계속 끊기면서 QoS 1
메시지가 **재전송**됐고, 그 결과 "브로커가 받은 수 > 시뮬레이터가 확인받은 수"가 됐다.

이 상태에서는 **중복과 유실을 분리할 수 없다.** 총량만으로는 "재전송돼 중복 저장된 것"과
"못 가서 사라진 것"이 상쇄돼 보인다. 가르려면 메시지 단위 식별이 필요하다
(`load-test/e2e-trace/`가 그 도구다 — 이번에 붙이지 않았다).

**판정 기준을 PUBACK에 건 것이 이 실험의 설계 결함이다.** split에서는 수집 인스턴스가
하나뿐이라 경합이 없어 세 수치가 정확히 일치했고, 그래서 판정이 의미를 갖는다.

## 4. 측정 도구가 조용히 비었다

첫 실행은 결과를 못 냈다. 실행 중인 backend의 환경변수를 `docker inspect --format
'{{range .Config.Env}}{{println .}}'`로 복사했는데 **`{{end}}`가 빠져** 템플릿 파싱
에러가 났고, docker는 그걸 stderr로만 알리고 **빈 문자열**을 돌려줬다. 그래서 `-e`
인자가 하나도 안 붙은 채 컨테이너가 떴고 이미지 기본값으로 `localhost:5432`에 붙으려다
죽었다.

복사한 인자가 20개 미만이면 즉시 멈추도록 검사를 넣었다. 정상 복사는 50개
(split은 52개)다.

## 이 문서의 한계

- **모드별 1회 실행이다.**
- **처리량 이득을 측정하지 못했다.** 이 부하에서는 1 인스턴스로 충분해 lag 차이가
  없었고, 파티션 3개라 인스턴스 3개 이상은 어차피 유휴다. "확장 가능해졌다"까지가
  이번 결론이고 "얼마나 빨라지나"는 미측정이다.
- naive의 중복·유실 수치는 위 3절 이유로 **무효**다. 실패 양상(fencing 45, 연결 끊김 44,
  멤버 미증가)만 유효하다.
- **호스트 포트 8080은 여전히 원본 인스턴스만 연다.** 추가 인스턴스의 actuator·REST는
  네트워크 안에서만 접근 가능하고, 이번 측정은 Kafka·InfluxDB 쪽 지표만 썼다.
- split 구성은 **compose에 반영하지 않았다.** 실험 스크립트가 `docker run`으로 띄운다.
  운영 구성으로 만들려면 `container_name`·포트 고정을 걷어내고 역할별 서비스를 나눠야
  하는데, 그건 기존 스크립트 수십 개가 `telemetry-backend` 이름과 `localhost:8080`에
  의존하고 있어 별도 작업이다.
- 리밸런싱 로그는 naive 6건, split 18건이다. split이 더 많은 것은 인스턴스가 실제로
  들어오고 나가면서 정상적으로 파티션을 재배치했기 때문으로 보이지만 **확인하지 않았다.**
