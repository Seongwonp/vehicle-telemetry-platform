# `session.timeout.ms`를 줄이면 무엇을 잃는가 — 같은 20초가 리밸런싱 2회가 된다 (2026-09-09)

| 항목 | 값 |
| --- | --- |
| **검증 상태** | **부분 검증(각 조건 1회)** |
| 적용 범위 | dev(평문) 프로파일, 파티션 9, 인스턴스 2(수집 1 + 저장 1), **부하 없음** |
| 코드 상태 | `a6a454d` + 작업 트리(이 스크립트 신규) |
| 실행 명령 | `bash load-test/storage-scale/run_session_timeout_cost.sh 20` |
| 원본 증거 | `evidence/20260909-003710` (COMPLETE) |
| 성공 기준 | 같은 길이의 정지가 `session.timeout.ms`에 따라 리밸런싱이 되는지 |

2026-09-08에 `session.timeout.ms`를 45,000ms로 **명시**하면서 이렇게 적었다 —
"줄이면 스케일 다운이 빨라지지만 GC 정지·순단을 죽음으로 오판해 리밸런싱이 는다.
**줄였을 때의 대가는 아직 안 쟀다.**" 그 대가를 잰다(ADR-023의 남은 과제).

## 방법 — `docker pause`로 긴 GC 정지를 흉내낸다

컨테이너를 `docker pause`(SIGSTOP)로 얼리면 하트비트가 멈춘다. **긴 GC 정지와 같은
모양**이다. 얼린 시간이 `session.timeout.ms`보다 길면 브로커가 그 멤버를 죽은 것으로 본다.

리밸런싱 횟수는 컨슈머 로그의 `Generation{generationId=N}`에서 **세대 번호 증가량**으로
센다. 로그 줄 수보다 정확하다 — 재시도나 부분 실패로 같은 세대가 여러 줄 찍힐 수 있다.

**부하는 걸지 않았다.** 리밸런싱 발생 여부는 부하와 무관하고, 부하를 걸면 회차 간 비교가
흔들린다(2026-09-07에 그걸로 하루를 잃었다).

## 결과 — 같은 20초가 한쪽에서는 아무 일도 아니다

| 조건 | 정지 중 멤버 | 세대 변화 | **리밸런싱** |
| --- | ---: | --- | ---: |
| **A** `session.timeout.ms=45000` (현재 값) | **6** (그대로) | 1 → 1 | **0회** |
| **B** `session.timeout.ms=10000` (줄인 값) | **3** (절반이 쫓겨남) | 1 → 3 | **2회** |

**같은 20초 정지다.** A에서는 브로커가 아직 살아있다고 보고 아무 일도 일어나지 않는다.
B에서는 10초를 넘긴 시점에 그 인스턴스의 멤버 3개(= concurrency 3)가 그룹에서 제거되고,
재개하면 다시 가입한다 — **나갈 때 한 번, 돌아올 때 한 번, 합쳐서 2회**다.

정지 중 멤버가 6 → 3으로 떨어지는 것도 B에서만 관측된다. 그동안 그 파티션들은
남은 인스턴스로 재할당돼 처리는 계속되지만, **리밸런싱 자체가 비용**이다 —
그 사이 전체 그룹이 멈췄다 다시 배치된다.

### 두 조건이 실제로 다른 값으로 돌았는지 확인했다

스크립트가 매 조건마다 backend 로그에서 실제 컨슈머 설정을 읽어 대조한다.
값이 안 맞으면 즉시 중단한다 — **설정이 안 먹은 채로 "차이 없음"이 나오는 것**이
이 실험에서 가장 위험한 실패 모드다.

```
조건 A: 실제 컨슈머 설정: session.timeout.ms = 45000
조건 B: 실제 컨슈머 설정: session.timeout.ms = 10000
```

## 그래서 45,000ms를 유지한다

이제 양쪽이 다 숫자로 있다.

| | 45,000ms (현재) | 10,000ms |
| --- | --- | --- |
| 스케일 다운 재할당 | **46~54초** (2026-09-08, 3회) | 더 빠를 것(미측정) |
| 20초 순단에서 리밸런싱 | **0회** | **2회** |

**줄이면 스케일 다운이 빨라지는 대신, 20초짜리 순단마다 리밸런싱이 두 번 돈다.**
이 프로젝트는 12시간 soak test에서 리밸런싱이 연쇄되어 복구가 안 되는 상태를 겪었다.
스케일 다운은 **계획된 작업**이라 트래픽이 낮은 시간에 하면 되지만, GC 정지와 순단은
**고를 수 없다.** 고를 수 없는 쪽을 안전하게 두는 게 맞다.

## 이 문서의 한계

- **각 조건 1회**다. 다만 판정이 타임아웃 초과 여부로 갈리는 결정적 동작이라
  회차 변동 요소가 적다(20초 vs 10초/45초는 경계에서 멀다).
- **10,000ms에서 스케일 다운이 얼마나 빨라지는지는 안 쟀다.** 이득 쪽은 추정이다.
- 정지 길이를 **20초 하나만** 봤다. 45초 근처(경계)에서 어떻게 되는지는 안 봤다.
- `docker pause`는 프로세스 전체를 얼린다. 실제 GC 정지는 일부 스레드만 멈추거나
  JVM이 하트비트를 늦게라도 보낼 수 있어 **완전히 같지는 않다.**
- 부하가 없는 상태다. 부하 중에는 `max.poll.interval.ms` 쪽이 먼저 걸릴 수 있는데
  그 경로는 안 봤다.
- 리밸런싱 2회의 **비용(정지 시간·재처리량)은 세지 않았다.** 횟수만 셌다.
