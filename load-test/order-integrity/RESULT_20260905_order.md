## 왜 쟀나 — 가설은 이미 코드에 적혀 있었다

`TelemetryProducer.retryPending()` 주석:

> 브로커 복구 직후 아주 짧은 구간에서는 새 메시지가 spool 드레인보다 먼저 Kafka에
> 닿아 같은 차량 메시지의 순서가 뒤집힐 수 있다(backlog 플래그가 best-effort라서).
> **각 메시지가 자체 timestamp를 갖고 있어 저장/조회는 영향받지 않는다.**

앞 문장(가설)은 맞았고, 뒤 문장(영향 없음)은 **저장·조회에 대해서만** 맞았다.

## 순서를 어떻게 정의했나

Kafka의 순서는 파티션 안에서만 보장된다. 파티션 키가 `vehicle_id`라 한 차량은 한
파티션에 몰리므로, 차량별 순서 = 그 차량 레코드들의 offset 순서다.
각 차량의 레코드를 `(partition, offset)`으로 정렬한 뒤 타임스탬프 단조성을 본다.

한 번 뒤집힌 뒤 이어지는 정상 메시지까지 세면 한 건의 사고가 수백 건으로 부풀려지므로,
비교 기준은 **그 차량에서 지금까지 본 최대 타임스탬프**다.

### 정상 경로에서 0인 것은 우연이 아니다

프로듀서 설정을 증거로 남겼다(`evidence/*/producer-config.txt`):

```
acks = -1 (all)
enable.idempotence = true
max.in.flight.requests.per.connection = 5
retries = 3
```

`enable.idempotence=true` + `max.in.flight ≤ 5`면 Kafka가 **재시도 중에도 파티션 내
순서를 보장**한다. 설정하지 않았는데 기본값으로 켜져 있었다(Kafka 3.0+).
이 조합이 깨지면 정상 경로에서도 역전이 생긴다 — 그래서 값을 증거에 남긴다.

> 이 값을 읽을 때 주의: 전체 로그에서 `retries =`를 grep하면 AdminClientConfig의
> 기본값(2147483647)이 같이 잡혀 "yml의 `retries: 3`이 안 먹었다"고 오독하게 된다.
> 실제로 한 번 그렇게 읽었고, 그래서 도구가 `ProducerConfig values` 블록 안에서만 찾는다.

### 드레인 경로의 역전은 "잠깐 뒤섞임"이 아니다

| 되돌아간 크기 | 건수 |
| --- | ---: |
| 1초 이하 | 0 |
| 10초 이하 | 0 |
| 1분 이하 | **0** |
| 5분 이하 | **924** |
| 5분 초과 | 0 |

**1분 미만이 하나도 없다.** 전부 1~2분 과거의 메시지가 뒤늦게 도착한 것이다.

차량당 역전 수는 **최소 4 / 중앙 5 / 최대 6**으로 균일하고, 발생 offset은
47,385~54,359의 좁은 구간에 몰려 있다(전체 243,323 중 약 7,000).

읽으면: **복구 직후 차량마다 약 5건씩, 최대 114초 묵은 메시지가 최신 메시지 뒤에
도착한다.** 차량당 5건은 5 msg/s에서 약 1초치 트래픽이고, 이는 `backlog` 플래그가
best-effort라 스케줄러가 플래그를 내리는 순간과 MQTT 스레드가 spool에 쓰는 순간 사이의
틈으로 설명된다.

## 사용자 영향 — 경로마다 다르다

| 경로 | 영향 | 근거 |
| --- | --- | --- |
| InfluxDB 저장 | **없음** | 포인트 identity가 타임스탬프라 늦게 와도 제자리에 쓰인다 |
| REST `/latest` | **없음** | Flux가 `sort(_time, desc) \|> limit(1)` — 도착 순서와 무관 |
| REST 기간 조회 | **없음** | 시간 범위 질의라 동일 |
| **앱 WebSocket 실시간** | **있음** | 아래 |
| anomaly-detector 룰 | 없음 | 메시지 단위 무상태 판정 |
| anomaly-detector ML | **미확인** | 슬라이딩 윈도우가 대략 시간순을 가정한다. 114초 묵은 샘플이 섞이는 영향은 재지 않았다 |

### 앱: 묵은 값이 "방금 갱신됨"으로 표시된다

`dashboard_screen.dart`의 WebSocket 콜백은 도착한 프레임을 **무조건** 최신값으로 쓴다.

```dart
setState(() {
  _latest = telemetry;
  _history = [telemetry!, ..._history].take(_historyLimit).toList();
  _lastUpdated = widget.now();   // ← 도착 시각으로 갱신
});
```

그래서 복구 구간에 **최대 114초 묵은 값이 현재 값으로 표시되고**, `_lastUpdated`가
도착 시각으로 갱신돼 "오래된 데이터" 표시로도 걸러지지 않는다. 속도 추이 차트에도
과거 값이 맨 앞에 끼어든다.

## 결정 — 클라이언트에서 단조성을 지킨다

역전 자체는 **허용한다.** 없애려면 spool 드레인과 신규 발행을 한 락으로 묶어야 하는데,
그건 예전에 수집 스레드를 멈춰 세워 처리량을 무너뜨린 구조로 되돌아가는 것이다
(`retryPending()` 주석 참고). 유실이 없고 저장·조회가 정확한 이상, 파이프라인에서
전역 순서를 보장할 이유가 없다.

대신 **표시 계층에서 막는다** — 앱이 이미 가진 값보다 오래된 프레임을 버린다.
순서가 중요한 곳은 "지금 값"을 보여주는 화면 하나뿐이고, 거기서 판단하는 것이
가장 싸고 정확하다. 조치는 앱 저장소에서 한다.

## 남은 것

- **각 모드 1회 실행이다.** 역전 924건은 이 실행의 값이고, 반복하면 달라진다
  (차량당 4~6이라는 폭은 한 실행 안의 분포다).
- **ML 슬라이딩 윈도우 영향 미측정.** 114초 묵은 샘플이 학습 버퍼에 섞일 때의
  탐지 품질 변화는 재지 않았다.
- **장애 시간을 바꿔가며 재지 않았다.** 90초에서 차량당 약 5건인데, 이 값이
  장애 길이에 비례하는지 상수인지 모른다(플래그 틈이라면 상수일 것으로 예상되지만
  확인하지 않았다).
- **spool 파일명 정렬이 실제로 시간순인지 확인하지 않았다.** 드레인이 FIFO라는 전제는
  코드 주석에서 온 것이고 실측하지 않았다.
