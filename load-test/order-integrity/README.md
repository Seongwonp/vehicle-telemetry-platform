# 차량별 순서 보장 범위 측정

```bash
# 정상 경로 기준선
bash load-test/order-integrity/run_scenario.sh normal

# Kafka 장애 → spool 드레인 경로
bash load-test/order-integrity/run_scenario.sh kafka 90
```

## 무엇을 재나

`vehicle-telemetry` 토픽을 처음부터 읽어 **차량마다** 타임스탬프가 단조 증가하는지 본다.
역전 = 그 차량에서 지금까지 본 최대 타임스탬프보다 이른 메시지.

Kafka의 순서는 파티션 안에서만 보장된다. 파티션 키가 `vehicle_id`라 한 차량은 한
파티션에 몰리므로, 차량별 순서 = 그 차량 레코드들의 offset 순서다.
**차량이 여러 파티션에 걸치면 그 자체가 발견이다** — 키 파티셔닝이 깨진 것이고
순서 보장의 전제가 무너진다. 그래서 따로 센다.

## 성공 기준을 "역전 0"으로 정하지 않는다

이 실험의 목적은 통과/실패가 아니라 **범위를 아는 것**이다. 미리 0을 기준으로 잡으면
역전이 나왔을 때 "실패"로 처리하고 원인·크기·영향을 안 보게 된다.
스크립트의 판정은 **키 파티셔닝이 깨졌는지만** 실패로 본다.

## 결과 (2026-09-05)

`RESULT_20260905_order.md`. 요약:

| | 정상 | Kafka 90초 장애 후 드레인 |
| --- | ---: | ---: |
| 역전 | **0** | **924 (0.38%)** |
| 최대 되돌아간 시간 | — | **113,722 ms** |
| 차량당 역전 | 0 | 4~6 (중앙 5) |

정상 경로가 0인 것은 우연이 아니다 — `enable.idempotence=true` +
`max.in.flight ≤ 5`가 재시도 중에도 파티션 내 순서를 보장한다. 그래서 스크립트가
`ProducerConfig` 블록을 증거로 남긴다.

드레인 경로의 역전은 **1분 미만이 하나도 없다** — 잠깐 뒤섞인 게 아니라 1~2분 묵은
메시지가 뒤늦게 도착하는 것이다. 저장·조회는 영향이 없고(타임스탬프 기준),
**앱의 실시간 표시만 영향을 받는다.**

## 주의

  AdminClientConfig의 기본값(2147483647)이 같이 잡혀 오독한다.
  도구는 `ProducerConfig values` 블록 안에서만 찾는다.
