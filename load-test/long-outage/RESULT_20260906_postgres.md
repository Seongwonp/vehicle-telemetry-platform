## 1. 같은 180초 설정이 여기서는 8분이 됐다 — 로그로 분해된다

백엔드 로그에 배치마다 재시도가 찍혀 있어(알림 경로는 실패를 로그로 남긴다) 시각 간격을
그대로 뺄 수 있었다. 레코드 10건짜리 배치 하나의 재시도 시각이다.

```
00:37:59  00:38:30  00:39:02  00:39:36  00:40:14  00:41:00  00:42:00 …
   +31       +32       +34       +38       +46       +60       +60
```

간격에서 **30초를 빼면 정확히 백오프 값**이 나온다: 1, 2, 4, 8, 16, 30, 30, …
즉 시도마다 HikariCP `connectionTimeout` 30초를 실패에 쓰고, 그 시간은 예산에 안 세어진다.

- 백오프 합이 180초에 도달하는 것은 11번째 시도(1+2+4+8+16+30×5 = 181)
- 그때까지의 **벽시계**는 백오프 181초 + 실패 11회 × 30초 ≈ **8분**
- 실측 첫 DLQ **t=485초(8.1분)**

InfluxDB는 실패가 즉시 끝나므로 벽시계 ≈ 백오프 합이었다(t=220초). **같은 설정이
의존성에 따라 3.7분과 8.1분이 된다**는 것이 이제 추정이 아니라 측정이다.

## 2. 12분 장애에서 DLQ는 21건뿐이다

한 배치 주기가 약 8분이라, 12분 장애에서 예산을 소진한 배치는 **사실상 한 번뿐**이다.
`dlq_offset`은 t=485초에 21이 되고 장애가 끝날 때까지 그대로다.

InfluxDB 쪽은 주기가 3.7분이라 4번 돌아 6,158건이 갔다. **블로킹하는 의존성이 오히려
DLQ를 덜 만든다** — 느린 실패가 재시도 예산을 천천히 태우기 때문이다.
(2026-09-05에 `connectionTimeout`을 줄이지 않기로 한 판단이 이 실험으로 다시 확인됐다.)

## 3. DLQ 21건은 전부 이미 저장돼 있었다

행 수가 토픽의 레코드 수와 **정확히 같다**(106,047 = 106,047, 고유 event_id도 동일).
그러면 DLQ 21건은 산술적으로 양쪽에 다 있어야 한다. 직접 확인했다.

```
DLQ event_id 수: 21
그중 PostgreSQL에 이미 저장된 것: 21
```

서버 커밋은 끝났는데 연결이 끊겨 클라이언트만 실패로 본 **in-doubt 트랜잭션**이다.
2026-09-05 60초 장애에서는 9건 중 3건이었는데, 이번에는 **21건 전부**다.

즉 **이 DLQ에는 복구가 필요한 알림이 하나도 없다.** 재처리해도 `UNIQUE(event_id)` +
`ON CONFLICT DO NOTHING`이 막아 행이 늘지 않는다(2026-09-05 확인).

같은 현상을 이번에 InfluxDB 쪽에서도 확인했다(47건). **"DLQ에 있다 = 저장 안 됐다"가
두 경로 모두에서 참이 아니다.** Runbook이 그것을 전제하면 안 된다.

## 4. 리밸런싱 0 — `max.poll.interval.ms`를 넘겨도 안 돌았다

`group_state`는 전 구간 `Stable`, `members` 3 고정이다. 재시도 주기가 약 8분이라
`max.poll.interval.ms`(300초)를 **두 배 이상 넘겼는데도** 컨슈머가 쫓겨나지 않았다.

`KafkaConfig.buildBackOff` 주석은 "리스너가 오래 붙잡히면 예산과 무관하게 리밸런싱이
돌 수 있다"고 적어뒀는데, 720초 장애에서는 **돌지 않았다.** 두 가지 중 하나다 —
정적 멤버십(`group.instance.id`)이 버텨주거나, Spring Kafka가 백오프 동안 파티션을
pause한 채 poll을 계속하거나. **이 실험은 둘을 구분하지 못한다**(정적 멤버십을 끄고
같은 조건을 돌려야 갈린다). 미측정으로 남긴다.

## 이 문서의 한계

- **1회 실행이다.**
- 리밸런싱이 안 도는 **이유를 구분하지 못했다**(정적 멤버십 대 pause-and-poll).
  이걸 가르려면 `group.instance.id`를 빼고 같은 조건을 돌려야 한다.
- 장애 길이 720초 하나만 봤다. 배치 주기가 약 8분이라 **더 긴 장애에서는 DLQ가
  주기당 한 번씩 늘어날 것으로 보이지만 확인하지 않았다.**
- DLQ 재처리를 실제로 돌리지 않았다(이번 DLQ는 전량 in-doubt라 되돌릴 것이 없다).
- 부하는 알림 약 145 msg/s다. 더 높은 부하에서는 배치 크기가 커져 DLQ 건수도 달라진다.
- `backoff_exhausted` 열은 0으로 남아 있다 — 로그 문구로 소진을 잡으려던 grep이 헛돌았다.
  판단은 DLQ offset과 메트릭으로 했다. 지우지 않고 남긴다.
