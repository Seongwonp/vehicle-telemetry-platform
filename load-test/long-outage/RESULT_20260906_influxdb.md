## 결과 요약

| | 값 |
| --- | ---: |
| 원본 토픽 `vehicle-telemetry` | 258,726 |
| InfluxDB 행 | 252,615 |
| DLQ `vehicle-telemetry-dlq` 증가 | 6,158 |
| **리밸런싱** | **0** |
| 첫 DLQ 발생 | **t=220초** (예산 180초) |
| 복구 후 lag 0 도달 | 부하 정지 t=943초 → t=953초 |

판정 기준은 실행 전에 정했다: **원본 토픽 == 저장 + DLQ 증가분(유실 0) AND 리밸런싱 0.**
결과는 PASS다. 다만 합이 정확히 같지 않고 **47건 초과**한다 — 아래 in-doubt 항목.

## 1. 예산 180초는 벽시계로 220초였다

```
t=183s  lag  47,300   DLQ     0     ← 예산(180초)을 넘겼는데 아직 0
t=220s  lag  56,506   DLQ    73     ← 첫 배치가 DLQ로
t=405s  lag 102,541   DLQ    99
t=442s  lag 111,725   DLQ   158
t=628s  lag 152,075   DLQ 6,158     ← 3 컨슈머 × max.poll.records 2,000
```

예산은 "백오프로 쉰 시간의 합"이라 벽시계보다 뒤에 찬다. InfluxDB는 컨테이너가 없으면
빨리 실패하므로 그 차이가 작을 것으로 봤고, 실제로 **180초 대 220초**였다.
차이 40초는 재시도마다 드는 실패 시간(이름 해석·연결 거부)과 배치 재처리 비용이다.

## 2. 백로그는 DLQ로 가지 않는다

DLQ 6,158건의 타임스탬프는 **전부 00:13:22~00:13:48**, 즉 **장애 시작 직후 26초 구간**뿐이다.
장애 한복판(00:14~00:25)에 발행된 레코드는 DLQ에 하나도 없다.

컨슈머는 실패한 배치를 붙잡고 재시도하느라 진도를 못 나가고, 그동안 들어온 17만 건은
**lag으로 쌓였다가 복구 후 정상 저장됐다.** 장애가 길어져도 DLQ는 "장애 시작 시점에
처리 중이던 것"만큼만 커진다. 12분 장애에서 DLQ는 전체의 **2.4%**다.

## 3. 리밸런싱은 12분 내내 0이었다

`group_state`는 전 구간 `Stable`, `members`는 3으로 고정이다.

배치 하나당 재시도 주기가 약 180~220초로 `max.poll.interval.ms`(300초)보다 짧아서
poll 간격을 넘기지 않는다. 즉 **이 조합에서는 "예산 < poll 간격"이 실제로 성립한다.**
`KafkaConfig.buildBackOff` 주석은 "예산이 벽시계가 아니라서 그 관계가 그대로 성립하지
않는다"고 적어뒀는데, **즉시 실패하는 의존성에서는 성립한다**가 이번 관찰이다.
(블로킹하는 의존성은 `RESULT_20260906_postgres.md` 참고.)

## 4. 복구는 38초, 드레인 속도 약 4,500 msg/s

```
t=740s  복구(컨테이너 재기동)
t=748s  lag 171,823
t=786s  lag     215     ← 38초 만에 17만 건 소화
```

배치 쓰기로 바꾼 뒤(ADR-022)의 드레인 속도다. 유입(약 250 msg/s)의 18배라 밀린 것을
빠르게 흡수한다.

## 5. 발견 — 47건은 InfluxDB에도 있고 DLQ에도 있다 (in-doubt 쓰기)

`저장 252,615 + DLQ 6,158 = 258,773`으로 토픽(258,726)보다 **47건 많다.** 산술로는
"47건이 양쪽에 다 있다"는 뜻이지만 그건 뺄셈이 말해주는 것이라, 직접 확인했다.

가장 이른 DLQ 20건을 그 키(`vehicle_id` + 타임스탬프)로 InfluxDB에 조회한 결과
**9건이 실제로 있었다.**

```
있음  SIM-038 00:13:22.170Z   SIM-012 .172Z   SIM-022 .173Z   SIM-050 .174Z
      SIM-044 .181Z   SIM-030 .182Z   SIM-046 .185Z   SIM-005 .270Z   SIM-003 .272Z
없음  전부 .365~.471 구간
```

`docker stop`으로 InfluxDB를 세울 때 **서버는 쓰기를 적용했는데 클라이언트는 연결이
끊겨 실패로 본** 건들이다. 2026-09-05에 PostgreSQL에서 찾은 in-doubt 트랜잭션과 같은
종류이고, 있는 것과 없는 것이 `.17x/.27x` 대 `.36x/.47x`로 갈리는 것은 파티션마다
배치가 따로 나가기 때문이다.

**실무 영향은 없다.** InfluxDB는 같은 키를 덮어쓰므로 재처리해도 행이 늘지 않는다
(2026-09-04 `storage-integrity`에서 확인). 다만 "DLQ에 있다 = 저장 안 됐다"가
**참이 아니라는 것**은 Runbook이 전제하면 안 되는 사실이다.

## 6. 발견 — DLQ로 6,158건이 갔는데 로그에는 한 줄도 안 남는다

장애 12분 동안, 그리고 DLQ 발행이 일어나는 동안 백엔드 로그에는 **관련된 줄이 하나도
없다.**

- `TelemetryRepository.saveAll`은 실패를 카운터로만 세고 예외를 다시 던진다(로그 없음)
- Spring Kafka의 재시도·복구 로그는 DEBUG인데 `logging.level.org.springframework.kafka: WARN`

그래서 이 실험의 시계열에서 `backoff_exhausted` 열은 **끝까지 0**인데 DLQ는 6,158이다.
(이 열을 채우려던 grep 문구가 헛돈 것이기도 하다. 지우지 않고 남긴다 — 로그로 재시도
소진을 잡으려는 다음 사람이 같은 것을 시도하기 때문이다.)

운영자에게 "DLQ를 조사하라"고 적어둔 Runbook이 있는데, **DLQ가 생겼다는 사실 자체가
로그에 없다.** 신호는 메트릭(`telemetry_kafka_dlq_published_total`,
`telemetry_influx_write_failures_total`)과 토픽뿐이다. 알림은 있으므로 방어선은
있지만, 사고 후 로그를 되짚는 경로가 비어 있다.

**이건 Spring의 문제가 아니라 두 경로의 비대칭이었다.** 짝 실험(PostgreSQL)의 로그에는
`[Kafka→Anomaly] 배치 저장 실패 10건 — offset 미커밋, 재시도한다`가 재시도마다 찍혀 있다.
알림 경로는 남기고 저장 경로는 안 남긴다. 실제로 그 로그 덕분에 PostgreSQL 쪽은
재시도 간격을 초 단위로 분해할 수 있었고, 이쪽은 아무것도 못 했다.

**고쳤다(같은 날):**

- `KafkaConfig`의 recoverer 람다에 `[DLQ 이동] 재시도 예산 소진 — topic-partition@offset
  → dlq (원인)` WARN. 원인 예외는 `ListenerExecutionFailedException`으로 한 겹 싸여 있어
  그대로 찍으면 "Listener failed"만 남으므로 근본 원인 메시지를 푼다.
  회귀 테스트 `KafkaDlqLoggingTest`.
- `TelemetryConsumer.consumeForStorage`에 배치 저장 실패 ERROR — 알림 경로와 같은 문구로
  맞췄다.

## 이 문서의 한계

- **1회 실행이다.** 반복하지 않았다.
- 부하는 약 250 msg/s로, 지금까지의 다른 실험(1,000~2,500 msg/s)보다 낮다.
  더 높은 부하에서는 배치 크기와 DLQ 규모가 달라질 수 있다.
- **DLQ 재처리를 실제로 돌리지 못했다.** 도구 실행이 이 세션에서 승인되지 않았다.
  분류는 확인했다 — `transient` 6,158건(100%), 원인 전부 `InfluxException`.
- 47건이라는 초과분 자체는 **산술로 얻은 값**이다. 표본 20건 중 9건을 직접 확인해
  메커니즘은 확인했지만, 6,158건 전량을 조회해 47을 재확인하지는 않았다.
- 장애 길이 720초 하나만 봤다. 예산 소진 시점(220초)과 poll 간격(300초)의 관계가
  다른 부하·다른 배치 크기에서도 같은지는 미측정.
