## 먼저 — 정답 기준을 만드는 데가 이 측정의 절반이었다

### `publish()`의 반환값은 기준이 아니다

`client.publish(..., qos=1)`이 돌려주는 `MQTT_ERR_SUCCESS`는 **"paho의 송신 큐에
넣었다"**는 뜻이지 브로커가 받았다는 뜻이 아니다. 브로커가 죽어도 paho가 그것을
알아채기 전까지 계속 성공을 반환한다.

브로커가 받았다는 유일한 증거는 QoS 1의 PUBACK, 즉 `on_publish` 콜백이다.
시뮬레이터에 `PublishStats`를 넣어 두 단계를 따로 세게 했다.

### 처음 만든 기준은 틀렸다 — 관측치보다 작게 나왔다

첫 실행에서 정답 기준(46,142)이 **backend 수신(49,060)보다 작게** 나왔다.
기준이 관측치보다 작으면 기준 구실을 못 한다. 원인이 둘이었다.

1. **시뮬레이터를 `docker rm -f`(SIGKILL)로 죽이고 있었다.** 그래서 최종 집계가 아니라
   최대 5초 묵은 주기 로그를 읽었다. 초당 1,000건 부하에서 5초는 5,000건이다.
   → `--rm`을 빼고 `docker stop`(SIGTERM)으로 정상 종료시킨 뒤 읽는다.
2. **종료 시 미확인 메시지를 버리고 있었다.** 브로커 장애 뒤 paho 큐에 수백 건씩
   밀려 있는데 바로 `disconnect()`하면 PUBACK 전에 사라진다.
   → 종료 시 최대 `SHUTDOWN_FLUSH_SECONDS`(45초)까지 flush를 기다린다.

### 그러다 알게 된 것 — QoS 1은 `NO_CONN`이어도 유실이 아니다

처음엔 `publish()`가 `MQTT_ERR_NO_CONN`을 반환한 건을 유실로 적었다.
그런데 측정에서 `confirmed`가 `queued`보다 **크게** 나왔다(46,142 > 39,440).
paho 1.6.1 소스를 확인하니 `_messages_reconnect_reset_out()`이 QoS 1 메시지를
`clean_session`과 무관하게 DUP로 표시해 **다시 큐에 넣는다.**

즉 `publish()` 실패는 유실이 아니라 **재전송 대상**이다. 코드 주석과 README에
"재전송되지 않는다"라고 써뒀던 것을 고쳤다.

## 결과 — 129,445건이 사라지고 있었다

브로커 90초 정지, 복구 후 60초, 그리고 정상 종료(flush 포함).

| | 수정 전 | 수정 후 |
| --- | ---: | ---: |
| publish() 시도 | 179,532 | 181,993 |
| **브로커 확인(PUBACK) = 정답 기준** | **179,532** | **178,451** |
| backend 수신 | 50,087 | **178,452** |
| **유실 (기준 − 수신)** | **129,445 (72.1%)** | **−1 (= 0)** |
| InfluxDB 행 | 50,085 | 178,451 |
| 브로커 `$SYS` dropped | **129,447** | **0** |

수정 전 두 값이 독립적으로 일치한다 — 내가 계산한 유실 **129,445**와
브로커 자신이 세는 dropped **129,447**. 서로 다른 출처라 교차 검증이 된다.

수정 후 `−1`은 유실이 아니라 **중복 1건**이다(QoS 1 재전송). InfluxDB 행이
정답 기준과 정확히 같아(178,451) 그 중복이 덮어쓰기로 흡수된 것도 확인된다.

## 원인 — Paho의 재연결 백오프 상한이 기본 128초였다

`MqttConfig`가 `setAutomaticReconnect(true)`만 켜고 `setMaxReconnectDelay()`를
지정하지 않았다. Paho는 1초에서 시작해 매번 두 배로 늘리고 **기본 상한이 128초**다.

그 시간은 그냥 기다리는 시간이 아니다. `cleanSession=false`라 브로커가 우리 세션
앞으로 오는 메시지를 **대신 쌓아두다가**, `max_queued_messages`(10,000)를 넘기면
말없이 버린다.

브로커 로그가 그 순간을 그대로 남긴다:

```
1788575455: Outgoing messages are being dropped for client telemetry-backend.
1788575492: New client connected ... as telemetry-backend (p2, c0, k60).
```

**버리기 시작한 뒤에야 백엔드가 붙었다.** 그 사이 시뮬레이터들은 밀렸던 것을
한꺼번에 쏟아냈고(복구 후 브로커 수신 139,448건), 백엔드가 재연결 후 실제로 받은 건
**10,002건** — `max_queued_messages` 10,000과 정확히 일치한다.

### 고친 것

```java
options.setMaxReconnectDelay(maxReconnectDelayMs);  // 기본 5,000ms
```

`mqtt.max-reconnect-delay-ms`(`MQTT_MAX_RECONNECT_DELAY_MS`)로 조정 가능하다.
브로커가 죽어 있는 동안 재연결 시도가 잦아지지만 5초 간격은 초당 0.2회라
브로커 부하로는 무시할 수준이고, 유실 위험과 바꿀 것이 못 된다.

수정 후 재실행에서 **브로커 dropped 0**, 그리고 복구 후 브로커가 받은 137,702건이
backend 수신 증가분(178,452 − 40,750 = **137,702**)과 **정확히 일치**한다.
`Error subscribing` 로그도 0건이 됐다(수정 전에는 재구독이 5초 타임아웃에 걸렸다).

회귀 방지로 `MqttConnectOptionsTest`를 넣었다 — 이 설정은 정상 동작 중에는 아무
차이도 만들지 않아서, 잘못 바뀌어도 일반 테스트로는 안 잡힌다.

## mTLS 프로파일에서 다시 (같은 날)

위 측정은 전부 평문(dev) 프로파일이었다. **운영 프로파일은 8883/mTLS**라 TLS
핸드셰이크가 재연결 시간에 얹힌다 — 5초 상한이 그래도 충분한지 따로 봐야 했다.

`PROFILE=tls bash run_scenario.sh mosquitto 90` (100대, 차량별 인증서)

| 항목 | 값 |
| --- | ---: |
| publish() 시도 | 101,358 |
| **브로커 확인(PUBACK) = 정답 기준** | **99,121** |
| backend 수신 | 99,122 |
| InfluxDB 행 | **99,121** |
| **유실** | **0** |
| 브로커 `$SYS` dropped | **0** |

**재연결은 약 2초**였다(브로커 재기동 직후 `New client connected ... as telemetry-backend`).
TLS 핸드셰이크가 붙어도 5초 상한 안에 들어온다.

`backend 수신 − 정답 기준 = 1`은 QoS 1 재전송 1건이고, InfluxDB 행이 정답 기준과
정확히 같아 덮어쓰기로 흡수된 것까지 확인된다.

`시도 − 확인 = 2,237`(2.2%)은 종료 시 45초 flush 안에 브로커까지 못 간 발행 측
잔여분이다. 파이프라인 유실이 아니다.

### 여기서 ACL 버그를 하나 찾았다

`broker/config/acl`이 `$SYS/broker/messages/received`만 허용하고 있었다. 코드는
파이프라인 대조 대시보드를 만들면서 `$SYS/broker/publish/messages/received`로
바꿨는데(모든 패킷 vs PUBLISH만 — 정상 부하에서 알림이 계속 울리던 문제),
**ACL은 같이 안 바꿨다.** 평문 프로파일은 ACL이 없어 드러나지 않았고,
**운영 프로파일에서만 구독이 막혀** 대시보드 1단계가 비게 된다.

고친 뒤 확인: 복구 후 브로커 수신 **70,810** = backend 수신 증가분
(99,122 − 28,311 = **70,811**). 지표가 실제로 도착한다.

### 측정 도구도 두 번 고쳤다

1. **복구 판정이 걸렸다.** mTLS로 붙어 확인하려 했는데 키 파일이 `0600`이라
   컨테이너 안 mosquitto 사용자가 못 읽는다(`Problem setting TLS options: File not found`).
   두 프로파일 모두에서 되는 **TCP 연결 확인**으로 바꿨다.
2. **최종 집계 대신 묵은 주기 로그를 읽고 있었다.** `docker stop`이 돌아와도 마지막
   로그 줄이 아직 안 보일 수 있다. 그래서 정답 기준이 실제보다 ~1,000건 작게 나왔고,
   **"저장(101,638)이 발행(100,628)보다 많다"는 불가능한 결과**가 됐다.
   종료 마커를 기다린 뒤 읽도록 고쳤고, 못 찾으면 경고를 찍는다.

두 번 다 "숫자가 앞뒤가 안 맞는다"가 신호였다.

## 300초 장애 — 재연결을 고쳐도 큐가 넘쳤다

90초는 유실 0이었지만 그건 "다 고쳐졌다"는 뜻이 아니었다. 장애를 300초로 늘리자
다시 유실이 나왔다.

| | 큐 10,000 | 큐 100,000 |
| --- | ---: | ---: |
| 브로커 확인(PUBACK) = 정답 기준 | 364,994 | 364,802 |
| backend 수신 | 347,751 | 364,804 |
| **유실** | **17,243 (4.7%)** | **0** |
| 브로커 `$SYS` dropped | **17,245** | **0** |
| InfluxDB 행 | 347,749 | **364,802** (정답 기준과 일치) |

또 한 번 내 계산(17,243)과 브로커의 dropped(17,245)가 독립적으로 맞았다.

**원인이 앞의 것과 다르다.** 128초 백오프 때는 *백엔드가 없어서* 버려졌다.
이번엔 백엔드가 2초 만에 붙었는데도 버려졌다 — 밀려 있던 32만 건이 한꺼번에
쏟아지면서 **구독자가 드레인하는 속도를 잠깐 넘어섰기** 때문이다.
같은 증상(브로커가 버린다)에 원인이 둘이고, 첫 번째만 고친 상태였다.

`max_queued_messages`를 10,000 → 100,000으로 올려 유실 0이 됐다.
payload 300B 기준 약 30MB다.

**이걸로 유실이 사라지는 게 아니라 뒤로 밀릴 뿐이다.** 더 긴 장애나 더 큰 부하면
다시 넘친다. 진짜 방어선은 `MqttBrokerDroppingMessages` 알림(`$SYS` dropped)이고,
그 알림은 이미 있다 — 이번 두 실행에서 실제로 값을 냈다.

## 남은 것

- **시도 181,993 − 확인 178,451 = 3,542건**은 종료 시 45초 flush 안에 브로커까지
  못 갔다. 발행 측 한계이지 파이프라인 유실이 아니다. flush 시간을 늘리면 줄어들
  것으로 보이지만 **어디까지 줄어드는지는 재지 않았다.**
- **재연결까지 실제로 걸린 시간을 직접 재지 않았다.** 브로커 로그의 연결 시각으로
  좁혀 보면 수정 후엔 복구로부터 20초 안쪽이지만, 상한 5초와의 차이가 어디서
  오는지(브로커 기동 시간, `connectionTimeout` 10초 등) 분해하지 않았다.
- ~~mTLS 프로파일 미측정~~ — **쟀다**(위 절). 유실 0, 재연결 약 2초.
  다만 차량 수가 100대(평문 200대)라 부하가 절반이다 — 인증서를 그만큼만 만들어 뒀다.
- ~~`max_queued_messages` 10,000 적정성 미판단~~ — **쟀고 100,000으로 올렸다**(위 절).
  다만 **어디서 다시 넘치는지는 안 쟀다** — 300초는 덮지만 600초는 모른다.
  필요량은 장애 시간과 유입 속도에 따라 달라지므로, 이 값은 "현재 설계 부하에서
  300초를 덮는다"까지만 보증한다.
- **브로커 메모리를 실제로 재지 않았다.** 30MB는 payload 크기로 계산한 추정이다.

## 이 문서의 한계

- **각 조건 1회 실행이다.** 재전달률·유실량이 실행마다 얼마나 흔들리는지 모른다.
  `docs/roadmap.md` P0-2가 이 실험의 3회 반복을 요구한다.
- **원본 로그를 보존하지 않았다.** 스크립트가 `_result_mosquitto*.txt`에 남긴 출력을
  보고 이 문서를 쓴 뒤 그 파일을 지웠다. 그래서 **여기 적힌 수치를 원본에서 다시
  계산할 수 없다.** `docs/evidence-policy.md` P0-1 위반이고, 증거 보존 구조는
  별도 작업으로 만든다.
- **commit SHA는 실행 시점이 아니라 "그 결과를 낸 코드가 들어간 커밋"이다.**
  실행은 커밋 전 작업 트리에서 했다.
- 단일 머신 결과다. 구성 요소를 분리한 환경으로 옮겨 쓸 수 없다.
