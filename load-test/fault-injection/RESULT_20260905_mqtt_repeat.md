## 결과 — 불변식은 3/3, 총량은 6% 흔들린다

| 지표 | 1회 | 2회 | 3회 | 편차 |
| --- | ---: | ---: | ---: | ---: |
| publish() 시도 | 190,538 | 179,053 | 182,575 | 11,485 |
| **브로커 확인(PUBACK) = 정답 기준** | 190,538 | 178,359 | 182,575 | 12,179 |
| backend MQTT 수신 | 190,540 | 178,361 | 182,577 | 12,179 |
| **InfluxDB 행** | **190,538** | **178,359** | **182,575** | 12,179 |
| DLQ | 0 | 0 | 0 | 0 |

**세 회차 모두 `브로커 확인 == InfluxDB 행`이 정확히 성립했다.** 유실 0, 3/3.

`backend 수신 − 정답 기준`이 매번 정확히 **+2**다. QoS 1 재전송 2건이고,
InfluxDB 행이 정답 기준과 같으므로 그 2건은 덮어쓰기로 흡수됐다.
이 값이 세 번 다 같은 것은 우연으로 보기 어렵다 — 브로커를 죽이는 순간
in-flight였던 PUBACK이 파티션 수(또는 그에 준하는 고정 구조)만큼 유실되는 것으로
보이지만, **그 메커니즘을 확인하지는 않았다.**

## 흔들리는 값과 흔들리지 않는 값

| | 값 | 성격 |
| --- | --- | --- |
| 총 처리량 | 178,359 ~ 190,538 (**6.4% 폭**) | 부하 기동 타이밍과 머신 상태에 좌우. **재현되지 않는다** |
| `시도 − 확인` 잔여 | **0 / 694 / 0** | 종료 시 45초 flush 안에 못 간 건수. **회차마다 다르다** |
| `수신 − 정답 기준` | +2 / +2 / +2 | QoS 1 재전송 |
| **유실** | **0 / 0 / 0** | identity 기반 불변식. **흔들리지 않는다** |

1회 측정만 봤을 때 "3,542건이 flush 안에 못 갔다"를 발행 측 한계로 적었는데,
**3회를 돌려보니 0건인 회차가 둘이었다.** 그 값은 조건이 아니라 타이밍에 달린
것이고, 1회 결과로 "약 2%가 남는다"고 일반화했으면 틀린 서술이 됐을 것이다.
