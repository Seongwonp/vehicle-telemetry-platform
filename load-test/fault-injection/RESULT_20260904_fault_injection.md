# 의존성 장애 주입 → 복구 → 정합성 대조 (2026-09-04)

CLAUDE.md 우선순위 3번. 각 의존성을 90초 정지시키고, 복구 후 데이터가 실제로
전부 남는지 세었다. 절차와 스크립트는 같은 폴더의 `README.md` / `run_scenario.sh`.

조건: 시뮬레이터 200대 / 0.2초(약 1,700 msg/s), 백엔드 1인스턴스, `docker stop`으로 정지.

---

## 시나리오 A — InfluxDB 90초 정지

메시지는 Kafka까지 정상 도착하므로 **Kafka 토픽이 정답**이다.

| 항목 | 값 |
| --- | ---: |
| MQTT 수신 (backend) | 161,356 |
| Kafka `vehicle-telemetry` | 161,356 |
| Kafka `vehicle-telemetry-dlq` | **76,878** |
| InfluxDB 행 (복구 직후) | 84,615 |

`161,356 − 84,615 = 76,741`이고 DLQ는 76,878건이다. DLQ가 137건 더 많은 것은 알려진
트레이드오프다 — 배치가 재시도되면 그 배치에서 이미 DLQ로 보낸 레코드가 중복 발행된다
(`TelemetryConsumer` 주석). 즉 **차이가 전부 DLQ로 설명된다: 유실이 아니라 격리다.**

### 재처리로 완전히 복구됨

`dlq-tools/dlq.py replay`로 76,878건을 되돌린 뒤:

```
InfluxDB 행   84,615 → 161,356
Kafka 토픽              161,356   ← 정확히 일치
DLQ           76,878 → 76,878    ← 안 늘었다(재처리분이 이번엔 성공)
```

**유실 0.** 격리 → 재처리 → 복구의 전 구간이 실측으로 확인됐다.

### 발견 1 — 짧은 장애도 DLQ를 주 경로로 만든다

**90초 장애에 전체 트래픽의 47.6%(76,878건)가 DLQ로 갔다.**

원인은 재시도 예산이다. `KafkaConfig`의 `FixedBackOff(1000L, 2L)`는 **3회 시도 / 약 2초**라,
2초를 넘기는 장애에서는 사실상 그 구간 전부가 DLQ로 간다. 현실의 의존성 장애는 거의 항상
2초보다 길다 — **DLQ가 예외 경로가 아니라 주 경로가 된다.**

유실은 아니지만, 복구가 **사람이 Runbook을 보고 수동으로 돌리는 절차**다.
장애 한 번에 수만 건을 되돌려야 한다.

### 발견 2 — 분류기가 진짜 원인을 못 보고 있었다

재처리 전 `inspect`를 돌리자 **76,878건이 전부 `unknown`** 으로 나왔다.
Spring이 리스너 예외를 `ListenerExecutionFailedException`으로 감싸기 때문에
`kafka_dlt-exception-fqcn`만 보면 InfluxDB 장애든 JSON 파싱 실패든 같은 wrapper 이름이다.
진짜 원인(`com.influxdb.exceptions.InfluxException`)은 `kafka_dlt-exception-cause-fqcn`에 있었다.

`cause-fqcn`을 먼저 보도록 고치자 **100%가 `transient`로 정확히 분류**됐다.
이 결함이 없었으면 자동 재처리 대상이 하나도 안 나왔을 것이다 —
장애 주입을 안 했으면 못 찾았을 버그다.

## 시나리오 B — Kafka 90초 정지

토픽 자체가 못 받으므로 **backend의 MQTT 수신 카운터가 정답**이다.
검증 대상은 로컬 spool(ADR: Kafka 브로커 장애 시 유실 방지)이다.

| 항목 | 값 |
| --- | ---: |
| MQTT 수신 (backend) | 174,819 |
| Kafka `vehicle-telemetry` (복구 60초 후) | 130,885 |
| Kafka `vehicle-telemetry-dlq` | 0 |
| 차이 | **43,934** |

### 유실이 아니다 — 아직 드레인 중이었다

처음에 spool 디렉터리를 `/var/lib/telemetry/spool`로 잘못 조회해 "잔여 0"으로 읽었고,
잠깐 유실로 판단했다. 실제 경로는 `/app/data/telemetry-spool`이고 **41,634건이 남아 있었다.**
(`ls`가 실패해도 `| wc -l`이 0을 내놓아서 생긴 착각이다.)

### 발견 3 — spool 드레인이 유입보다 89배 느리다

61초 동안 1,200건이 빠졌다 — **19 msg/s**. 유입은 약 1,700 msg/s였다.

```
retryPending():  pending(100)  +  @Scheduled(fixedDelay = 5000ms)
                 => 100건 / 5초 = 20 msg/s 상한 (부하·브로커 용량과 무관)
```

**90초 장애가 약 35분의 복구 시간을 만든다.** 장애가 길어지면 복구 시간이 선형으로
늘어나고, 그 사이 새 장애가 겹치면 spool이 계속 자란다.

배치 크기(100)와 주기(5초)는 성능을 재보고 정한 값이 아니라 기본값으로 보인다.
드레인 상한이 유입의 1/89이면 "유실은 막지만 제때 복구되지 않는" 상태다.

## 정리

| 시나리오 | 유실 | 복구 방식 | 복구 시간 |
| --- | --- | --- | --- |
| InfluxDB 90초 | **0** | DLQ 재처리 (**수동**) | 재처리 실행 시간 |
| Kafka 90초 | **0** | spool 자동 드레인 | **약 35분** (19 msg/s) |

**둘 다 유실은 없다.** 설계 의도대로 격리·보관되고 되돌리면 전부 복구된다.
하지만 **복구 경로가 둘 다 실용적이지 않다** — 하나는 사람 손이 필요하고,
하나는 유입의 1/89 속도다.

## 다음에 할 것 (우선순위 순)

1. **spool 드레인 배치/주기 튜닝.** `pending(limit)`과 `fixedDelay`를 설정으로 빼고
   측정해서 정한다. 주의: `pending()`이 디렉터리를 정렬해 스캔하므로 파일이 수만 개면
   호출 자체가 비싸진다 — 배치만 키우면 되는 게 아니라 스캔 비용도 함께 재야 한다.
2. **재시도 예산 재검토.** 백오프를 늘리면 DLQ로 가는 양이 크게 준다. 재시도는 멱등이고
   (`load-test/storage-integrity/`), lag은 이미 알림으로 드러난다. 단
   `max.poll.interval.ms`를 넘겨 리밸런싱이 도는지 먼저 확인해야 한다.
3. **MQTT 브로커 장애 시나리오.** 정답이 시뮬레이터 쪽에만 있어서(발행 성공 건수를
   세지 않는다) 계측을 먼저 추가해야 한다.

## 한계

- 각 시나리오 **1회 실행**이다. 장애 지속 시간과 부하에 따라 DLQ 비율·드레인 시간이
  크게 달라진다.
- `docker stop`(SIGTERM)이라 의존성이 정상 종료한 경우다. 크래시(SIGKILL)나
  네트워크 단절(패킷 드롭)은 재현하지 않았다 — 특히 타임아웃 동작이 다를 수 있다.
- 백엔드 1인스턴스, 리밸런싱 없는 조건이다.
- 시나리오 B의 "유실 0"은 드레인 속도로 추정한 것이고, 완주 확인은 별도로 진행했다.

# 후속: spool 드레인 튜닝 (같은 날)

위 발견 3(드레인 19 msg/s)을 고쳤다. **추측하지 않고 계측부터 붙였다** —
드레인이 느릴 때 "스캔이 비싼가, 배치가 작은가"를 가를 수 있어야 했다.

추가한 지표: `telemetry.spool.pending`(게이지), `telemetry.spool.scan`(타이머),
`telemetry.spool.drained`(카운터).

## 측정 — 배치 크기가 그대로 상한이다

유입 약 1,700 msg/s, Kafka 180초 정지, `retry-ms=5000` 고정.

| `retry-batch` | 드레인 속도 | 잔여 드레인 시간 |
| ---: | ---: | --- |
| 100 (기존) | **19 msg/s** | 105분 |
| 2,000 | **387 msg/s** | 5분 |
| 10,000 | — | **부하 정지 후 약 1분 내 완전 드레인** |

387 msg/s는 이론치(2,000/5초 = 400)에 붙어 있다. 즉 전송이 느린 게 아니라
**배치가 상한**이다.

**스캔은 병목이 아니었다.** 파일 15만 개 기준 스캔 1회가 약 121ms로, 5초 주기의 2.4%다.
그래서 "주기를 줄이는 것보다 배치를 키우는 쪽이 낫다"는 판단이 측정으로 확인됐다 —
주기를 줄이면 이 121ms가 그대로 배로 늘어난다.

기본값을 **10,000**으로 정했다.

## 측정하다 알게 된 것

**1. 90초 장애로는 spool이 아예 안 쓰인다.** 배치 2,000으로 90초 장애를 재현했더니
`drained_total = 0`이고 MQTT 수신 = 토픽 = InfluxDB로 완벽했다. 수정이 잘 된 줄 알았는데,
Kafka 프로듀서의 `delivery.timeout.ms` 기본값이 120초라 **90초는 프로듀서 내부 버퍼가
통째로 흡수한 것**이었다. 앞선 실행에서 43k가 spool된 건 버퍼(32MB 기본)가 가득 찼기
때문이고, 그 경계가 이 부하에서 아슬아슬하다. **spool을 검증하려면 장애가
`delivery.timeout.ms`를 넘겨야 한다** — 그래서 180초로 다시 쟀다.

**2. 드레인 카운터가 과다 계산되고 있었다.** `drained_total`(379,536)이 MQTT 수신
(261,340)보다 컸다. 선택 시점에 `pending.size()`를 세고 있어서, 이전 주기의 전송이
안 끝난 파일을 다음 주기가 또 집으면 중복 계산된다. **실제로 삭제된 파일**을 세도록
고치고 회귀 테스트로 고정했다.

## 남는 구조적 제약

드레인 중에는 `backlog` 플래그 때문에 **새 메시지도 spool로 간다.** 따라서 부하가
계속되는 동안 백로그가 줄어드는 속도는 **드레인 속도 − 유입 속도**다.
유입과 같은 속도로는 부족하고 **넘어서야** 줄어든다. 배치 10,000은 이론치 2,000 msg/s라
유입 1,700 msg/s 대비 여유가 약 300 msg/s뿐이다 — 부하가 더 크거나 장애가 길면
이 여유가 사라진다. 더 키우려면 프로듀서 버퍼(`buffer.memory` 기본 32MB)와
`max.block.ms`를 함께 봐야 한다. **거기까지는 재지 않았다.**

# 후속: 재시도 예산 재검토 (같은 날)

위 발견 1(90초 장애에 트래픽의 47.6%가 DLQ행)을 고쳤다.

## 예전 값의 근거가 지금은 성립하지 않았다

`FixedBackOff(1000L, 2L)`(3회 시도 / 약 2초)를 고른 이유가 코드 주석에 남아 있었다 —
"한 레코드가 계속 실패하면 그 파티션의 컨슈머 스레드가 오래 막힌다."

**그 걱정은 이 코드에 해당하지 않는다.** `consumeForStorage`는 레코드별 역직렬화·변환
실패를 이미 개별 catch로 DLQ 처리한다. 즉 에러 핸들러까지 올라오는 건 `saveAll()` 실패,
곧 **의존성 장애**다. 개별 메시지가 나빠서가 아니라 InfluxDB가 죽어서 오는 것이다.

같은 파라미터를 두 가지 다른 실패 모드에 쓰고 있었고, 실제로 발생하는 쪽이 아니라
발생하지 않는 쪽에 맞춰 튜닝돼 있었다.

## 바꾼 것

`ExponentialBackOff` + **총 경과 시간 예산**으로 바꿨다. "몇 번 재시도하느냐"보다
"몇 초짜리 장애까지 견디느냐"가 실제로 정하고 싶은 값이기 때문이다.

```
telemetry.kafka.retry.budget-ms          180000  (max.poll.interval.ms 300000보다 작게)
telemetry.kafka.retry.initial-interval-ms  1000
telemetry.kafka.retry.multiplier            2.0
telemetry.kafka.retry.max-interval-ms      30000
```

앞쪽 재시도가 짧아 순간적인 blip은 빠르게 넘기고, 뒤로 갈수록 간격이 벌어져 긴 장애를 견딘다.

## 측정 — 같은 InfluxDB 90초 장애

| 항목 | 예산 2초 (기존) | 예산 180초 |
| --- | ---: | ---: |
| Kafka 토픽 | 161,356 | 180,329 |
| **DLQ** | **76,878 (47.6%)** | **0** |
| InfluxDB 행 (복구 직후) | 84,615 | **180,329** |
| 토픽과의 차이 | 76,741 | **0** |

**90초 장애 전체가 재시도로 흡수됐다.** DLQ 0건, 수동 재처리 불필요, 복구 자동.

### 리밸런싱은 발생하지 않았다

이 변경의 유일한 위험이 "백오프가 `max.poll.interval.ms`를 넘겨 컨슈머가 그룹에서
쫓겨나는 것"이었다. 로그를 세었다.

```
Revoking previously assigned / heartbeat failed / LeaveGroup : 0건
Backoff exhausted                                            : 0건
```

`max.poll.interval.ms`가 로그에 6번 나오지만 전부 기동 시 설정 출력이고 위반이 아니다.
예산 180초 < 300초라 구조적으로도 여유가 있다.

## 남는 것

- **영구 실패 배치는 이제 180초를 붙든다.** InfluxDB가 특정 배치를 계속 거부하는 경우
  (예: 필드 타입 충돌) 그 파티션이 그동안 막힌다. 레코드 단위 실패는 개별 catch로
  걸러지므로 흔한 경우는 아니지만, **재현해서 재보지는 않았다.**
- **180초보다 긴 장애는 여전히 DLQ로 간다.** 그때는 `dlq-tools/dlq.py`로 되돌리면 되고,
  분류기가 `transient`로 정확히 잡는 것은 확인됐다.
- 예산을 더 늘리려면 `max.poll.interval.ms`를 함께 올려야 한다. 그러면 진짜로 죽은
  컨슈머를 감지하는 데 걸리는 시간도 같이 늘어난다 — **그 트레이드오프는 재지 않았다.**
