# 의존성 장애 주입 → 복구 → 정합성 대조 (2026-09-04)

CLAUDE.md 우선순위 3번. 각 의존성을 90초 정지시키고, 복구 후 데이터가 실제로
전부 남는지 세었다. 절차와 스크립트는 같은 폴더의 `README.md` / `run_scenario.sh`.

조건: 시뮬레이터 200대 / 0.2초(약 1,700 msg/s), 백엔드 1인스턴스, `docker stop`으로 정지.

---

## 시나리오 A — InfluxDB 90초 정지

메시지는 Kafka까지 정상 도착하므로 **Kafka 토픽이 정답**이다.

| 항목 | 값 |
| --- | ---: |
| MQTT 수신 (backend) | 161,356 |
| Kafka `vehicle-telemetry` | 161,356 |
| Kafka `vehicle-telemetry-dlq` | **76,878** |
| InfluxDB 행 (복구 직후) | 84,615 |

`161,356 − 84,615 = 76,741`이고 DLQ는 76,878건이다. DLQ가 137건 더 많은 것은 알려진
트레이드오프다 — 배치가 재시도되면 그 배치에서 이미 DLQ로 보낸 레코드가 중복 발행된다
(`TelemetryConsumer` 주석). 즉 **차이가 전부 DLQ로 설명된다: 유실이 아니라 격리다.**

### 재처리로 완전히 복구됨

`dlq-tools/dlq.py replay`로 76,878건을 되돌린 뒤:

```
InfluxDB 행   84,615 → 161,356
Kafka 토픽              161,356   ← 정확히 일치
DLQ           76,878 → 76,878    ← 안 늘었다(재처리분이 이번엔 성공)
```

**유실 0.** 격리 → 재처리 → 복구의 전 구간이 실측으로 확인됐다.

### 발견 1 — 짧은 장애도 DLQ를 주 경로로 만든다

**90초 장애에 전체 트래픽의 47.6%(76,878건)가 DLQ로 갔다.**

원인은 재시도 예산이다. `KafkaConfig`의 `FixedBackOff(1000L, 2L)`는 **3회 시도 / 약 2초**라,
2초를 넘기는 장애에서는 사실상 그 구간 전부가 DLQ로 간다. 현실의 의존성 장애는 거의 항상
2초보다 길다 — **DLQ가 예외 경로가 아니라 주 경로가 된다.**

유실은 아니지만, 복구가 **사람이 Runbook을 보고 수동으로 돌리는 절차**다.
장애 한 번에 수만 건을 되돌려야 한다.

### 발견 2 — 분류기가 진짜 원인을 못 보고 있었다

재처리 전 `inspect`를 돌리자 **76,878건이 전부 `unknown`** 으로 나왔다.
Spring이 리스너 예외를 `ListenerExecutionFailedException`으로 감싸기 때문에
`kafka_dlt-exception-fqcn`만 보면 InfluxDB 장애든 JSON 파싱 실패든 같은 wrapper 이름이다.
진짜 원인(`com.influxdb.exceptions.InfluxException`)은 `kafka_dlt-exception-cause-fqcn`에 있었다.

`cause-fqcn`을 먼저 보도록 고치자 **100%가 `transient`로 정확히 분류**됐다.
이 결함이 없었으면 자동 재처리 대상이 하나도 안 나왔을 것이다 —
장애 주입을 안 했으면 못 찾았을 버그다.

## 시나리오 B — Kafka 90초 정지

토픽 자체가 못 받으므로 **backend의 MQTT 수신 카운터가 정답**이다.
검증 대상은 로컬 spool(ADR: Kafka 브로커 장애 시 유실 방지)이다.

| 항목 | 값 |
| --- | ---: |
| MQTT 수신 (backend) | 174,819 |
| Kafka `vehicle-telemetry` (복구 60초 후) | 130,885 |
| Kafka `vehicle-telemetry-dlq` | 0 |
| 차이 | **43,934** |

### 유실이 아니다 — 아직 드레인 중이었다

처음에 spool 디렉터리를 `/var/lib/telemetry/spool`로 잘못 조회해 "잔여 0"으로 읽었고,
잠깐 유실로 판단했다. 실제 경로는 `/app/data/telemetry-spool`이고 **41,634건이 남아 있었다.**
(`ls`가 실패해도 `| wc -l`이 0을 내놓아서 생긴 착각이다.)

### 발견 3 — spool 드레인이 유입보다 89배 느리다

61초 동안 1,200건이 빠졌다 — **19 msg/s**. 유입은 약 1,700 msg/s였다.

```
retryPending():  pending(100)  +  @Scheduled(fixedDelay = 5000ms)
                 => 100건 / 5초 = 20 msg/s 상한 (부하·브로커 용량과 무관)
```

**90초 장애가 약 35분의 복구 시간을 만든다.** 장애가 길어지면 복구 시간이 선형으로
늘어나고, 그 사이 새 장애가 겹치면 spool이 계속 자란다.

배치 크기(100)와 주기(5초)는 성능을 재보고 정한 값이 아니라 기본값으로 보인다.
드레인 상한이 유입의 1/89이면 "유실은 막지만 제때 복구되지 않는" 상태다.

## 정리

| 시나리오 | 유실 | 복구 방식 | 복구 시간 |
| --- | --- | --- | --- |
| InfluxDB 90초 | **0** | DLQ 재처리 (**수동**) | 재처리 실행 시간 |
| Kafka 90초 | **0** | spool 자동 드레인 | **약 35분** (19 msg/s) |

**둘 다 유실은 없다.** 설계 의도대로 격리·보관되고 되돌리면 전부 복구된다.
하지만 **복구 경로가 둘 다 실용적이지 않다** — 하나는 사람 손이 필요하고,
하나는 유입의 1/89 속도다.

## 다음에 할 것 (우선순위 순)

1. **spool 드레인 배치/주기 튜닝.** `pending(limit)`과 `fixedDelay`를 설정으로 빼고
   측정해서 정한다. 주의: `pending()`이 디렉터리를 정렬해 스캔하므로 파일이 수만 개면
   호출 자체가 비싸진다 — 배치만 키우면 되는 게 아니라 스캔 비용도 함께 재야 한다.
2. **재시도 예산 재검토.** 백오프를 늘리면 DLQ로 가는 양이 크게 준다. 재시도는 멱등이고
   (`load-test/storage-integrity/`), lag은 이미 알림으로 드러난다. 단
   `max.poll.interval.ms`를 넘겨 리밸런싱이 도는지 먼저 확인해야 한다.
3. **MQTT 브로커 장애 시나리오.** 정답이 시뮬레이터 쪽에만 있어서(발행 성공 건수를
   세지 않는다) 계측을 먼저 추가해야 한다.

## 한계

- 각 시나리오 **1회 실행**이다. 장애 지속 시간과 부하에 따라 DLQ 비율·드레인 시간이
  크게 달라진다.
- `docker stop`(SIGTERM)이라 의존성이 정상 종료한 경우다. 크래시(SIGKILL)나
  네트워크 단절(패킷 드롭)은 재현하지 않았다 — 특히 타임아웃 동작이 다를 수 있다.
- 백엔드 1인스턴스, 리밸런싱 없는 조건이다.
- 시나리오 B의 "유실 0"은 드레인 속도로 추정한 것이고, 완주 확인은 별도로 진행했다.
