# 10차 측정: ML 켠 상태의 이상 감지 처리량 (2026-09-03)

지금까지의 모든 측정(7~9차)은 `ML_ENABLED=false` 기준이었다. ML을 켠 조건은
유일하게 남은 미검증 축이라 이번에 측정했다.

## 조건

- `ML_ENABLED=true`, `ML_MIN_SAMPLES=200` (나머지는 9차와 동일)
- anomaly-detector 3인스턴스, 시뮬레이터 6프로세스
- `IsolationForest(n_estimators=100, contamination=0.05)`,
  `window_size=2000`, `retrain_interval=500` (ml_detector.py 기본값)
- 시작 전 offset을 `--to-latest`로 리셋

## 결과 — 처리량이 약 25배 떨어진다

| | ML OFF (9차) | **ML ON (이번)** |
| --- | --- | --- |
| 이상 감지 처리량 | 약 7,500 msg/s | **303 msg/s** |
| 유입 | 7,497 msg/s | 7,223 msg/s |
| Lag | 평균 914, 안정 | **1,266,620 이후로도 계속 증가** |
| 인스턴스 CPU | 각 약 47-70% | **각 90-103% (포화)** |

3인스턴스 모두 CPU가 100% 근처에 붙었다. Python은 GIL 때문에 프로세스당 약 1코어가
상한이므로, 이 구성은 **인스턴스를 늘려도 코어 수만큼밖에 못 올라간다.**
유입을 따라가려면 산술적으로 약 25배, 즉 75인스턴스가 필요하다는 뜻이다.

## 원인 분해 — 재학습이 아니라 `predict()` 호출 오버헤드

처음 세운 가설은 "500건마다 도는 재학습이 주범"이었다. **틀렸다.**
컨테이너 안에서 직접 측정한 결과:

| 연산 | 소요 |
| --- | --- |
| `fit(2000×7, 100트리)` 1회 | 207.5 ms |
| `predict(단건)` 1회 | **11.5 ms** |
| 500건 처리 시 predict 누적 | 5,752 ms |
| 500건 처리 시 fit | 208 ms |
| **predict가 차지하는 비중** | **97%** |

`predict` 11.5ms × 초당 처리량 = 인스턴스당 약 87 msg/s가 이론 상한인데,
실측이 303/3 ≈ 101 msg/s로 거의 정확히 일치한다. 즉 이 구성의 처리량은
**메시지당 `predict()` 호출 하나로 결정된다.**

## 해법 방향 — 배치 예측 (측정으로 확인)

`predict()` 비용이 샘플 수가 아니라 **호출 횟수**에 지배된다:

| 배치 크기 | 호출 소요 | 건당 | 이론 처리량 |
| --- | --- | --- | --- |
| 1건 | 15.29 ms | 15.294 ms | 65 msg/s |
| 10건 | 11.78 ms | 1.178 ms | 849 msg/s |
| 100건 | 14.19 ms | 0.142 ms | 7,045 msg/s |
| **500건** | **16.84 ms** | **0.034 ms** | **29,698 msg/s** |

500건을 한 번에 예측하는 비용이 1건과 사실상 같다(16.8ms vs 15.3ms).
**이 프로젝트에서 InfluxDB 쓰기를 배치로 묶어 8.2 → 9,600 msg/s로 회복한 것과
정확히 같은 구조의 문제다** — 건당 호출 오버헤드가 지배하는 경로.

Kafka 컨슈머는 이미 `poll()`로 메시지를 묶어서 받으므로, 그 배치 단위로
`predict()`를 한 번만 호출하면 된다. 다만 현재 `anomaly_detector.py`는 메시지별
루프에서 수동 커밋·DLQ 처리를 하므로(ADR-017), 배치화하려면 그 경계를 함께
설계해야 한다 — 이번 범위 밖으로 두고 별도 작업으로 남긴다.

## 결론

- **현 구현으로 ML을 켜면 실부하를 감당할 수 없다.** `ML_ENABLED=false`가 기본값인 것은
  타당하며, 켜려면 배치 예측 도입이 선행돼야 한다.
- 병목은 모델의 계산량이 아니라 **호출 방식**이다. `n_estimators`를 줄이거나 더 가벼운
  모델로 바꾸는 것보다 배치화가 훨씬 큰 효과를 낸다(배치 500건에서 건당 0.034ms).

## 한계

- 관찰 시간이 짧다(약 4분). 다만 3인스턴스가 모두 CPU 상한에 붙고 lag이 단조 증가해
  결론이 뒤집힐 여지는 없다.
- 마이크로벤치마크는 난수 데이터(2000×7) 기준이다. 실제 텔레메트리 분포에서
  절대 수치는 다를 수 있으나, 배치 크기에 따른 비용 구조(호출당 고정비 지배)는 같다.
- 배치 예측을 실제로 구현해 처리량이 회복되는지는 **측정하지 않았다.** 위 표는
  sklearn 호출 비용만 잰 것이고, 배치화에 따른 커밋·DLQ 경계 변경 비용은 포함돼 있지 않다.
