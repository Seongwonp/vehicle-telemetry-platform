## 결과 — 불변식 3/3

| 지표 | 1회 | 2회 | 3회 | 편차 |
| --- | ---: | ---: | ---: | ---: |
| 브로커 확인(PUBACK) | 94,811 | 94,212 | 94,512 | 599 |
| Kafka 토픽 | 94,811 | 94,212 | 94,512 | 599 |
| **InfluxDB 행** | **94,811** | **94,212** | **94,512** | 599 |
| **덮어쓰기 유실** | **0** | **0** | **0** | 0 |
| kill 시 커밋 offset | 26,048 | 25,174 | 25,440 | 874 |

**세 회차 모두 `브로커 확인 == Kafka 토픽 == InfluxDB 행`이 정확히 성립했다.**
SIGKILL로 in-flight offset이 미커밋된 상태에서 재전달이 일어나지만, 포인트 identity가
`(measurement, vehicle_id, ms)`라 덮어쓰기로 흡수된다 — 그 결과가 3/3이다.

kill 시점을 offset 20,000으로 지정했는데 실제로는 25,174~26,048에서 걸렸다.
확인 주기가 5초라 그 사이에 넘어간 것이고, **회차 간 편차 874는 이 주기 때문이다.**

## 재전달 수는 이 도구로 잴 수 없다

`batch_size_sum(총) − 토픽`이 **−1,145 / −1,353 / −1,310**으로 세 회차 모두 음수다.
노이즈가 아니라 **체계적 편향**이다.

원인은 지표의 성격이다. `telemetry_influx_write_batch_size_sum`은 프로세스 생명주기
카운터라 재시작으로 리셋되므로 종료 직전 값을 따로 받아 합산해야 한다. 그런데
**샘플과 kill 사이에 처리된 메시지는 죽은 프로세스와 함께 사라져 어느 쪽에도 안 잡힌다.**
그래서 이 차이는

```
batch_sum(총) − 토픽 = (재전달) − (샘플 이후 처리분)
```

이고, 두 항을 분리할 수 없다. 실측에서 뒤쪽이 더 커서 음수가 나온다.

**2026-09-04의 "재전달 68건(0.0873%)"도 같은 방법으로 낸 값이라 신뢰할 수 없다.**
그 문서는 1회 실행이었고 우연히 양수가 나왔을 뿐이다. 해당 문서에 이 사실을 적었다.

정확히 재려면 **프로세스 밖에 처리 카운터**가 있어야 한다(예: 처리 건수를 DB나
별도 토픽에 커밋). 지금은 없고, 이번 작업 범위 밖이다.

### 그래서 판정 기준을 바꿨다

처음 스크립트는 `overwrite_loss == 0`이면 PASS를 찍으면서 판정 문구에 음수 재전달을
그대로 넣었다 — **"PASS (재전달 -1145건)"**. 값이 말이 안 되는데 통과로 보이는,
정책이 가장 경계하는 형태다(`docs/evidence-policy.md`의 "측정 도구 자체의 병목과
파싱 오류를 확인했다").

판정을 **측정 가능한 불변식**(브로커 확인 == 토픽 == 행)으로만 하도록 고쳤고,
`batch_sum − 토픽`은 이름을 바꿔 원본에만 남긴다. 위 3회 결과의 판정은
`counts.csv`에서 다시 계산한 것이다.

## 남은 것

- **재전달 수 미측정.** 프로세스 밖 처리 카운터가 필요하다.
- **kill 시점 편차 874**(offset 25,174~26,048). 확인 주기를 줄이면 좁아지지만,
  줄이면 그만큼 `docker exec` 호출이 부하에 영향을 준다.
- **단일 백엔드 인스턴스**다. 여러 인스턴스 중 하나만 죽는 경우는 다르다
  (`container_name` 고정으로 스케일이 안 된다).
- SIGKILL만 봤다. OOM kill, 호스트 정전 등은 재현하지 않았다.
