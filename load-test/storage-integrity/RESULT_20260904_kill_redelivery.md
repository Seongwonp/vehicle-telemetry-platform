# 강제 종료·재전달 시 InfluxDB 중복·덮어쓰기 수량 측정 (2026-09-04)

| 항목 | 값 |
| --- | --- |
| **검증 상태** | **부분 검증** — 1회 실행 |
| 적용 범위 | 단일 Docker Compose, 200대 / 0.2초, 백엔드 1인스턴스, `docker kill` 1회 |
| 코드 상태 | commit `e4effc2` |
| 실행 명령 | `load-test/storage-integrity/measure_integrity.py` (아래 절차 참고) |
| 원본 증거 | **보존하지 않음** |

> **1회 실행이다.** 재전달 68건(0.0873%)은 죽는 순간의 in-flight 양에 좌우되는 값이라
> 반복하면 달라진다. 이 문서가 보이는 것은 "재전달이 행을 늘리지 않는다"는 불변식이다.

CLAUDE.md 우선순위 1번. `WritePrecision.S` → `MS` 수정(ADR-014) 이후
"이제 안 겹친다"고 적어두기만 했지 **숫자로 확인한 적이 없었다.** 그리고 Kafka가
at-least-once라 강제 종료 시 재전달이 생기는데, 그게 InfluxDB에 어떻게 남는지도
추론만 했다. 둘 다 세었다.

## 조건

- commit `e4effc2`, 스택 `down -v`로 완전히 비우고 시작
- 시뮬레이터 1프로세스 × 200대 / 0.2초, 백엔드 1인스턴스
- 커밋 offset이 20,000을 넘긴 시점에 **`docker kill telemetry-backend`** (SIGKILL)
- 재시작 후 60초 더 부하, 부하 정지, lag 0까지 드레인한 뒤 집계

`docker stop`(SIGTERM)이 아니라 `docker kill`인 게 중요하다 — SIGTERM이면 Spring이
정상 종료하며 in-flight를 커밋해버려서 재전달 자체가 안 생긴다.

## 결과

| 항목 | 값 |
| --- | ---: |
| Kafka 토픽 메시지 수 | 77,929 |
| 고유 `(vehicle_id, ms)` 키 수 | **77,929** |
| 깨진 메시지 | 0 |
| 강제 종료 시점 — 저장된 InfluxDB 행 | 24,004 |
| 강제 종료 시점 — 커밋된 offset 합계 | 23,936 |
| 재시작 후 `saveAll` 전달 포인트 | 53,993 |
| 최종 InfluxDB 행 수 | **77,929** |

```
재전달 건수    = 24,004 − 23,936 =     68 (0.0873%)
덮어쓰기 유실  = 77,929 − 77,929 =      0 (0.0000%)
```

**판정: 재전달 68건이 발생했지만 InfluxDB 행 수는 고유 키 수와 정확히 같다 —
재전달이 덮어쓰기로 흡수됐다(멱등).**

### 교차 검증

숫자가 서로 맞물린다.

```
23,936 (종료 시 커밋) + 53,993 (재시작 후 처리) = 77,929 = 토픽 총 건수  ✓
24,004 (종료 전 저장) + 53,993 (재시작 후 저장) = 77,997 = 77,929 + 68  ✓
```

재시작한 consumer가 커밋된 offset부터 정확히 이어받았고, 저장 시도는 토픽보다 딱
재전달분만큼 많다. 어느 한 숫자가 틀렸으면 이 두 등식이 동시에 성립할 수 없다.

## 왜 멱등인가 (그리고 언제 아닌가)

InfluxDB 포인트의 identity는 (measurement, 태그 집합, 타임스탬프)다. 우리 코드에서는
`vehicle_telemetry` + `vehicle_id` 태그 + **밀리초** 타임스탬프이고,
포인트는 메시지에서 결정론적으로 만들어진다(`TelemetryRepository.toPoint`).
따라서 같은 메시지를 다시 쓰면 identity도 필드 값도 같아 그대로 덮어써진다.

**다만 이건 "덮어쓰기라서 무해한" 것이지 "중복이 안 생기는" 게 아니다.**
identity가 같은데 값이 다르면 뒤엣것이 앞엣것을 조용히 지운다. 실제로 그게
`WritePrecision.S` 시절의 유실 버그였다 — 차량당 초당 2건이면 절반이 사라지는데
Kafka lag은 0이라 정상처럼 보였다.

이번 측정에서 고유 키 수가 메시지 수와 **정확히 같다**(77,929 = 77,929)는 건,
이 부하(200대 × 0.2초)에서는 같은 차량이 같은 밀리초에 두 번 발행하는 일이
한 번도 없었다는 뜻이다. 즉 ms 정밀도가 이 조건에서는 충분하다.

## 재전달 건수의 상한

68건은 우연한 값이 아니라 구조적으로 묶여 있다. `MANUAL_IMMEDIATE` ack라
배치를 처리할 때마다 즉시 커밋하므로, 커밋되지 않은 채 죽을 수 있는 건
**진행 중이던 배치들**뿐이다. 상한은 `max.poll.records`(500) × concurrency(3) = 1,500건.
실측 68건은 그 안에 잘 들어간다.

## 한계

- **1회 실행이다.** 재전달 건수는 죽는 순간 in-flight가 얼마였느냐에 달려 있어
  실행마다 달라진다(0~1,500). 반복해서 분포를 보지는 않았다.
- **같은 밀리초 충돌을 실제로 만들어보지 않았다.** 이번 부하에서 충돌이 0이었다는 건
  "이 조건에서 안전하다"는 뜻이지 "구조적으로 불가능하다"는 뜻이 아니다.
  발행 간격을 극단적으로 좁히거나 차량 수를 줄이면 충돌이 생기고, 그때는 여전히
  조용한 유실이 난다. **정말 막으려면 identity에 밀리초 이하를 구분할 무언가가
  더 필요하다**(시퀀스 번호를 태그로 넣는 등) — 이번 범위에서는 하지 않았다.
- 백엔드 1인스턴스, 파티션 리밸런싱 없는 조건이다. 다중 인스턴스에서 리밸런싱이
  겹치면 재전달 구간이 더 커질 수 있는데 재보지 않았다.

## 측정 과정에서 고친 내 실수 (기록)

1. **첫 시도는 메트릭 스냅샷 경합으로 실패했다.** `telemetry_influx_write_batch_size_sum`을
   종료 직전에 읽고 `docker kill`을 보냈는데, 그 사이(약 0.27초)에도 처리가 계속돼
   재전달 건수가 **-270**이라는 음수가 나왔다. 이 메트릭은 프로세스 생명주기 카운터라
   재시작하면 0으로 돌아가는 것도 함께 문제였다.
   → **종료 직후·재시작 전에 "저장된 행 수"와 "커밋 offset"을 읽는 방식**으로 바꿨다.
   둘 다 프로세스 밖(InfluxDB, Kafka)에 남아 있어 경합이 없다.
2. **두 번째 시도는 파싱 실패였다.** `influx query --raw` 출력 끝에 빈 줄이 있어
   `tail -3 | head -1`이 헤더 행을 집었고 `_value`라는 문자열이 나왔다.
   → 마지막 숫자 행을 고르도록 고쳤다.

두 실수 모두 "숫자가 이상하면 그 숫자를 설명할 수 있을 때까지 결론을 내지 않는다"로
걸러졌다. -270과 `_value`는 결과로 채택될 수 없는 값이었다.
