# 같은 밀리초 키 충돌 — 재현과 판단 (2026-09-05)

CLAUDE.md 우선순위 1번의 남은 갈래. 재전달 실험에서는 충돌이 0건이었지만
(`RESULT_20260904_kill_redelivery.md`), 그건 "그 부하에서 안 났다"는 뜻이지
"구조적으로 안 난다"는 뜻이 아니었다. 두 가지를 확정해야 했다.

1. 충돌이 실제로 유실을 만드는가
2. 만든다면 **언제부터** 만드는가 — 그래야 대응할지 말지 판단할 수 있다

**결론: 유실은 실재한다(500건 → 1행). 다만 차량당 1,000 msg/s를 넘어야 시작되고,
이 시스템의 실제 차량당 발행 속도는 5 msg/s다 — 200배 여유다. 그래서 고치지 않는다.**

도구: `ms_collision.py`

---

## 1. 재현 — 500건을 보내면 1행이 남는다

InfluxDB 포인트의 identity는 `(measurement, 태그, 타임스탬프)`이고, 이 프로젝트에서는
`(vehicle_telemetry, vehicle_id, ms 타임스탬프)`다. 같은 차량이 같은 밀리초에 두 건을
보내면 뒤엣것이 앞엣것을 덮어쓴다.

같은 vehicle_id·같은 타임스탬프로 500건을 발행했다.

```
발행 건수            : 500
브로커 확인(PUBACK)  : 500
InfluxDB 행          : 1
```

**499건이 에러도 로그도 없이 사라졌다.** 파이프라인의 어느 단계에서도 실패가 아니다 —
MQTT는 500건 다 PUBACK했고, Kafka에도 500건 다 들어갔고, InfluxDB 쓰기도 성공했다.
행 수를 직접 세지 않으면 알 수 없다.

같은 구조의 버그를 이미 한 번 겪었다 — `WritePrecision.S`(초)였을 때 발행 주기가
1초 미만이면 그대로 유실됐고, 부하 테스트로 발견해 MS로 올렸다(ADR-014).

## 2. 임계값 — 차량당 1,000 msg/s

한 차량을 일정 간격으로 발행시키며 속도를 올렸다(각 10초).

| 차량당 발행 속도 | 발행 건수 | 고유 밀리초 | 충돌 | 유실률 |
| ---: | ---: | ---: | ---: | ---: |
| 5 msg/s | 50 | 50 | 0 | 0% |
| 50 | 500 | 500 | 0 | 0% |
| 200 | 2,000 | 2,000 | 0 | 0% |
| 500 | 5,000 | 4,999 | 1 | 0.02% |
| 1,000 | 10,000 | 9,936 | 64 | 0.64% |
| **2,000** | 20,000 | 9,960 | 10,040 | **50.20%** |

절벽이 **정확히 1,000 msg/s**에 있다 — 밀리초당 1건이다. 그 위로는 유실률이
대략 `1 − 1000/R`로 간다(2,000에서 50%, 4,000이면 75%).

1,000 미만에서 나온 소수의 충돌(500에서 1건, 1,000에서 64건)은 발행 간격의 지터다.
일정 간격으로 보내도 스케줄링 오차 때문에 가끔 같은 밀리초에 두 건이 몰린다.

> 처음에는 속도 제한 없이 "가능한 한 빠르게" 재려 했는데 초당 105,000건이 나가면서
> paho 큐만 넘치고 InfluxDB까지 도달한 건 573건뿐이라 측정이 오염됐다. 실차는 물론
> 부하 테스트에서도 안 나오는 값이라 답을 못 준다 — 속도를 고정해 다시 쟀다.

## 3. 판단 — 고치지 않는다

**이 시스템의 차량당 발행 속도는 5 msg/s다**(`PUBLISH_INTERVAL=0.2`).
실제 OBD-II 동글은 1~10 Hz다. 임계값까지 **200배** 여유가 있다.

부하 테스트에서 초당 수천 건을 만들 때도 그것은 **차량 수를 늘려서**다
(200대 × 5 = 1,000 msg/s). `vehicle_id`가 태그라 차량이 다르면 identity가 다르므로
아무리 총량이 커도 충돌하지 않는다. 실제로 이번 브로커 장애 실험에서 총 178,451건을
처리하는 동안 InfluxDB 행 수가 정답 기준과 정확히 일치했다.

대안을 둘 다 검토했고, 둘 다 이 여유폭에 비해 비용이 크다.

| 대안 | 왜 안 하나 |
| --- | --- |
| **시퀀스 태그 추가** | 태그는 시리즈 카디널리티를 만든다. 포인트마다 다른 값을 태그로 넣으면 **포인트 수 = 시리즈 수**가 되어 InfluxDB의 인덱스가 무너진다. 시계열 DB에서 가장 잘 알려진 안티패턴이다 |
| **마이크로초 정밀도(`WritePrecision.US`)** | 절벽을 1,000배 밀어내지만, 시뮬레이터·실제 동글·CLAUDE.md의 데이터 스펙(`"2026-05-09T10:00:00Z"`)까지 타임스탬프 계약을 바꿔야 한다. 200배 여유가 이미 있는 위험에 치를 비용이 아니다 |

**대신 임계값을 코드에 남겼다.** `TelemetryRepository.toPoint()` 주석에 "차량당
1,000 msg/s를 넘으면 유실이 시작된다"를 실측치와 함께 적어, 발행 주기를 줄이려는
사람이 먼저 보게 했다.

## 남은 것

- **다중 인스턴스 리밸런싱 구간은 여전히 미측정이다.** 재전달이 생겨도 원본
  타임스탬프를 그대로 들고 오므로 새 충돌은 안 만들지만(덮어쓰기로 흡수),
  그것을 실측으로 확인하지는 않았다.
- **실제 OBD-II 동글의 타임스탬프 정밀도를 확인하지 않았다.** 동글이 초 단위만
  준다면 이 분석의 전제(밀리초)가 무너진다. 실물 연동 시 가장 먼저 볼 것.
- 각 속도 1회 실행, 단일 차량 기준이다.
