## 2. 완료한 것과 증거

### 2-1. Redis 장애 × 낮은 부하 — L1 1회, **무효**, L2 미실행

- **계획을 먼저 고정했다**: `PLAN_20260914.md` — 개방형 부하, IP당 rate limit(60/분) 아래로 생성기 컨테이너를 나눔,
  L1 3.2 req/s → L2 6.4 → L3 9.6(상한), 구간(warm 20 / baseline 90 / 중단 60 / 복구 150 s), 유효성·중단 기준.
  timeout·rate limit·회로 차단기·보안 설정은 **바꾸지 않았다.** Prometheus·Alertmanager는 띄우지 않았다(외부 발송 없음).
- **첫 시도는 도구 결함으로 사전 확인에서 멈췄다**(`curl | grep -q` + `pipefail`, 증거 생성 전) → 고쳐서 재실행.
- **L1** (`RESULT_20260914_L1.md`, `evidence/20260914-132129/`):
  - 구간별 **평균** 요청 수는 계획과 같았고 생성기 오류 0, 생성기 CPU 0.1%.
  - 그러나 요청 **발행이 계획 시각보다 크게 늦었다**(전송 지연 p95 최대 8.2 s·최대 10.7 s, 기준 p95 ≤ 100 ms) —
    **계획한 요청 간격을 지키지 못해 부하 조건을 달성한 실행으로 보지 않는다. 실행 무효, L2 미실행.**
  - 지연은 생성기 5개에서 **동시에** 났고 컨테이너 안 표본기도 12.7 s 늦었으며, 호스트 루프는 늦지 않았다(시계 차이 약 0.3 s).
  - **무부하 프로브**(`evidence/20260914-stallprobe/`): 부하 없이 5분 동안 컨테이너 쪽 실행 지연 6건(**약 10.76 s × 3**), 호스트 0건.
  - **컨테이너 실행 지연이 공통으로 관측됐고, Docker/가상화 계층을 의심하지만 원인은 미확정이다.**
- **무효 실행의 응답 시간·스레드 수는 성능 결론으로 쓰지 않는다.** RESULT §6에 원본 집계와 "다음 유효 실행에서 확인할 질문"으로만 남겼다.
- **같은 환경에서 부하 실험을 반복하지 않는다**(2026-09-14 지시).

### 2-2. event_id 설계 구체화 (구현 없음)

`docs/event-correlation-design.md` §10:
- producer → MQTT → spool → Kafka → 저장·감지 → DLQ 재처리 **12구간 전달표** — 끊길 수 있는 곳은 **계약 2곳(Java·Python)과 재직렬화 DTO 1곳**.
- 원본 `message_id` / 알림 `source_message_id` / 기존 `event_id`(공식 불변) 구분 규칙.
- 구버전 producer·`null`·형식 오류·깨진 JSON·계약 위반 처리표.
- 같은 ID 다른 payload: **막지 않고 식별**(추천) — 입구 캐시 탐지는 Redis 의존이 생겨 비추천.
- 배포 순서: fixture+양쪽 계약 → **감지기** → 백엔드(**`@JsonInclude(NON_NULL)`**) → producer, 롤백 전 spool 0·lag 0.
- 변경 파일·공유 fixture 칸·완료 조건(혼합 버전 테스트 포함)·결정 5건(§10-7).
