## 2026-01-10

### Kafka 개념 공부

Kafka 공식 문서랑 유튜브 강의 보면서 핵심 개념 정리.

**이해한 것**
- Topic: 메시지를 분류하는 채널 (폴더 같은 개념)
- Partition: Topic 내부를 나눈 것, 병렬 처리 단위
- Consumer Group: 같은 그룹 내에서는 파티션을 나눠 처리 → 한 파티션을 여러 컨슈머가 동시에 읽지 않음
- Offset: 각 Consumer가 어디까지 읽었는지 기록

**헷갈렸던 부분**
Consumer Group이 왜 필요한지 처음엔 이해를 못했는데,
"같은 메시지를 다른 목적으로 여러 번 처리하고 싶을 때 그룹을 분리한다"고 이해했다.
이 프로젝트에서 저장 Consumer와 이상감지 Consumer가 같은 메시지를 각자 처리해야 하므로
그룹 분리가 핵심이 될 것 같다.

**참고**
- Kafka 파티션 키: 같은 키는 항상 같은 파티션으로 → 순서 보장
- 이 프로젝트에서 `vehicle_id`를 키로 쓰면 차량별 순서 보장 가능

## 2026-01-18

### MQTT 개념 공부 + OBD-II 조사

**MQTT**
- IoT에 최적화된 경량 pub/sub 프로토콜
- AMQP(RabbitMQ)보다 오버헤드 적음 → 배터리 기기나 차량 동글에 적합
- QoS 3단계: 0(최대 1회), 1(최소 1회), 2(정확히 1회)
- QoS 1이 "성능 vs 신뢰성" 균형상 적합할 것 같다

**OBD-II**
- 1996년 이후 출시된 차량에 의무 탑재
- ELM327 동글을 OBD-II 포트에 꽂으면 차량 데이터 읽기 가능
- python-obd 라이브러리로 접근 가능
- 지원 PID: 속도, RPM, 엔진 온도, 스로틀, 연료량 등

지금은 시뮬레이터로 개발하고, 나중에 실제 동글로 전환하는 구조로 만들어야겠다.

## 2026-03-12

### Kafka → InfluxDB 저장 구현

`TelemetryConsumer.java`, `TelemetryRepository.java` 작성.

**Consumer Group 두 개 쓰는 이유**
처음에 하나의 Consumer Group으로 묶었더니 `consumeForStorage`만 메시지를 받고
이상 감지 Consumer는 아무것도 못 받는 문제가 생겼다.
Kafka는 같은 그룹 내에서 파티션을 나눠주기 때문이다.
그룹을 분리(`telemetry-storage-group`, `anomaly-detector-group`)해서 각자 모든 메시지 수신.

**InfluxDB tag vs field**
`vehicle_id`를 tag로 쓰는 이유를 이해하는 데 시간이 걸렸다.
InfluxDB에서 tag는 인덱싱, field는 인덱싱 안 됨.
"KR-GA-1234의 데이터만 조회"하는 쿼리가 tag 필터는 빠르고, field 필터는 풀스캔이다.
당연히 vehicle_id는 tag로 써야 한다.

**트러블슈팅**
| 문제 | 원인 | 해결 |
|------|------|------|
| timestamp 파싱 오류 | Python 시뮬레이터가 ISO-8601 아닌 포맷으로 전송 | 시뮬레이터에서 `datetime.now(timezone.utc).isoformat()` 사용 통일 |

## 2026-04-10

### JWT 인증 구현

`JwtTokenProvider`, `JwtAuthenticationFilter`, `SecurityConfig`, `AuthController` 작성.

**JWT를 선택한 이유**
세션 기반이면 Redis에 세션 저장소가 필요하고, 서버 여러 대 운영 시 세션 공유 문제가 생긴다.
JWT는 Stateless라 서버 어디에서든 검증 가능. 현재 단일 서버라도 확장성 고려.

**`@Component` 없이 new로 주입하는 이유**
처음에 `JwtAuthenticationFilter`에 `@Component`를 붙였더니
Spring Security 필터체인에 한 번, 서블릿 컨테이너에 한 번, 총 두 번 실행되는 버그가 있었다.
`SecurityConfig`에서 직접 `new JwtAuthenticationFilter()`로 생성해서 `addFilterBefore`에 넘기는 방식으로 해결.

**HMAC-SHA256 키 길이 오류**
처음에 짧은 secret 문자열을 써서 `WeakKeyException` 발생.
HMAC-SHA256은 256bit(32바이트) 이상 키가 필요하다. `.env`에서 긴 랜덤 문자열 사용.

## 2026-05-03

### Isolation Forest 머신러닝 이상 감지

`anomaly-detector/ml_detector.py` 작성.

**Isolation Forest를 선택한 이유**
- 라벨 없는 데이터에서 비지도 학습으로 이상 감지 가능
- 차량 데이터는 "정상" 데이터가 압도적으로 많고 "이상" 데이터는 극히 드물어 불균형 — 이런 경우에 적합
- `contamination=0.05`로 "5%는 이상으로 본다"는 가정을 설정

**초기 200샘플 수집 후 학습 시작하는 이유**
데이터가 너무 적으면 모델이 정상/이상 경계를 못 잡는다.
처음 200개는 정상 데이터 위주로 쌓이므로 이 기반으로 학습하고 이후부터 판단하는 방식.

### Phase 10 — MQTT mTLS 실제 활성화

당일 이어서 진행. `mqtt.tls.enabled` 플래그(기본 false)로 평문/mTLS를 전환할 수 있게
`MqttConfig.java`에 SSL 소켓 팩토리 로직 추가.

**막힌 부분 1**: `broker/certs/generate-certs.sh`를 실제로 실행해본 게 이번이 처음이었다 —
`openssl x509 -req ... -quiet` 옵션이 `x509` 서브커맨드엔 없는 옵션이라(`req`에만 있음)
2단계(서버 인증서 생성)에서 항상 실패하고 있었다. 지금까지 아무도 이 스크립트를 돌려본 적이
없었다는 뜻. `-quiet` 제거로 수정.

**막힌 부분 2**: openssl이 만드는 개인키(PKCS#1)를 Java가 못 읽어서, Spring Boot용으로
`client.p12`(인증서+키)를 추가로 생성하도록 스크립트를 확장했다. 처음엔 CA 인증서만 담은
트러스트스토어도 `openssl pkcs12 -export -nokeys`로 만들었는데, `keytool -list`로 확인해보니
항목이 0개로 나왔다 — openssl이 만드는 cert-only PKCS12는 `trustedCertEntry` 속성이 없어서
Java `KeyStore`가 인식을 못 하는 것. `keytool -importcert`로 바꾸니 정상적으로 1개 항목이 잡혔다.
자세한 이유는 ADR-013.

**검증**: `openssl s_server`/`s_client`로 생성된 server/client 인증서 간 실제 TLS 1.2 mutual auth
핸드셰이크가 되는지 직접 확인(둘 다 `verify return:1`). Java 쪽은 별도 클래스로 `KeyStore` →
`KeyManagerFactory`/`TrustManagerFactory` → `SSLContext` 빌드까지 생성된 `client.p12`/`truststore.p12`
파일로 직접 돌려서 예외 없이 `SSLSocketFactory`가 만들어지는 것까지 확인.
Docker가 로컬에 안 떠 있어서 Mosquitto 컨테이너까지 붙인 완전한 end-to-end 테스트는 못 했다 —
다음에 실제로 켤 때 `docker-compose restart mosquitto` 후 백엔드 로그에서 연결 확인 필요.

기본값은 여전히 평문(1883) — 데모나 보안 점검 때만 `.env`에서 `MQTT_TLS_ENABLED=true` +
`MQTT_PORT=8883`으로 바꾸고 mosquitto.conf TLS 섹션 주석을 해제하면 켜지는 구조.

## 2026-08-07

### 12시간 soak test — Kafka lag이 0인데 데이터가 사라지고 있었다

이상 감지 서비스를 3인스턴스로 띄우고 12시간을 돌렸다. 목적은 "장시간 안정적인가"였는데,
정작 얻은 건 **저장 경로의 무음 유실 버그**였다.

증상이 지독했다. `telemetry-storage-group`의 Kafka lag은 12시간 내내 낮게 유지됐다.
지표만 보면 완벽히 정상이다. 그런데 InfluxDB 쓰기는 **테스트 시작 26초 만에 멈춰** 있었다.

원인은 `TelemetryConsumer`의 catch 하나였다. InfluxDB 쓰기 실패가 역직렬화 실패와 **같은
catch에 묶여** 있어서, DB 장애 중에도 원본을 DLQ로 옮기고 offset을 커밋해버렸다.
컨슈머 입장에선 "처리 완료"라 lag이 안 쌓인다. 조용히 12시간치가 날아갔다.

**여기서 배운 것**: lag이 0이라는 건 "잘 처리되고 있다"가 아니라 "offset이 전진했다"일
뿐이다. 두 문장은 전혀 다른데 그동안 같은 뜻으로 읽고 있었다.

이어서 세 개를 더 고쳤다.
- 쓰기 타임아웃 미지정 + Kafka 정적 멤버십 부재 → poll 초과 시 rebalance livelock
- 에러 핸들러가 기본값(10회 재시도)이라 처리량이 무너짐 → bounded retry로 명시
- 재시도 소진 시 recoverer가 없어 **로그만 남기고 버려지던** 경로 → DLQ recoverer 추가

세 번째는 첫 번째 수정이 없애려던 바로 그 유형의 유실이 다른 경로로 남아 있던 것이다.
하나를 고치면 같은 모양의 다른 구멍이 보인다.

## 2026-08-31

### 처리량이 300배 무너져 있었는데 아무도 몰랐다

soak test 후속으로 실부하를 다시 걸었더니 저장 처리량이 **8.2 msg/s**였다. 목표의 0.3%다.
그런데 `docker stats`로 본 InfluxDB는 CPU 1.66%, 메모리 91MB — **놀고 있었다.**
"DB가 느리다"가 아니라 **요청당 I/O 대기** 신호다.

범인은 2026-08-04의 보안·신뢰성 수정이었다. 그때 `WriteApi`(비동기 배치) →
`WriteApiBlocking`(단건)으로 바꿨는데, 그 대가를 **재측정하지 않았다.** 메시지마다
HTTP 요청 1회 + WAL fsync 1회 + Kafka 커밋 1회가 발생하고 있었다.

배치로 묶어 **8.2 → 약 9,600 msg/s**로 회복했다. 내구성 보장은 그대로 두고 건당
오버헤드만 없앤 것이라, 원래 수정의 목적은 하나도 훼손하지 않았다.

수집 경로에도 같은 모양이 있었다. MQTT 수신마다 spool 파일을 먼저 쓰고 있어서
**20 msg/s**였다 — 정상 경로에서는 디스크를 안 거치고 실패했을 때만 spool하도록 바꿔
**9,600 msg/s**가 됐다.

**여기서 배운 것**: "건당 호출 오버헤드가 지배한다"는 패턴이 이 프로젝트 전체에 반복된다.
InfluxDB 쓰기, spool 쓰기, 나중엔 sklearn `predict()`까지 전부 같은 모양이었다.
그리고 **성능에 영향을 주는 수정에는 재측정이 딸려야 한다** — 안 그러면 두 달을 모른다.
자세한 내용은 ADR-019.

## 2026-09-03

### ML 이상 감지 — 세 번 추측했고 세 번 다 틀렸다

ML을 켜자 처리량이 25배 떨어졌다. 원인을 세 번 짚었는데 세 번 다 측정이 뒤집었다.

1. **"재학습이 병목일 것"** → 아니었다. `fit`이 207.5ms인데 `predict(단건)`가 11.5ms라,
   500건 처리 시 **predict가 전체의 97%** 였다. 그런데 predict는 500건을 한 번에 넣어도
   비용이 1건과 사실상 같다(16.84ms). 배치화하니 303 → 4,550 msg/s.
2. **배치화하자 그제서야 재학습이 병목이 됐다.** 건수 기준이라 처리량이 오르니 빈도도
   같이 폭주했다(초당 2.67회 = 코어의 55%). 시간 하한 60초를 두어 **8,436 msg/s**.
3. **탐지 품질을 재려다 더 근본적인 걸 발견했다.** ML 알림이 처리 건수의 5.71%인데
   이게 `contamination=0.05` 설정값과 일치했다. `contamination`은 탐지율이 아니라
   **표시할 비율**이다 — 정상 차량만 있어도 항상 5%가 알림으로 뜬다.
   즉 "이상 감지"가 아니라 **"가장 바깥쪽 5% 표시"** 였다.

그다음 탐지 품질을 채점하려니 **정답이 없었다.** 시뮬레이터가 주입하던 이상값이 전부
룰 임계값과 대응해서, 정답이 곧 "룰이 잡는 것"이었다. 룰이 못 잡는 복합 패턴 4종과
정답 로그(`[GT]`)를 시뮬레이터에 추가하고 나서야 채점이 가능해졌다.

채점하니 복합 이상 recall 52%였고, 패턴별로 갈라보니 한 유형(`throttle_no_response`)만
**6.9%** 로 유독 낮았다. 원인은 튜닝이 아니라 **모델이 `throttle_position`을 아예 안
보는 것**이었다 — "스로틀을 밟는데 차가 안 나간다"를 스로틀 없이 보면 공회전과 구별이 안 된다.

**여기서 배운 것**: 평균은 원인을 감춘다. 52%라는 숫자만 봤으면 파라미터를 만졌을 텐데,
패턴별로 가르니 파라미터로는 못 고치는 문제가 드러났다.

## 2026-09-05

### 내가 만든 것이 세 번 틀렸고, 세 번 다 측정이 잡았다

우선순위 1·2·3번의 남은 갈래를 전부 닫은 날이다. 결과보다 **틀린 지점**이 더 남는다.

**MQTT 브로커 장애 — 72%가 사라지고 있었다.**
이 시나리오는 "정답 기준이 없어서" 계속 미뤄져 있었다. 브로커가 죽으면 그 아래 단계가
전부 비어 기준이 될 수 없고, 시뮬레이터는 발행 성공 건수를 세지 않았다.

기준을 만드는 데 측정의 절반이 들었고, **두 번 틀렸다.**
처음엔 시뮬레이터를 `docker rm -f`로 죽여서 5초 묵은 주기 로그를 읽었다 —
정답 기준이 backend 수신량보다 **작게** 나왔다. 기준이 관측치보다 작으면 기준이 아니다.
두 번째로 `publish()`가 `NO_CONN`을 반환한 건을 유실로 적었더니 `confirmed`가
`queued`보다 **크게** 나왔다. paho 소스를 열어보니 QoS 1 메시지는 `clean_session`과
무관하게 재연결 시 재전송된다 — 유실이 아니라 재전송 대상이었다.

기준이 서고 나서 나온 숫자는 컸다. 브로커가 PUBACK한 179,532건 중 backend에는
**50,087건만** 도착했다. 원인은 우리 쪽이었다 — `setMaxReconnectDelay`를 지정하지
않아 Paho 기본값 **128초**가 적용됐고, 그동안 브로커가 우리 세션 앞으로 큐잉하다
`max_queued_messages`(10,000)를 넘기면 **말없이 버렸다.** 재연결 후 받은 건 10,002건,
큐 크기와 정확히 같다. 상한을 5초로 낮추니 유실 0.

내가 계산한 유실(129,445)과 브로커 자신의 `$SYS` dropped(129,447)가 독립적으로
일치한 게 이 측정의 근거다. 그리고 그 dropped 지표는 **12시간 soak 사고 때 만들어둔
것**이었다 — 그때는 "브로커만이 아는 유실"을 위해 넣었고, 오늘 실제로 값을 했다.

**이상 알림 — 행은 안 늘었는데 알림은 다시 나갔다.**
DLQ 재처리가 PostgreSQL에 중복을 만드는지 재는 게 목표였다. 답은 "안 만든다"였다
(`UNIQUE(event_id)` + `ON CONFLICT DO NOTHING`, 두 번 되돌려도 행 증가 0).

정작 발견은 옆에 있었다. 컨슈머가 `insertIfAbsent`의 반환값을 **버리고** 무조건
WebSocket 브로드캐스트를 했다. 행은 막히지만 알림은 막을 것이 없어서, 재처리할 때마다
이미 저장된 알림이 다시 나갔다. 앱이 그 토픽을 아직 구독하지 않아 실피해는 없었지만,
"중복이 없다"는 결론만 적고 끝냈으면 못 봤을 것이다.

이 측정이 성립한 이유도 적어둘 만하다. DLQ 9건 중 **3건은 이미 저장돼 있었다** —
서버 커밋은 끝났는데 연결이 끊겨 클라이언트만 실패로 본 in-doubt 건이다.
그 3건이 없었으면 "중복이 안 났다"가 아무것도 증명하지 못했다. 그래서 측정 스크립트가
**"재처리 대상 중 이미 저장된 것"을 먼저 찍고, 0이면 경고**하게 만들었다.

**처리량 — "느리다"고 두 번 적고 재지는 않았다.**
PostgreSQL 장애 실험에서 200초를 기다려도 lag이 3,693 남았고, 리밸런싱 실험에서는
따라잡는 데 13분이 걸렸다. 두 번 다 "느리다"고만 적었다. 재보니 **49 msg/s**,
같은 부하의 알림 발생량이 193 msg/s라 **유입의 1/4**이었다. lag이 쌓이는 게 정상
동작이었던 셈이다.

원인은 레코드 단위 리스너 + `MANUAL_IMMEDIATE`이라 알림 한 건마다 PostgreSQL
커밋(fsync) 1회 + 브로커 왕복 1회. **저장 경로(InfluxDB)에서 똑같은 이유로 8 msg/s까지
떨어진 적이 있고 배치화로 고쳤는데(ADR-011), 알림 경로는 그때 같이 안 고쳤다.**
같은 모양으로 맞추니 lag 20,128 → 238, 4배 부하에서도 유입 전량 소화.

**그리고 그 배치화가 새 버그를 만들었다.** 300초 장애로 재보니 로그에
"배치 저장 실패 **0건**"이 반복해서 찍혔다. 저장할 게 없는데 저장이 실패한다 —
앞뒤가 안 맞는 숫자였다. 클래스 레벨 `@Transactional(readOnly = true)` 때문에
DB를 안 건드리는 `toEntity()`까지 트랜잭션을 열고 있었고, 그래서 DB 장애 중
**변환 단계에서** 실패해 레코드가 하나씩 DLQ로 갔다 — 배치화로 없애려던 바로 그 동작이다.
고친 뒤 같은 장애에서 DLQ 0건.

**덤 — "180초 예산"은 벽시계 시간이 아니었다.**
예산이 180초인데 300초 장애를 DLQ 0건으로 견뎠다. `ExponentialBackOff.maxElapsedTime`이
세는 것은 **백오프로 쉰 시간의 합**이고, 리스너가 실패하는 데 쓴 시간은 안 센다.
시도마다 HikariCP `connectionTimeout` 30초를 기다리니 백오프 합은 좀처럼 안 는다.
실효 내성은 대략 8분. 코드 주석부터 README까지 "총 경과 시간"이라고 적어둔 것을
전부 바로잡았다.

**고치지 않기로 한 것도 하나.**
같은 밀리초 키 충돌은 재현됐다 — 같은 타임스탬프로 500건을 보내면 InfluxDB에
**1행**만 남는다(499건이 에러도 로그도 없이 소실). 하지만 임계값이 차량당
1,000 msg/s(밀리초당 1건)이고 이 시스템은 차량당 5 msg/s다. 200배 여유다.
시퀀스 태그는 포인트마다 시리즈를 만들어 인덱스를 무너뜨리고, 마이크로초 정밀도는
데이터 스펙까지 바꿔야 한다. **재현하고, 임계값을 재고, 안 고치기로 하고, 그 근거를
`toPoint()` 주석에 남겼다.**

**앱 — 폭을 제한했더니 이번엔 안이 비었다.**
화면마다 `maxWidth`를 따로 정해 8종(420~1200)이 흩어져 있었다. 간격·글자에서 고쳤던
것과 같은 문제라 `ContentWidths` 4단으로 묶었다. 기준은 폭이 아니라 "한 줄에 무엇이
들어가는가"다. 그런데 1280px 스냅샷을 뽑아보니 이번엔 계측 카드가 **비어** 있었다 —
아크 게이지가 104~144px 고정이라 카드가 커져도 그대로였다. 폭 제한만으로는 부족했다.

**mTLS로 다시 — 그리고 ACL 버그.**
위 브로커 측정은 전부 평문 프로파일이었다. 운영은 8883/mTLS라 TLS 핸드셰이크가
재연결 시간에 얹히므로 따로 재봤다. 결과는 유실 0, 재연결 약 2초 — 5초 상한 안이다.

정작 수확은 옆에 있었다. `broker/config/acl`이 `$SYS/broker/messages/received`만
허용하고 있었다. 대시보드를 만들며 코드는 `publish/messages/received`로 바꿨는데
**ACL은 같이 안 바꿨다.** 평문 프로파일에는 ACL이 없어 드러나지 않았고,
**운영 프로파일에서만** 파이프라인 대조 대시보드의 1단계가 빈다.
"평문에서 잘 돌아간다"가 "운영에서 잘 돌아간다"가 아니라는 걸 또 배웠다.

이 실행에서 측정 도구도 두 번 고쳤다. 복구 판정을 컨테이너 안에서 mTLS로 붙어
확인하려다 **키 파일이 0600이라 못 읽는** 문제에 걸렸고, 최종 집계 대신
**묵은 주기 로그**를 읽어 "저장(101,638)이 발행(100,628)보다 많다"는 불가능한
숫자가 나왔다. 둘 다 "앞뒤가 안 맞는다"가 신호였다.

**같은 증상에 원인이 둘이었다.**
브로커 90초 장애를 유실 0으로 만들고 끝냈는데, 300초로 늘려보니 **17,243건(4.7%)이
다시 버려졌다.** 이번엔 백엔드가 2초 만에 붙었는데도 그랬다 — 밀려 있던 32만 건이
한꺼번에 쏟아지면서 구독자가 드레인하는 속도를 잠깐 넘어섰기 때문이다.
"브로커가 버린다"는 같은 증상에 원인이 둘이었고, 나는 첫 번째(백엔드가 없어서)만
고쳐놓고 다 고쳤다고 생각하고 있었다. `max_queued_messages`를 10,000 → 100,000으로
올려 0이 됐다. 세 번째로 내 계산과 브로커의 `$SYS` dropped가 독립적으로 맞았다.

**회귀 확인.** 하루에 MQTT 연결 옵션, 컨슈머 배치화, 트랜잭션 전파를 다 건드렸으니
기존 시나리오를 다시 돌렸다. InfluxDB·Kafka 90초 장애 모두 **유실 0**이고, 이번엔
새로 만든 발행 측 계측 덕분에 **전 단계가 한 줄로 대조된다**:

```
influxdb 시나리오 — 발행 162,402 = PUBACK 162,402 = MQTT 수신 162,402
                  = Kafka 162,402 = InfluxDB 행 162,402
kafka 시나리오   — 발행 170,079 = PUBACK 170,079 = MQTT 수신 170,079
                  = InfluxDB 행 170,079 (토픽은 170,080 — spool 재전송 1건이
                    InfluxDB 덮어쓰기로 흡수됐다)
```

예전에는 이 대조가 Kafka 토픽부터 시작했는데, 이제 **차량이 보낸 시점부터** 이어진다.

**이 날 배운 것**: 세 번 다 "내가 방금 만든 것"이 틀렸고, 세 번 다 **숫자가 앞뒤가
안 맞는 순간**에 잡혔다 — 기준이 관측치보다 작다, `confirmed`가 `queued`보다 크다,
저장할 게 없는데 저장이 실패한다. 셋 다 그냥 넘어갈 수 있는 모양이었다.
전날 적어둔 "숫자가 이상할 때 설명될 때까지 결론을 내지 않는다"가 그대로 또 필요했다.

## 2026-09-06

### 결론은 그대로였는데, 근거가 두 개 무너졌다

노트북에서 Codex에게 이 저장소를 평가받아 정리해둔 문서를 읽는 것으로 시작했다.
지적의 핵심은 기능이 아니라 **주장의 품질**이었다 — 한 번 실행한 결과를 성질처럼
적었고, 그 수치를 다시 계산할 원본이 남아 있지 않다는 것.

먼저 문장부터 낮췄다. `docs/evidence-policy.md`를 만들어 검증 상태를 다섯 단계로
정의하고(미검증 / 컴파일 검증 / 부분 검증 / 검증 완료 / 회귀 검증), 결과 문서 열두
개에 **검증 상태·적용 범위·코드 상태·실행 명령·원본 경로** 헤더를 붙였다.
"유실 0"이라고 쓴 곳은 대부분 "그 조건에서 1회 관찰됨"이었다.

**원본을 남기게 만들었다.** `load-test/lib/evidence.sh`로 실행마다
`evidence/<run-id>/`에 시각·git SHA·**작업 트리 dirty 여부**·명령·성공 기준·판정,
집계 CSV, 콘솔 로그, Prometheus 스냅샷, Kafka offset 원문, checksums를 남긴다.
한 실행에 약 30KB다. 붙이다가 스크립트 결함도 하나 나왔다 — health 대기 루프에
**타임아웃이 없어서**, Docker Desktop이 죽은 채 20분을 기다리고도 로그에 단서가
하나도 없었던 실행이 있었다. `wait_until`로 바꿔 300초 뒤 컨테이너 상태와 함께 멈춘다.

**그리고 세 실험을 각 3회 돌렸더니, 내가 쓴 숫자 두 개가 무너졌다.**

불변식은 9회 모두 성립했다(유실 0, 행 증가 0, 브로커 확인 == 토픽 == 행).
무너진 건 **대표값처럼 적어둔 수치** 쪽이다.

1. 리밸런싱 재전달 "40건(0.100%)"을 이 실험의 성질처럼 적어뒀는데, 반복하니
   **42 / 6 / 11**로 7배 흔들렸다. 대표값이 아니라 그날 한 번의 값이었다.
2. 강제 종료 재전달 "68건"은 더 나빴다 — **측정 자체가 성립하지 않았다.**
   3회 모두 음수(−1145 / −1353 / −1310)가 나왔다. `batch_size_sum`은 프로세스
   생명주기 카운터라 컨슈머를 죽였다 살리면 기준선이 리셋된다. 그걸로 뺄셈을 하고
   있었다. 판정 로직도 음수를 그대로 두고 `PASS (재전달 -1145건)`을 찍고 있었다.

판정은 이제 실제로 잴 수 있는 불변식만 쓰고, 2026-09-04의 "68건"은 결과 문서에
**신뢰할 수 없음**으로 표시했다. 지우지는 않았다.

**계약 드리프트 — yml을 고쳐도 동작이 안 바뀌고 있었다.**
코드에서 리스너 방식·Consumer Group·토픽·지표 이름·설정값을 뽑아 문서와 대조했다.
가장 큰 건 `spring.kafka.listener.*`였다. 커스텀 컨테이너 팩토리가 Boot 설정을
물려받지 않고 같은 값을 Java에 하드코딩하고 있어서, **yml을 고쳐도 아무 일도
일어나지 않는다.** 값이 우연히 같아서 아무도 몰랐다.
`ConcurrentKafkaListenerContainerFactoryConfigurer`로 yml을 권위로 바꾸고
회귀 테스트 3건(`KafkaListenerContractTest`)을 붙였다.
지표 이름 9개와 토픽·그룹 목록은 대조 결과 불일치가 없었다 — README 다이어그램의
그룹명 오타와 화살표 오류는 있었다.

**순서 — 정상 경로는 0, 드레인 경로는 200대 전부에서 역전.**
차량별 타임스탬프 역전을 정상 경로와 Kafka 90초 장애 후 spool 드레인 경로로 나눠 셌다.
정상 0건, 드레인 **924건(0.38%)**, 역전이 난 차량은 **200대 전부**, 최대 되돌아간
시간 **113,722ms**. 눈에 띈 건 **1분 미만 역전이 하나도 없다**는 것이다 —
잠깐 뒤섞인 게 아니라 1~2분 묵은 메시지가 뒤늦게 오는 것이고, `retryPending()`
주석에 가설로만 적혀 있던 내용이 그대로 확인됐다.
정상 경로가 0인 이유는 `enable.idempotence=true` + `max.in.flight ≤ 5`인데
**내가 설정한 게 아니라 Kafka 3.0+ 기본값**이라, 깨지면 조용히 깨진다. `ProducerConfig`
블록을 증거로 남겼다.
파이프라인에서 순서를 맞추는 대신 **표시 계층에서 막기로** 했다 — 저장과 조회는
영향이 없고 영향받는 건 앱 실시간 화면 하나뿐이다. 앱이 이미 가진 값보다 오래된
프레임을 버리도록 고쳤다.

**독성 메시지 — 아무 카운터에도 안 잡히는 유실을 찾았다.**
독성 5유형을 Kafka에 직접 넣고, 유형마다 **같은 키의 정상 레코드 100건**을 함께
넣어 가운데에 끼웠다. 대조군이 없으면 "독성이 DLQ로 갔다"까지만 알 수 있는데
그건 질문이 아니다. 질문은 "한 건이 정상 메시지까지 막는가"다. 답은 **아니오** —
함께 막힌 유형이 없다.

발견은 다른 데서 나왔다. `{"speed": 1e309}`는 **유효한 JSON**이고 Jackson이
`Infinity`로 파싱한다. 쓰기가 실패할 줄 알았는데 **성공하고 `speed` 필드만 빠진 채
저장된다.** DLQ 0, 에러 로그 0, 카운터 변화 0. 행은 남으니 정합성 대조(토픽 수 =
행 수)로도 안 잡힌다. 행 단위 유실만 세는 지금 방식이 **필드 단위 유실은 못 본다.**

여기서도 측정 도구가 먼저 틀렸다. 첫 실행에서 이 유형이 `JsonParseException`으로
DLQ에 갔는데, 원인은 Python `json.dumps`가 `float('inf')`를 `Infinity`라는 **비표준
리터럴**로 쓰고 Jackson이 그걸 역직렬화에서 거부하기 때문이었다. 의도한 `saveAll`
경로까지 가지도 못한 것이다. `1e309`를 손으로 넣고서야 위 발견이 나왔다.
**"DLQ로 갔으니 격리가 잘 된다"로 끝냈으면 못 봤다.**

**이 날 배운 것**: 전날은 "내가 만든 것"이 틀렸고, 이 날은 **"내가 쓴 것"이 틀렸다.**
결론은 하나도 안 바뀌었는데 근거가 두 개 무너졌다는 게 요점이다.
1회 실행을 성질처럼 쓰면, 결론이 맞아도 그건 운이다.
그래서 CLAUDE.md에 "작업을 끝낼 때"를 넣었다 — 작업이 끝난 시점은 코드가 도는
시점이 아니라 문서가 따라잡은 시점이다.

### 오전 — 도구가 세 번 틀렸고, 세 번 다 값의 모양이 이상해서 잡혔다

P1-3·P1-4·P1-5를 닫았다. 결론은 전부 PASS인데, **그 PASS에 도달하기까지 내가 만든
측정 도구가 세 번 틀렸다.** 남길 값은 그쪽이다.

**같은 180초가 3.7분과 8.1분이 됐다.**
어제까지의 장애 실험은 전부 90~300초였다. 그래서 `retry.budget-ms`(180초)가 실제로
소진되는 모습을 **한 번도 못 봤다.** 720초 장애를 의존성만 바꿔 두 번 주입했다.

첫 DLQ 발생이 InfluxDB **220초**, PostgreSQL **485초**다. 왜 두 배 넘게 차이 나는지는
로그가 그대로 말해줬다 — 알림 경로는 배치 실패마다 ERROR를 남기는데, 그 시각 간격이
31, 32, 34, 38, 46, 60, 60초였다. **30초를 빼면 1, 2, 4, 8, 16, 30, 30이다.** 백오프 값
그대로다. 시도마다 HikariCP `connectionTimeout` 30초를 실패에 쓰고, 그 시간은 예산에
안 세어진다. 어제 "실효 내성 약 8분"이라고 추정만 적어둔 것이 이렇게 분해됐다.

**로그가 없다는 것을 로그를 보다가 알았다.**
InfluxDB 쪽은 반대였다 — DLQ에 6,158건이 가는 동안 백엔드 로그에 **한 줄도 없었다.**
저장소는 실패를 카운터로만 세고 예외를 던지고, Spring의 재시도 로그는 DEBUG인데
설정이 WARN이다. 처음엔 "Spring이 안 찍는구나"로 정리하려 했는데, 짝 실험의 로그에
`[Kafka→Anomaly] 배치 저장 실패 10건`이 잔뜩 있는 걸 보고 생각이 바뀌었다.
**Spring의 문제가 아니라 두 경로의 비대칭이었다.** 알림 경로는 남기고 저장 경로는
안 남긴다. 그래서 PostgreSQL 장애는 초 단위로 분해됐고 InfluxDB 장애는 아무것도
분해할 수 없었다. 두 곳을 맞췄다 — recoverer에 `[DLQ 이동]` WARN(원인 예외를 풀어서),
저장 경로에 배치 실패 ERROR. 회귀 테스트 `KafkaDlqLoggingTest`.

Runbook은 운영자에게 "DLQ를 조사하라"고 적어놨는데, **DLQ가 생겼다는 사실 자체가
로그에 없었다.** 지표와 알림은 있었으니 방어선은 있었지만, 사고 후 되짚는 경로가 비어
있었다.

**"DLQ에 있다 = 저장 안 됐다"가 두 경로 모두에서 거짓이었다.**
InfluxDB 실험에서 `저장 252,615 + DLQ 6,158`이 토픽(258,726)보다 **47건 많았다.**
뺄셈으로는 "47건이 양쪽에 다 있다"인데, 그건 산술이 말해주는 것이지 확인이 아니다.
가장 이른 DLQ 20건을 그 키로 InfluxDB에 직접 조회했더니 **9건이 있었다.**
있는 것은 `.17x/.27x`, 없는 것은 `.36x/.47x`로 갈렸다 — 파티션마다 배치가 따로 나가서
한쪽만 서버에 닿은 것이다. PostgreSQL 쪽은 더 심했다: DLQ 21건이 **전부** 이미
저장돼 있었다. 그 DLQ에는 **복구가 필요한 알림이 하나도 없다.**

**백로그는 DLQ로 가지 않는다.** DLQ 6,158건의 타임스탬프를 뽑아보니 전부 장애 시작
직후 **26초 구간**이었다. 장애 한복판 12분치는 하나도 없다. 컨슈머가 실패한 배치를
붙잡고 재시도하는 동안 나머지 17만 건은 lag으로 쌓였다가 복구 후 정상 저장됐다.
"장애가 길수록 DLQ가 커진다"고 막연히 생각했는데 반대였다.

**도구가 안 끝났다.**
E2E 추적(P1-5)에서 Kafka 조회를 "20초간 새 메시지가 없으면 끝"으로 짰다. 배경 부하가
계속 쓰는 토픽에서는 **조용해지는 순간이 오지 않는다.** 4분 넘게 돌다 죽였다.
끝 offset을 미리 찍어두고 거기까지만 읽도록 고쳤다.

**지연이 발행 간격의 그림자였다.**
그리고 첫 성공 실행에서 REST 가시성 지연이 이렇게 나왔다.

```
9583, 9082, 8581, 8081, 7580, ... 1573, 1072 (ms)
```

마커 순서대로 **정확히 500ms씩** 줄어든다. 마커 발행 간격이 0.5초다.
실제 지연이라면 이렇게 깔끔할 리가 없다. 원인은 폴링을 발행이 다 끝난 뒤에 시작한

고치니 p50이 **6,078 → 680ms**가 됐다.

**앱은 CI를 얻었다.** 앱 저장소에 format·analyze·test를 도는 CI를 넣었다(첫 실행 success).
Flutter 버전은 고정했다 — `channel: stable`만 주면 앱 코드가 그대로인데 어느 날 러너가
받은 최신 stable 때문에 깨지고, 그러면 CI 실패가 신호가 아니라 잡음이 된다.
**실기기 검증은 여전히 못 했다**(기기가 없다). CI가 그걸 대체하지 않는다는 문장을
AGENTS.md에 같이 적었다.

**이 반나절 배운 것**: 어제는 "1회 실행을 성질처럼 쓰면 결론이 맞아도 운"이라고 적었다.
오늘은 그 앞 단계였다 — **측정 도구가 만든 값이 시스템의 성질처럼 보였다.**
세 번 다 값의 *모양*이 신호였다(끝나지 않는다 / 500ms씩 규칙적으로 줄어든다 /
로그가 한 줄도 없다). 숫자의 크기가 아니라 모양을 의심하는 편이 빨랐다.

### 낮 — 미결정을 닫으니 도구가 또 틀렸다

P1을 다 닫은 뒤 "닫으면서 새로 생긴 미결정과 미측정"만 모아 다시 우선순위를 정했다
(로드맵 P1.5). 새 기능은 하나도 없다. 전부 **방금 만든 주장에 빠진 부분**이다.

**Infinity — 비용을 따져보니 판단할 것이 없었다.**
`{"speed": 1e309}`가 저장되면서 필드만 사라지는 것을 어제 찾아놓고 "고칠지 미결정"으로
뒀다. 이유는 "발생 가능성을 확인하지 않은 채 모든 메시지에 검사 비용을 물릴지"였다.
막상 계산해보니 **포인트당 비교 8회**이고, 같은 포인트를 보내는 HTTP 요청 하나가
이 호스트에서 약 0.8초다. 비교할 크기가 아니었다. 미결정으로 둔 시간이 판단하는 시간보다
길었다.

건너뛰지 않고 **던지게** 했다. 건너뛰면 값이 조용히 없어지고, 던지면 컨슈머의 레코드
단위 catch가 그 레코드만 DLQ로 보낸다 — 같은 유실이라도 **보이고 되돌릴 수 있는** 쪽으로
바꾸는 것이다. 다시 재보니 저장(필드 소실) → DLQ 1건이 됐고 대조군 100건은 그대로다.

그런데 그 DLQ 1건이 **분류에서 `unknown`(100%)으로 떨어졌다.** 새로 만든 예외
(`InvalidDataAccessApiUsageException`)가 `dlq.py` 목록에 없었기 때문이다. 되돌려도 값은
그대로 Infinity라 영구인데, 운영자가 손으로 봐야 하는 상태로 남을 뻔했다.
**새 실패 유형을 만들면 분류도 같이 봐야 한다**는 걸 목록에 적어뒀는데, 정작 내가 그걸
안 했다.

**리밸런싱 — 내가 짐작한 이유가 틀렸다.**
어제 720초 장애에서 재시도가 `max.poll.interval.ms`(300초)를 두 배 넘게 초과하는데도
리밸런싱이 0이었다. 정적 멤버십 덕이라고 적고 "구분 못 함"으로 남겼다.

리스너 로거를 DEBUG로 올리자 재시도 주체가 그대로 찍혔다 — `FallbackBatchErrorHandler`.
같은 offset 묶음이 30초 간격으로 반복된다. 그 클래스가 무엇을 하는지는 **쓰고 있는 jar를
javap로 열어** 확인했다: `ErrorHandlingUtils.retryBatch`가 `Consumer.pause` → `poll` ×2 →
`resume` ×3을 부르고, poll 인자는 둘 다 `Duration.ZERO`다. **백오프로 쉬는 동안 파티션을
pause한 채 계속 poll한다.** 컨슈머가 살아 있으니 poll 간격이 만료되지 않는다.

정적 멤버십은 상관이 없었다. `KafkaConfig`에 "리스너가 오래 붙잡히면 리밸런싱이 돌 수
있다"고 적어둔 것도 이 경로에서는 반대였다. 고쳤다.

이 실행은 720초 장애 **2회차**도 겸했다. 첫 DLQ 220 → 222초, DLQ 6,158 → 6,185(0.4%),
리밸런싱 0 → 0. **in-doubt 건수만 47 → 23으로 흔들린다** — `docker stop` 순간 서버까지
닿은 쓰기가 몇 건이냐는 타이밍 문제다. 어제 배운 것이 그대로 적용된다: 흔들리는 값을
성질처럼 쓰면 안 된다.

**추적 도구가 측정하려던 상황에서 죽었다.**
어제 만든 E2E 추적 도구는 "최초 미도달 단계"를 찍도록 짰는데, 정상 경로에서만 돌렸다.
전 단계 20/20이면 **그 코드는 한 번도 실행되지 않는다.** InfluxDB를 세운 채 돌려봤다.

첫 실행은 결과를 못 냈다. 저장소 조회가 이름 해석에 실패해 `ConnectionError`로 프로세스를
통째로 죽였다. **"어디서 끊겼나"를 재는 도구가, 끊긴 단계를 조회하다 죽는 구조였다.**
고친 뒤 결과는 깔끔하다 — MQTT 20/20, Kafka 20/20, InfluxDB 0/20, REST 0/20,
WebSocket 0/20이고 마커 20건 전부 `최초 미도달 단계=influx`다.

WebSocket이 0인 것은 설계대로다. 브로드캐스트는 저장 성공 뒤에만 일어나므로 저장이
막히면 앱 화면은 **조용해진다** — 묵은 값이 새 값인 척 올라오지 않는다. 어제 순서
측정에서 앱에 넣은 방어와 방향이 같다.

**죽은 토픽도 지웠다.** `vehicle-dtc-events`는 Phase 3을 계획할 때 만들어놓고 아무도 쓰지
않는다(DTC는 텔레메트리 payload 안에 있다). 배포마다 빈 토픽이 생겨 "이건 뭐지"를
반복하게 만들 뿐이었다.

**이 반나절 배운 것**: 오전에는 "내가 쓴 것이 틀렸다"였고, 지금은 **"내가 만든 도구가
측정하려던 바로 그 상황에서 못 쓴다"**였다. 두 도구 다 정상 경로에서만 돌려봤기 때문에
드러날 수 없었다. 장애를 재는 도구는 **장애 상태에서 한 번은 돌려봐야** 도구인지 아닌지
알 수 있다. 그리고 미결정으로 남긴 것 하나(Infinity)는 정작 따져보니 5분이면 끝날
판단이었다 — **미룬 이유가 "판단이 어렵다"가 아니라 "판단을 안 해봤다"였다.**

### 저녁 — 확장이 막혀 있던 이유는 성능이 아니라 이름 두 개였다

P0·P1·P1.5를 다 닫고 남은 것 중에서 **"측정 못 함"으로 표시된 항목**을 골랐다.
저장 경로(Java)의 다중 인스턴스다. 2026-09-05 리밸런싱 측정 때 Python 이상 감지만
3 → 1 → 3으로 돌리고, 저장 경로는 `container_name`과 포트 8080이 고정돼 스케일이 안 돼서
미측정으로 남겨뒀었다. 수집 파이프라인의 본류인데 거기만 비어 있었다.

**먼저 고치지 않고 그대로 복제해봤다.** 무엇이 먼저 깨지는지 보려고.

깨진 건 두 군데였고, 둘 다 **고정된 식별자**였다. 백엔드는 MQTT 수집과 Kafka→InfluxDB
저장을 겸하는데, MQTT `client-id`가 `telemetry-backend`로 고정이고 `cleanSession=false`다.
같은 id로 두 번 붙으면 브로커가 앞 세션을 끊는다 — 두 인스턴스가 서로를 끊는다
(원본 인스턴스에서 연결 끊김 **44건**). Kafka 쪽은 `group.instance.id`가 고정이라
정적 멤버가 겹치고, 뒤에 온 인스턴스가 앞의 멤버를 밀어낸다
(`FencedInstanceIdException` **45건**).

그래서 인스턴스를 3개로 늘렸는데 **컨슈머 그룹 멤버는 3 그대로**였다.
파티션을 나눠 갖는 게 아니라 **뺏는다.** 처리 용량은 하나도 안 는다.
스케일 인 직후에는 멤버가 잠깐 **2**로 떨어지기까지 했다.

`mqtt.ingest.enabled` 스위치를 넣어 수집을 끄고 정적 멤버 id만 인스턴스별로 갈랐다.
그러자 멤버가 **9**(3 인스턴스 × concurrency 3)가 되고 fencing도 연결 끊김도 0이 됐다.
PUBACK·토픽·InfluxDB 행이 **117,125로 정확히 일치**한다.

**그런데 이걸 "3배 빨라졌다"로 쓰면 안 된다.** 파티션이 3개라 9개 멤버 중 6개는 유휴다.
게다가 이 부하(250 msg/s)에서는 1 인스턴스로도 lag이 100대라 **용량 차이가 아예 드러나지
않는다.** 이번에 확인한 건 "확장 가능한 구조가 됐다"까지고, "얼마나 빨라지나"는
파티션과 유입을 함께 올려야 잴 수 있다. 결과 문서에 그렇게 적었다.

**naive 쪽 수치는 버렸다.**
토픽(133,220)이 PUBACK(132,051)보다 많고 행도 PUBACK보다 많았다. 발행한 것보다 고유 키가
많을 수는 없다. 브로커 카운터를 보니 `broker_messages_received`가 155,801로 PUBACK보다
23,750 많았다 — 연결 경합으로 세션이 계속 끊기면서 QoS 1 재전송이 일어난 것이다.
그 상태에서는 **"재전송돼 중복 저장된 것"과 "못 가서 사라진 것"이 총량에서 상쇄돼**
분리할 수 없다.

판정 기준을 PUBACK에 걸어둔 게 내 설계 결함이었다. split에서는 수집 인스턴스가 하나라
경합이 없어 세 수치가 일치했고, 그래서 판정이 의미를 가졌다. **같은 기준이 한 조건에서는
쓸모없고 다른 조건에서는 쓸모 있다**는 걸 두 실행을 나란히 놓고서야 알았다.

**도구는 오늘 여섯 번째로 틀렸다.**
실행 중인 backend의 환경변수를 그대로 복사하려고
`docker inspect --format '{{range .Config.Env}}{{println .}}'`를 썼는데 **`{{end}}`를
빼먹었다.** docker는 파싱 에러를 stderr로만 내고 **빈 문자열**을 돌려준다. 그래서 `-e`
인자가 하나도 안 붙은 채 컨테이너가 떴고, 이미지 기본값으로 `localhost:5432`에 붙으려다
죽었다. 증상만 보면 "DB 연결 실패"라 원인이 엉뚱한 데 있는 것처럼 보인다.
인자가 20개 미만이면 즉시 멈추는 검사를 넣었다(정상은 50개).

**이 날 배운 것**: 확장이 막혀 있던 이유가 처리량도 아키텍처도 아니고 **하드코딩된 이름
두 개**였다. 그리고 그건 "스케일해보기 전까지는 드러날 수 없는" 종류였다 —
단일 인스턴스에서는 두 값이 고정이든 아니든 아무 차이가 없다.
오늘 하루 도구가 여섯 번 틀렸는데, 여섯 번 다 **평소 경로에서는 안 드러나는 자리**였다.

### 밤 — 설정을 읽어보니 위치정보가 무기한 쌓이고 있었다

처리량 이득 측정을 다음으로 미뤘다. 저장 경로가 배치화 후 약 9,600 msg/s를 처리하는데
시뮬레이터가 프로세스당 1,000~1,250 msg/s라, 그 이상 부하를 만들면 병목이 부하 생성기로
옮겨간다. 무인으로 돌리기엔 실패 확률이 높아서 **긴 실행 없이 확정할 수 있는 것**을 골랐다 —
데이터 보존·삭제 정책이다.

설정을 읽는 데 30분이 안 걸렸는데 하나가 걸렸다. **InfluxDB 버킷 보존이 무기한이었다.**
`docker-compose.yml`에 `DOCKER_INFLUXDB_INIT_RETENTION`이 없고, InfluxDB 2.x는 그 값이
없으면 무제한으로 만든다. 거기 들어가는 게 `lat`/`lng`가 포함된 텔레메트리다 —
**차량의 이동 경로가 영구히 쌓이고 있었다.**

90일로 정했다. 근거는 취향이 아니라 코드다 — 조회 기능이 보는 범위가 실시간, `/latest`,
주행 기록(기본 1시간·최대 6시간), 이상 이력이고 **90일을 넘겨 조회하는 기능이 하나도 없다.**
무제한을 유지할 이유가 없었다.

같이 알아낸 것 하나: `DELETE /api/vehicles/{id}`는 소프트 삭제다. `active`만 내리고
InfluxDB의 위치 데이터는 그대로 남는다. 코드 주석에도 그렇게 적혀 있었는데 **그게
개인정보 관점에서 무엇을 뜻하는지는 아무 데도 안 적혀 있었다.** 이번에도 고치지 않기로
했지만 이유를 적었다 — Kafka는 특정 레코드만 지울 수 없어서 "지웠다"고 말하려면 최소
리텐션(1시간)이 지나야 하고, 삭제 API는 인가가 잘못되면 그 자체가 사고다.
대신 수동 삭제 명령을 문서에 넣었다.

로그도 봤다. 요청 로그 패턴에 `clientIp`가 들어가는데 컨테이너 로그에 보존 정책이 없었다.
`backend`에만 로테이션(50m × 3)을 넣었다 — `clientIp`를 남기는 게 이 서비스뿐이다.
다만 이건 **용량 기준**이라 "며칠 보관"이 아니고, 그 한계도 문서에 적었다.

**이 날 배운 것**: 오늘 종일 장애를 주입하고 도구를 고쳤는데, 정작 가장 오래 방치돼 있던
문제는 **설정 파일 한 줄이 없는 것**이었고 부하를 걸 필요도 없었다. 실험으로만 찾을 수
있는 문제가 있고, 읽으면 보이는 문제가 있다. 후자를 안 읽고 있었다.

### 저녁 — 처리량을 재려다 증거를 지웠고, 죽은 실행을 살아있다고 읽었다

오전에 "저장 경로가 수평 확장 가능한 구조가 됐다"까지 보였고 처리량 이득은 미측정으로
남겨뒀다. 그걸 재려고 파티션을 12로 올리고 Kafka에 직접 부하를 넣었다.

**측정 설계를 두 번 고쳐야 했다.** 처음엔 백로그 1.5M을 쌓고 드레인 속도를 재려 했는데
**인스턴스 1개가 40초 만에 다 비웠다.** B 구간에 드레인할 게 없으면 비교가 성립하지 않는다.
그래서 구간 내내 프로듀서를 돌려 lag이 유지되게 바꿨다 — `처리량 = 토픽 증가율 − lag 증가율`.
이 식은 lag > 0일 때만 처리 능력이라, 구간마다 `lag=0` 표본 수를 같이 기록하게 했다.

**그리고 두 번 크게 틀렸다.**

첫째, **증거를 지웠다.** 실험 전에 이전 실행 폴더를 치우려고 `rm -rf evidence/20260906-16*`을
내렸는데, 이 세션은 명령 실행이 실제 시각보다 크게 지연되고 있었고 그게 **실행 중이던
실험의 폴더**를 지웠다. `CLAUDE.md` 맨 위에 "2026-09-05에 같은 실수를 했다"고 내가 적어둔
경고를 그대로 반복했다. 경고를 적는 것과 지키는 것은 다르다. 이제 규칙으로 바꿨다 —
**실험 디렉터리에서 evidence를 글롭으로 지우지 않는다.**

둘째, **죽은 실행을 살아있다고 읽었다.** 재실행은 시작하자마자 죽어 있었다. 계속 발행
방식으로 바꾸며 `BACKLOG` 변수를 없앴는데 로그 헤더에 참조가 남아 `set -u`가 잡았다.
그런데 로그를 지켜보던 감시자가 **앞선 실행의 이벤트를 늦게 전달**하고 있었고, 나는 그걸
재실행의 결과로 읽고 "1회차와 0.5% 안에서 재현됐다"는 표까지 문서에 썼다. 잘못을 잡은 건
숫자가 아니라 **증거 파일을 직접 연 것**이었다 — 거기엔 처리 19,428 / 발행 81,398이 찍혀
있었고, 내가 "재현"이라 부른 값(32,869 / 44,207)과 아예 달랐다.

**그 불일치가 오히려 진짜 결과를 알려줬다.** 두 실행은 발행 압력이 달랐다(33~40k vs
78~92k). 그리고 배수가 1.34배와 2.62배로 갈렸다. 발행이 느리면 3 인스턴스가 자기 능력을
다 못 보여준다 — 앞선 실행의 B(44,394)는 그때 발행(40,905)보다 겨우 8% 높았다. 즉
**"N배 빨라진다"는 시스템의 성질이 아니라 부하 조건의 함수다.** 재현 실패인 줄 알았던 게
측정의 전제를 드러냈다.

그래서 문서에는 배수를 앞세우지 않았다. 가장 단단한 사실은 배수가 아니라 **A 표본
7개가 전부 31,047 이하이고 B 표본 8개가 전부 33,935 이상이라 범위가 겹치지 않는다**는
것이다. 같은 1 인스턴스인 A와 A'가 27% 차이 나는 것도 같이 적었다 — 기준선의 재현성이
그 정도라는 뜻이고, 그걸 숨기면 배수가 실제보다 정밀해 보인다.

결과: `load-test/storage-scale/RESULT_20260906_throughput.md`.

### 상한을 찾으러 갔다가 못 찾았고, 그게 결과다

어제 "3개가 1개보다 확실히 빠르다"까지는 냈는데 **왜 3배가 아닌지**를 몰랐다. 용의자가
셋(InfluxDB 직렬화 / 호스트 CPU / 발행 속도)인데 하나도 안 갈랐다. 그래서 인스턴스를
1→2→3→4로 훑으면서 컨테이너별 CPU를 같이 찍었다.

**계획부터 하나 틀렸다.** 어제 "2개랑 6개를 재자"고 적었는데, `concurrency=3`이라
인스턴스 하나가 컨슈머 스레드 3개다. 파티션 12개면 **4개에서 이미 다 찬다.** 6개는
스레드 6개가 유휴라 이득이 없는 게 아니라 **측정 자체가 무의미**하다. 계산을 안 하고
숫자를 적었던 것이다. 실제로 돌려보니 멤버 수가 3→6→9→**12**로 정확히 갔다.

결과는 **꺾이는 지점이 없다**였다. 24,390 → 40,470 → 44,771 → 57,864이고 InfluxDB CPU도
49% → 153%로 같이 오른다. 즉 **1순위 용의자였던 InfluxDB 포화가 아니다.** 상한을 찾으려던
실험이 "이 범위에는 상한이 없다"를 알려준 셈이라, 문서에는 그렇게 적었다. 다음엔 파티션
24에 인스턴스 8개까지, 그리고 **호스트 전체 CPU**를 재야 한다 — 지금은 컨테이너별 값만
있어서 "호스트가 포화인지"를 판정할 근거가 없다.

### 다시 훑으니 천장이 있었다 — 그리고 CPU가 아니었다

파티션을 24로 올리고 인스턴스를 8까지 열었다. 이번엔 **수확 체감이 보였다**
(+62% → +32% → +22%). 그런데 그보다 값이 나온 건 **다른 실험과 대조한 것**이었다.

| 구성 | 처리량 |
| --- | ---: |
| 파티션 12 · 인스턴스 4 | 57,864 |
| 파티션 24 · 인스턴스 8 | 56,985 |

파티션도 인스턴스도 두 배인데 **1.5% 안에서 같다.** 한 실험만 보면 "아직 안 꺾였다"로
읽었을 값이, 두 실험을 겹치자 **천장**이 됐다. 스윕 하나로는 못 볼 것이었다.

그리고 그 천장이 CPU가 아니라는 것도 나왔다. 호스트 CPU 합이 923.7%인데 코어가 16개라
**1600%의 58%**다. 더 결정적인 건 backend CPU 합이 4개→8개에서 **142.0 → 146.8**로 거의
안 늘었다는 것 — 인스턴스를 두 배로 늘렸는데 CPU를 3% 더 쓴다면, 새로 붙은 컨슈머는
**일하는 게 아니라 기다리고 있다.**

**어제 "InfluxDB 포화"로 의심했던 방향은 절반만 맞았다.** 병목이 저장 쪽인 건 맞는데
CPU 포화가 아니라 I/O 대기다. 다음엔 CPU 말고 쓰기 지연과 디스크를 봐야 한다.

### 원인을 찾았고, 동시에 내 천장 숫자를 스스로 깼다

"CPU가 아니면 뭐냐"에 답하려고 쓰기 지연을 뽑았다. 새로 계측할 필요도 없었다 —
`TelemetryRepository`에 `telemetry.influx.write` Timer가 이미 있었고, 심지어 주석에
과거 같은 패턴("InfluxDB CPU는 1.66%인데 쓰기만 느린 I/O 대기")까지 적혀 있었다.
**있는 걸 안 보고 새로 만들 뻔했다.**

결과가 깔끔했다. **배치 크기가 2,000으로 고정인데 지연만 늘어난다.**

| | 1개 | 2개 | 4개 | 8개 |
| --- | ---: | ---: | ---: | ---: |
| 쓰기 지연 | 388ms | 378ms | **665ms** | 717ms |
| 처리량 증가 | — | **+125%** | +17% | +17% |

**1 → 2는 지연이 그대로인데 처리량이 두 배**다. 진짜 병렬 이득이다.
**2 → 4에서 지연이 76% 뛰면서 증가가 +17%로 꺾인다.** 같은 양의 일에 시간이 더 걸린다는
뜻이고, 공유 자원 포화의 전형적인 모양이다.

그런데 같은 실행이 **어제 내 결론도 깼다.** 파티션 24·8개를 두 번 재니 56,985와 44,279로
**25% 벌어졌다.** 1회차에서 "파티션 12·4개(57,864)와 1.5% 안에서 일치하니 천장은 약
57,000"이라고 썼는데, 그 근접이 **우연에 가까웠다.** 두 번 재보니 이 환경의 변동 폭이
그 1.5%보다 훨씬 크다.

**한 번 맞은 것처럼 보이는 수치가 제일 위험하다.** 두 실험이 우연히 가까우면 그게
법칙처럼 보인다. 그래서 이번 문서에서는 천장을 숫자로 쓰지 않고 **모양**(수확 체감)과
**원인**(쓰기 지연)만 남겼다. 숫자로 말하려면 3회가 필요하다.

### 3회를 채웠더니, 채운 것 자체가 결론을 뒤집었다

"천장을 숫자로 말하려면 3회가 필요하다"고 내가 문서에 적었으니 채웠다. 그리고
**채운 결과가 앞의 결론을 대부분 무효로 만들었다.**

| 인스턴스 | 1회차 10:25 | 2회차 11:07 | 3회차 11:35 |
| ---: | ---: | ---: | ---: |
| 1 | 21,849 | 14,317 | 13,956 |
| 4 | 46,633 | 37,839 | 33,323 |
| 8 | **56,985** | **44,279** | **26,564** |

**모든 행이 단조 감소한다.** 무작위 변동이면 오르내려야 하는데 한 방향이다.
그리고 3회차에서는 **8개가 4개보다 20% 느렸다** — 1·2회차와 정반대다.

디스크는 622GB 남았고 호스트 CPU도 924%/1600%로 여유였다. 남은 후보는
**2시간 30분 연속 고부하로 인한 발열 스로틀링**인데 **온도를 안 쟀으니 추정이다.**

**이게 오늘 가장 값이 큰 발견이라고 본다.** 3회를 안 돌렸으면 "천장 약 57,000"과
"수확 체감"을 그대로 두고 끝냈을 것이다. 실제로는 **회차 간 비교가 성립하지 않는
환경**에서 잰 것이었고, 그러면 두 실험이 우연히 가까웠던 것을 법칙으로 읽게 된다.

반복은 "같은 값이 나오는지 확인하는 절차"가 아니라 **"비교가 성립하는 환경인지
확인하는 절차"**였다. 오늘은 성립하지 않는다는 답이 나왔다.

살아남은 것은 방향 하나다 — 인스턴스를 늘리면 쓰기 지연이 늘고 처리량 증가는 줄어든다.
이건 2·3회차 모두에서 같은 방향이었다.

### 그리고 도구가 또 조용히 죽었다 (오늘 세 번째)

반복 요약을 만들려고 기존 `summarize.sh`를 돌렸더니 표가 **한 줄에서 끝났다.**
에러는 없었다. 원인은 `$((mx - mn))` — bash 정수 산술인데 내가 추가한 CPU·지연이
소수(29.7, 5.4)라 거기서 죽었고, 출력이 `{ ... } > "$OUT"` 안이라 **에러가 파일로도
화면으로도 안 갔다.**

오늘 조용한 실패가 셋이다.

1. `BACKLOG: unbound variable` — `set -u`
2. actuator 긁기가 측정 루프를 3분간 멈춤 — 원인 미상
3. `summarize.sh`의 정수 산술 — 리다이렉트가 에러를 삼킴

**공통점은 "실패했는데 실패처럼 안 보인다"이다.** 셋 다 결과 파일을 직접 열어봐서
잡았다. 어제 적은 "결과는 이벤트가 아니라 증거 파일에서 읽는다"가 오늘 세 번 값을 냈다.

### 계측이 측정을 죽였다

이 데이터를 얻기까지 25분짜리 실행 하나를 통째로 버렸다. actuator 긁는 코드를
`sample()` 안에 넣었더니 **측정 루프가 첫 표본에서 3분간 멈췄다.** 같은 curl을 손으로
재면 97ms인데도 그랬다. 원인은 끝까지 특정 못 했다.

고친 방식은 원인 규명이 아니라 **구조 변경**이었다 — 감시자를 별도 프로세스로 빼서
그게 멈추든 죽든 스윕은 돌게 했다. 측정 루프는 현재 구간 이름만 작은 파일에 쓴다.

**교훈은 "계측을 추가할 때 그것이 실패해도 측정이 계속되는지부터 본다"다.**
오늘 도구 문제로 잃은 시간이 측정 자체보다 길었는데, 대부분 이 원칙을 안 지켜서였다.

### 그런데 그 CPU 숫자 절반은 못 쓴다

A와 A' 구간은 같은 1 인스턴스인데 InfluxDB CPU 중앙값이 5.4%와 46.8%로 **8배** 달랐다.
표본을 열어보니 이유가 바로 보였다 — 구간 안에서 `0.23 → 58.05 → 1.56 → 144.15`처럼
튄다. `docker stats --no-stream`이 재는 창이 짧은데 InfluxDB 쓰기는 배치로 몰려서,
15초 간격 표본 7개로는 대표값이 안 나온다.

**"수치가 나왔다"와 "그 수치를 쓸 수 있다"는 다르다.** 호스트 합은 컨테이너 여러 개가
서로 상쇄돼 단조 증가하고 구간 간 차이도 뚜렷해서 쓸 수 있었는데, 컨테이너 하나짜리
값은 못 쓴다. 어제 파티션 12 스윕에서 "InfluxDB가 49%→153%로 오른다"고 적은 것도
**같은 이유로 신뢰도가 낮다** — 그때는 A/A' 대조로 확인할 생각을 못 했다.

### 그리고 도구가 다섯 번 조용히 죽었다

보존 마이그레이션 절차를 만드는 일은 측정보다 **스크립트를 돌아가게 만드는 데** 시간이
더 걸렸다. 다섯 번 죽었고 **다섯 다 로그 한 줄 없이** 끝났다.

1. `influx bucket update`가 **`--org`를 안 받는다.** list·write·query는 받아서, 공통
   헬퍼로 전부에 붙였더니 이 명령만 실패했다.
2. `--name`이 **대상 선택이 아니라 "새 이름 설정"**이었다. 대상은 `--id`뿐이라 버킷 ID를
   먼저 조회해야 한다. 이건 Runbook의 한 단계가 됐다.
3. Git Bash가 컨테이너 안 경로를 Windows 경로로 바꾼다. `MSYS_NO_PATHCONV=1`을 붙였더니
   이번엔 **호스트 쪽 경로**까지 안 바뀌어 `D:\tmp\...`를 찾았다. 한쪽만 끌 수가 없어서
   파일 경로를 아예 주고받지 않고 **stdin**으로 넣었다.
4. `| head -N`이 **SIGPIPE**를 냈다. 이게 제일 오래 걸렸다 — 쓰기는 **이미 성공한 뒤**라
   데이터는 들어가 있고 로그만 멈춰서, "왜 데이터는 있는데 다음 줄이 안 나오지"를 한참 봤다.
5. Flux에서 `range(stop: now)`는 **400 오류**다. `now`는 함수라 `now()`여야 한다.
   첫 조회는 통과하고 두 번째만 죽어서 또 같은 모양이 됐다.

공통점은 **`set -euo pipefail`**이다. 실패가 로그를 안 남긴다. 어제 `BACKLOG: unbound
variable`로 죽은 것과 정확히 같은 부류인데, 어제는 그걸 모르고 **앞선 실행의 이벤트를
재실행 결과로 읽기까지** 했다. 오늘은 그 교훈이 실제로 값을 냈다 — 매번 실행 직후
증거 디렉터리와 로그가 **진행되는지** 확인하고 넘어갔고, 그래서 다섯 번 다 몇 분 안에 잡았다.

### 측정 결과 자체는 정책에 직접 걸린다

보존을 90일로 줄이면 **즉시 안 지워진다.** t+1s·23s·44s에 400행 그대로였고 t+65초에
사라졌다 — 검사 주기(실험에서 60초)의 다음 회차다. **운영 기본값은 30분**이라 그동안
GPS가 담긴 초과 데이터가 남아 있다. "설정을 90일로 했다"와 "90일 넘은 위치정보가 없다"는
역시 다른 말이었고, 그 간격이 얼마인지가 이제 숫자로 있다.

그리고 **되돌릴 수 없다.** 무기한으로 다시 바꿔도 0행이다. Runbook 맨 위에 경고로 올렸다.

### 어제 견적도 틀렸다

"split을 compose에 반영하려면 스크립트 수십 개를 고쳐야 한다"고 적었는데, 세어보니
**증거 파일과 결과 텍스트를 같이 센 값**이었다(soak 로그 하나에만 `telemetry-backend`가
916번 나온다). 실행 코드만 세면 **17개 파일**이고 반나절 규모다. 견적을 grep 숫자로
말할 때는 **무엇을 세고 있는지**부터 봐야 한다.

### 하루를 닫으며 — 오늘 값을 낸 것은 "못 한다"는 말이었다

아침에 세운 계획은 둘이었다. 처리량 상한의 원인을 밝히고, 보존 마이그레이션 절차를
만드는 것. 둘 다 했고 후속으로 3회 반복까지 갔다. 그런데 **결과 문서에서 제일 값이
나가는 문장은 전부 부정형**이다.

- "상한을 못 찾았다"(파티션 12 스윕)
- "약 57,000은 취소한다"(2회차)
- "이 환경에서는 천장을 숫자로 말할 수 없다"(3회 반복)
- "느려진 원인을 못 밝혔다"

처음엔 이게 실패처럼 보였는데, 지나고 보니 **오늘 한 일의 절반은 어제와 오늘 오전의
내 주장을 무너뜨린 것**이었다. 파티션 12 스윕에서 "InfluxDB CPU가 49%→153%로 오른다"고
쓴 걸 파티션 24 스윕이 "그 CPU 숫자는 못 쓴다"로 뒤집었고, "천장 약 57,000"을 2회차가
뒤집었고, "수확 체감"을 3회차가 "회차마다 다르다"로 흔들었다.

**남은 것은 방향 하나다** — 인스턴스를 늘리면 쓰기 지연이 늘고 처리량 증가는 줄어든다.
이건 잰 회차마다 같은 방향이었다. 크기는 못 말한다.

오늘 도구 문제로 잃은 시간이 측정 자체보다 길었다. 다섯 번 죽었고, 그중 셋은
**실패한 티가 안 났다.** 그래서 마지막에 도구를 고쳤다 — 죽은 실행이 완주와
구분되게, 소수 지표가 문서를 안 끊게. 다음 사람이 같은 함정에 다시 빠지지 않으면
그게 오늘의 남은 값이다.

### 덧 — 부하를 안 거는 일을 하나 골랐고, 거기서 대가를 하나 새로 쟀다

오늘 결론이 "부하를 오래 거는 측정은 당분간 값이 안 나온다"였으니, 남은 시간에는
**부하와 무관한 것**을 골랐다. 로드맵의 "split 구성을 compose에 반영" 항목이다.

2026-09-06에 수집/저장 분리를 만들어놓고도 그게 **실험 스크립트의 `docker run` 안에만**
있었다. `run_throughput.sh`가 돌고 있는 컨테이너에서 환경변수를 복사해 두 개만 덮어쓰는
식이다. 측정에는 충분한데, "운영에서 이걸 어떻게 켜느냐"에 가리킬 곳이 스크립트 본문뿐이었다.
compose 프로파일 `scale`로 옮겼다.

**환경변수를 앵커로 묶은 게 이 작업의 핵심이었다.** 저장 인스턴스를 따로 적으면
50줄짜리 환경변수 블록이 복제되고, 그러면 언젠가 주 backend와 갈라진다. 그리고 그렇게
갈라진 건 **측정에서 안 드러난다** — 둘 다 정상 동작하고 숫자만 달라진다. 그래서
`x-backend-env` 하나를 셋이 공유하게 하고, `docker compose config`로 렌더링해서
**차이가 의도한 두 키뿐**임을 확인했다. 기존 `backend`의 렌더링 결과는 앵커 도입 전후로
바이트 단위로 같았다.

Prometheus를 `static_configs`로 안 한 것도 같은 종류의 판단이다. 저장 인스턴스는 평상시에
안 뜬다. 대상을 고정으로 적으면 프로파일을 안 켠 동안 계속 `up == 0`으로 보이고, 그건
**장애처럼 보이는 정상**이다. 이 프로젝트는 이미 그걸 겪었다 — `MqttIngestFallingBehind`가
잘못된 지표 비교로 정상 부하에서 계속 울고 있었다. `file_sd_configs`로 바꾸니 파일이
없으면 대상이 0개다.

#### 그리고 대가를 하나 쟀다 — 줄이는 건 45초짜리다

기동은 잘 됐다. 인스턴스 3개가 파티션 9개를 정확히 3개씩 나눠 갖고, 정적 id 9종이
겹치지 않고, fencing 0, MQTT 세션은 주 backend 하나뿐이었다.

**내릴 때가 예상과 달랐다.** `down`은 3초 만에 반환하는데 컨슈머 그룹 멤버가 3으로
돌아오는 데 **44초**가 걸렸다. 처음엔 스크립트가 뭘 잘못했나 싶었는데 아니었다 —
**정적 멤버십의 정의 그대로**다. `group.instance.id`를 쓰면 컨슈머가 종료해도 그룹을 즉시
떠나지 않고 `session.timeout.ms`(클라이언트 기본 45초)를 기다린다. 리밸런싱 폭풍을
피하려고 켠 기능이고, 그 대가가 여기 있었다.

그동안 그 파티션은 아무도 소비하지 않는다. 유실은 아니다 — Kafka가 들고 있고 lag으로
쌓였다가 재할당 후 처리된다. 하지만 **부하 중에 인스턴스를 내리면 그 파티션의 지연이
최소 45초 튄다**는 뜻이다. **늘리는 건 싸고 줄이는 건 45초짜리다.**

이건 찾으려고 한 게 아니라 `down`을 확인하다 우연히 걸린 것이다. 오늘 하루의 패턴이
여기서도 반복됐다 — **값이 나온 건 "된다"가 아니라 "이만큼 안 된다" 쪽이었다.**

측정하지 않은 것도 분명히 적어둔다. **처리량은 안 쟀다.** 오늘 결론이 회차 간 비교가
성립하지 않는다는 것이었으니, 이 호스트에서 지금 숫자를 새로 내는 것은 값이 없다.
`session.timeout.ms`도 **설정으로 고정돼 있지 않다** — 45초는 클라이언트 기본값이지
우리가 정한 계약이 아니다.

### 측정한 동작이 문서에 없는 기본값에 매달려 있었다

어제 스케일 다운을 확인하다 "재할당까지 44초"를 쟀고, 그걸 Runbook에 적었다.
`session.timeout.ms`(클라이언트 기본 45초) 때문이라는 설명까지 붙였다.

**그런데 그 값이 우리 설정 어디에도 없었다.** `application.yml`을 열어보면
`group.instance.id`는 있는데 `session.timeout.ms`는 없다. 45초는 Kafka 클라이언트가
기본으로 주는 값이고, 우리는 그 기본값 위에 문서를 세워둔 셈이었다.

이건 P0-3에서 찾은 것의 **반대 방향**이다. 그때는 `spring.kafka.listener.*`가 있는데
동작에 반영이 안 됐다 — **설정은 있는데 동작이 없었다.** 이번엔 반대로
**동작은 있는데 설정이 없다.** 둘 다 "문서를 읽은 사람이 믿는 것"과 "실제로 일어나는 것"이
갈라지는 같은 병이고, 둘 다 정상 동작 중에는 아무 티가 안 난다.

Kafka 클라이언트를 한 번 올리다 기본값이 바뀌면 Runbook의 "45초"가 조용히 틀린 말이 된다.
지금 값과 **같은 값**을 명시로 박았다. 동작은 하나도 안 바뀐다 — 그게 요점이다.

#### 테스트를 어디에 걸 것인가에서 한 번 갈렸다

팩토리에 도달하는지 보려고 했다. 그런데 그건 **배선만 증명한다.** 누가 `application.yml`에서
그 줄을 지워도 테스트는 그대로 통과한다 — 테스트가 자기 값을 들고 있으니까.
지금 막으려는 건 정확히 그 경우다.

그래서 `YamlPropertySourceLoader`로 **실제 `application.yml`을 읽어서** 단언하게 했다.

| yml에서 그 줄을 삭제 | **2건 실패**(명시 단언 + 환경변수 단언) |

전체 스위트도 돌렸다 — **116개 전부 통과, skip 0.** Docker가 올라와 있어서
Testcontainers 계약 테스트 5종(Flyway/Influx/Kafka DLQ/Kafka 저장 실패/Redis)까지

#### 값은 안 바꿨다 — 바꿀 근거가 없다

오판해 리밸런싱이 는다. **이 프로젝트는 12시간 soak test에서 리밸런싱 폭풍에 갇힌 적이
있고, 정적 멤버십은 그걸 피하려고 켠 것이다.** 그 대가를 안 재고 줄이면 어제 얻은 것을
반납하는 셈이라, 명시만 하고 값은 그대로 뒀다. **줄였을 때의 대가는 아직 안 쟀다** —
그것도 그대로 적어둔다.

### dev 프로파일을 띄워보니, 어제 안 드러난 게 하나 있었다

어제 남긴 미검증 하나를 닫으러 갔다 — compose 프로파일 `scale`을 **평문(dev) 스택에서
실제로 띄우기.** 어제는 Docker Desktop이 내려가 있어서 렌더링만 봤다.

구조는 예상대로였다. 멤버 9 / 정적 id 9 / 호스트 3 / 할당 파티션 9, fencing 0,
브로커 접속은 주 backend 하나뿐. dev 오버레이가 저장 인스턴스에도 먹어서
`MQTT_PORT=1883`, `MQTT_TLS_ENABLED=false`가 들어가 있었다 — 이게 확인하려던 것이었다.
어제 명시한 `session.timeout.ms = 45000`도 실제 컨슈머 설정에 찍혔다.

**예상 못 한 건 중간 상태였다.** `up 2` 직후 `status`를 봤더니 이랬다.

```
멤버(컨슈머 스레드): 9
할당된 파티션 합  : 3
→ 유휴 멤버 6개. 파티션이 모자란다 — 늘리지 않으면 인스턴스를 늘려도 이득이 없다.
```

파티션은 분명히 9개로 늘렸는데 할당은 3개다. 스크립트가 "파티션이 모자란다"고 하는데
파티션은 안 모자랐다. 2분 뒤에 다시 봐도 그대로였다.

원인은 **컨슈머가 들고 있는 토픽 메타데이터가 낡은 것**이었다. `metadata.max.age.ms`가
기본 5분이라 그 전까지는 파티션이 3개인 줄 안다. 저장 인스턴스가 붙으면서 리밸런싱은
즉시 돌았지만, **리더가 아는 파티션이 3개니까 3개만 나눠준다.** 로그 타임스탬프로 보면
11:21:38에 3개를 할당했고 11:26:05에 다시 리밸런싱이 돌면서 9개가 됐다 — 4분 27초.

**어제는 왜 안 드러났나.** 어제는 backend를 띄우기 *전에* 파티션을 늘렸다. 오늘은
순서가 반대였다. 같은 절차를 두 번 했는데 한 번은 안 보이는 종류의 것이었다.

이건 운영에서 정확히 "인스턴스를 늘렸는데 처리량이 그대로"로 보인다. 그리고 그 상태에서
급하게 인스턴스를 더 늘리면 유휴 멤버만 는다. Runbook의 "파티션을 **먼저** 늘려라"에
이제 이유와 숫자가 붙었다.

#### 그리고 내 스크립트가 정상을 장애처럼 보여주고 있었다

같은 `status` 출력에서 Prometheus 쪽이 이랬다.

```
=== Prometheus 스크레이프 대상 ===
[{"targets": ["backend-storage-1:8080","backend-storage-2:8080"], ...}]
  (Prometheus 응답 없음)
```

직접 질의해보니 Prometheus는 200이고 대상 둘 다 `up=1`이었다. 파이프라인이
`curl ... | grep ... || echo "(Prometheus 응답 없음)"` 모양이라, **grep이 0건이면
파이프라인이 실패로 끝나서** 그 메시지가 찍힌 것이다. 대상 파일을 막 쓴 직후에는
file_sd 갱신 주기(30초)만큼 비어 있는 게 정상인데.

어제 `static_configs`를 피한 이유가 "장애처럼 보이는 정상을 만들지 않으려고"였다.
그래놓고 **같은 실수를 스크립트 메시지에서 저질렀다.** 도달성 확인과 대상 수 확인을
분리했다.

### NaN은 검사에 걸리지 않았다 — 검사까지 오지도 않았다

2026-09-06 독성 실험에서 `speed: 1e309`(양의 Infinity)만 보고 NaN과 음수 쪽을 미검증으로
남겼다. 오늘 둘 다 넣었다.

음수는 예상대로였다. `-1e309`가 `Double.NEGATIVE_INFINITY`로 파싱되고 `toPoint()`의
`finite()`에 걸려 DLQ로 간다. 양수와 **같은 예외 클래스, 같은 `permanent` 분류**다.
`Double.isFinite()`를 쓴 코드를 읽으면 당연한 결론인데, 그건 추론이었고 이제 실측이다.

**NaN이 예상과 달랐다.** 나는 "NaN도 `finite()`에 걸리겠지"라고 생각하고 있었는데,
DLQ에 찍힌 예외가 이거였다.

```
com.fasterxml.jackson.core.JsonParseException
Non-standard token 'NaN': enable `JsonReadFeature.ALLOW_NON_NUMERIC_NUMBERS` to allow
```

**`finite()`에 도달하지도 못한다.** `NaN`은 JSON 스펙에 없는 비표준 리터럴이고,
Boot 기본 `ObjectMapper`가 그걸 꺼둔 채라 역직렬화 단계에서 잘린다. 즉 결과만 보면
"NaN도 막힌다"가 맞지만, **막는 주체가 내가 넣은 방어가 아니다.**

이 구분이 왜 중요한가. 언젠가 누가 `finite()`를 보고 "포인트마다 비교 8회씩 하는데
이게 정말 필요한가" 물을 것이다. 그때 "Infinity는 실제로 들어오고, NaN은 이 입구로는
못 들어온다"를 알고 있으면 판단이 되지만, "검사가 있으니 안전하다"만 알고 있으면
판단할 수가 없다. 그래서 결과 문서와 `finite()` javadoc 양쪽에 적었다 —
**NaN 분기는 지금 입구에 대해서는 잉여이고, 산술로 NaN이 생기는 경로가 생기면 그때 유효해진다.**

대조군은 두 유형 모두 100/100 살아남았다. 독성 1건이 같은 배치의 정상 레코드를 막지
않는다는 결론은 그대로다.

### 스케일 다운 3회 — 그리고 하나를 버렸다

어제 44초, 오늘 46초를 재놓고 "2회라 안정성 주장은 못 한다"고 적었다. 채웠다.
dev 프로파일 동일 조건에서 **46 / 48 / 47초**, 폭 2초다. 이제 "약 45~48초"라고 쓸 수 있다.

**그 사이에 회차 하나를 버렸다.** 처음 잰 값이 **8초**로 나왔다. 앞의 것들과 너무 달라서
그대로 적지 않고 왜 그런지 봤는데, 스케일 업 후 대기 조건을 `할당된 파티션 >= 9`로만
걸어둔 게 문제였다. 직전 스케일 다운 뒤 남아 있던 **기존 3개 멤버가 이미 9개 파티션을
전부 쥐고 있어서** 조건이 즉시 참이 됐고, 저장 인스턴스가 그룹에 붙기도 전에 내린 것이다.
멤버 수와 할당 수를 **둘 다** 봐야 했다.

값이 8초로 안 나오고 43초쯤 나왔으면 그냥 적었을 것이다. **범위 밖으로 튀어준 덕에
잡혔다.** 이 프로젝트에서 반복해서 값을 낸 게 이 모양이다 — 숫자가 앞뒤가 안 맞는 순간.

한 가지 더 보였다. `down` 명령 자체가 반환하는 데 4~5초가 들고 위 시간은 명령을 낸
시점부터 잰 것이라, **순수 세션 만료는 42~43초**다. `session.timeout.ms`(45,000ms)와
같은 자리다.

### 부하를 걸고 내려보니 — 계측이 먼저 함정에 걸렸다

무부하 3회를 채웠지만 Runbook의 "부하 중에 내리면 그 파티션의 지연이 튄다"는 여전히
**추론**이었다. 부하를 걸고 다시 쟀다.

결과 자체는 예상대로였다. 제거된 인스턴스가 쥔 6개 파티션이 멈추고(평균 lag 7,137 →
177,952), **살아있는 backend의 3개는 평평했다**(2,244 → 1,324). 격리는 성립한다.
유실도 0이다 — 토픽 총 offset과 InfluxDB 행 수가 두 회차 모두 정확히 일치했다.

**틀린 건 내 계측이었다.** 지표로 "무소유 파티션 수"(`CONSUMER-ID`가 `-`인 파티션)를
넣어뒀는데 1회차 내내 **끝까지 0**이었다. 6개가 분명히 멈춰 있는데 0이다.

원인은 정적 멤버십의 정의 그 자체였다. **인스턴스를 내려도 죽은 멤버가
`session.timeout.ms`까지 소유권을 그대로 들고 있다.** `--describe` 출력만 보면 9개 전부
주인이 있고 멀쩡해 보인다. 내가 지표를 고를 때 "주인이 없어지겠지"라고 생각했는데,
**주인이 없어지지 않는 게 이 기능의 요점**이었다.

> 소유자가 있다는 것이 소비되고 있다는 뜻이 아니다.

1회차는 파티션별 lag 원본을 직접 열어서 결론을 냈다. 지표를 `current_offset`이 직전
표본 대비 안 움직인 파티션 수로 바꾸니 2회차에서 **정확히 6개**가 t=219~245에 잡혔고,
재할당 직후 0으로 돌아갔다.

운영에서도 같은 함정이다. 스케일 다운 직후 `--describe`를 보고 "주인이 다 있으니 정상"이라
판단하면 틀린다. Runbook에 경고로 넣었다.

### 대조군이 없으면 근거도 없다 — 정적 멤버십을 끄고 재봤다

이 프로젝트에서 정적 멤버십은 12시간 soak test의 리밸런싱 폭풍을 피하려고 켠 것이다.
근거가 분명해서 한 번도 의심하지 않았는데, 어제 스케일 다운 45초를 재고 나서
"그게 정적 멤버십 때문"이라고 쓸 때 문득 걸렸다. **그것도 설명이지 측정이 아니다.**

끄고 재보려 했더니 **끌 수가 없었다.** Kafka는 `group.instance.id`에 빈 문자열을
허용하지 않는다(`NonEmptyString` 검증에 걸려 기동이 실패한다). 끄려면 `application.yml`에서
줄을 지우고 다시 빌드해야 한다. **대조군을 만들 수 없는 구조였다는 걸 이때 알았다.**

그래서 `KafkaConfig`에 커스터마이저를 하나 넣었다 — **빈 값이면 그 속성을 제거한다.**
`GROUP_INSTANCE_ID_BASE=`로 끌 수 있게 됐고, compose에서 `${VAR-기본값}`으로 받는다.
`:-`가 아니라 `-`인 게 중요하다. `:-`는 빈 값도 기본값으로 되돌려서 **끄려는 의도가
조용히 무시된다.** 처음에 `:-`로 썼다가 렌더링을 확인하면서 잡았다.

결과는 깨끗했다.

| | ON (3회) | OFF (1회) |
| --- | ---: | ---: |
| 멤버 9 → 3 | 다운 후 46 / 52 / 54초 | **9초** |
| 정지 파티션 | **6개** | **0개** |

**끄니 컨테이너가 멈추는 즉시 재할당된다.** 정적 멤버가 아닌 컨슈머는 종료할 때
LeaveGroup을 보내기 때문이다. 설명이 측정이 됐다.

정적 멤버십을 켠 이유는 스케일 다운을 느리게 하려는 게 아니라 폭풍을 피하려는 것이었고,
그 폭풍은 재현하지 않았다.

ADR-024에 "이 ADR의 가장 큰 공백은 끄는 것의 대가"라고 적어뒀다.

### `dtc_codes` — 배열을 문자열로 접는 자리에서 둘이 샜다

`toPoint()`는 `String.join(",", dtcCodes)`로 배열을 문자열 하나로 만든다.
접는 순간 두 가지가 가능해지는데 둘 다 확인한 적이 없었다.

- **`[null]`** → `String.join`이 null을 **"null"이라는 네 글자**로 만든다. NPE가 아니다.
- **`["P0301,P0420"]`**(코드 1개) → 저장된 문자열이 `["P0301","P0420"]`(코드 2개)와 **똑같다.**

둘 다 저장되고 DLQ·에러·카운터가 전부 0이다. 행 수도 맞아서 정합성 대조로도 안 잡힌다.

**고치지는 않았다.** `speed: 1e309`를 고친 이유는 **필드가 통째로 사라져서** "값이 없다"와
"0이다"를 구분할 수 없었기 때문인데, 여기는 값이 남아 있고 DTC 형식(`[PBCU]\d{4}`)에
안 맞아 눈에 띈다. 쉼표 충돌은 스펙을 지키는 입력에서 아예 못 생긴다. 구분자를 바꾸는 건
저장 포맷 계약을 바꾸는 일이라 대가가 더 크다.

대신 **다시 볼 조건**을 코드 주석에 박았다 — 실제 장치에서 한 번이라도 관찰되면 뒤집는다.
`rpm: 2000.7`과 같은 모양의 판단이다. 오늘 이런 결정을 두 번 했는데, 둘 다
"고치지 않는다"가 결론이라 오히려 **왜 안 고치는지를 남기는 게 일의 대부분**이었다.

### 양쪽 대가가 처음으로 다 숫자가 됐다

어제 `session.timeout.ms`를 45,000ms로 명시하면서 "줄였을 때의 대가는 아직 안 쟀다"고
적어뒀다. 그걸 쟀다.

방법은 `docker pause`다. 컨테이너를 SIGSTOP으로 얼리면 하트비트가 멈추니
**긴 GC 정지와 같은 모양**이 된다. 20초를 얼리고 리밸런싱 횟수를 세대(generation) 번호
증가량으로 셌다.

| 같은 20초 정지 | 정지 중 멤버 | 리밸런싱 |
| --- | ---: | ---: |
| `session.timeout.ms=45000` | 6 (그대로) | **0회** |
| `session.timeout.ms=10000` | **3** (절반이 쫓겨남) | **2회** |

**같은 20초인데 한쪽에서는 아무 일도 안 일어난다.** 10초 쪽은 나갈 때 한 번,
돌아올 때 한 번 돈다.

이걸로 양쪽이 처음으로 다 숫자가 됐다 — 45,000ms를 유지하는 비용은 **스케일 다운
46~54초**이고, 줄이는 비용은 **20초 순단마다 리밸런싱 2회**다.
판단 기준은 명확했다: **스케일 다운은 시간을 골라서 할 수 있지만 GC 정지와 순단은
고를 수 없다.** 고를 수 없는 쪽을 안전하게 둔다.

실험을 짜면서 제일 신경 쓴 건 결과가 아니라 **"설정이 안 먹은 채로 '차이 없음'이
나오는 것"**이었다. 두 조건이 같은 값으로 돌면 "차이가 없다"는 결론이 나오는데
그게 제일 그럴듯하게 틀린 답이다. 그래서 매 조건마다 backend 로그에서 실제 컨슈머
설정을 읽어 대조하고, 안 맞으면 즉시 중단하게 했다. 로그에 45000과 10000이 각각
찍힌 걸 확인하고 나서야 결과를 읽었다.

### 마무리하다 도구 결함을 둘 더 남겼다

커밋을 다 하고 상태를 점검하다 `monitoring/prometheus/targets/backend-storage.json`이
남아 있는 걸 봤다. 새로 쓴 `run_session_timeout_cost.sh`가 `scale-storage.sh up`만 부르고
`down`을 안 불러서다. compose `down -v`로는 안 지워지는 파일이다.

남겨두면 다음 기동 때 Prometheus가 없는 인스턴스를 긁으려 한다 — **어제 `static_configs`를
피한 이유(장애처럼 보이는 정상)를 그대로 되살리는 것**이다. 어제는 같은 함정을 스크립트
메시지에서 밟았고 오늘은 파일로 밟았다. 같은 실수가 형태를 바꿔 두 번 나왔다.

고치면서 한 번 더 틀렸다. 정리 호출을 `evidence_capture_kafka_groups`보다 **앞에** 넣어서,
컨슈머 그룹 스냅샷이 **정리된 뒤의 상태**로 남게 돼 있었다. 증거를 거두기 전에 치우면
증거가 아니다. 뒤로 옮겼다.

둘 다 실험 결과에는 영향이 없다(이번 실행의 증거는 이미 다 남았다). 하지만
**정리를 안 하는 실험 스크립트는 다음 실행을 오염시킨다.** 결과보다 이쪽이 더 오래 간다.

### ADR의 가장 큰 공백에 손을 댔다 — 그리고 내 집계를 못 믿게 됐다

낮에 정적 멤버십을 끈 대조군을 돌리고 ADR-024에 이렇게 적었다: "이 대조군은 끄는 것의
이득만 봤다. 켠 이유(리밸런싱 폭풍)는 재현하지 않았다 — **이게 이 ADR의 가장 큰 공백**이다."
시간이 남아서 그 반대편을 쳐봤다.

`docker pause`로 330초를 얼렸다. `max.poll.interval.ms`(300초)를 넘기니, 정적 멤버십이
막아주는 바로 그 경로 — 컨슈머가 그룹을 완전히 떠났다가 member id를 새로 받는 경로 —
를 타게 된다.

스크립트가 낸 요약은 이랬다.

```
조건            리밸런싱  폭풍표식  재개 후 멤버
A 정적 ON         2         12         6
B 정적 OFF        2         12         6
판정: 이 조건에서는 차이가 안 보인다 — 폭풍 재현 실패
```

**완전히 같다.** 여기서 그냥 "차이 없음"으로 적고 끝낼 뻔했다. 그런데 숫자가 너무
똑같아서(12와 12, 2와 2) 이상했다. 원본 로그를 열었다.

| 정지됐다 돌아온 인스턴스의 재가입 로그 | ON | OFF |
| --- | ---: | ---: |
| `Successfully joined group` | 12 | 12 |
| **`MemberIdRequiredException`** | **0** | **12** |

OFF 쪽 문구가 이렇다 — `rebalance failed due to 'The group member needs to have a valid
member id before actually entering a consumer group.'` **12시간 soak test에서 본 그 예외다.**

#### 내 집계가 두 군데서 틀렸다

1. **엉뚱한 컨테이너를 셌다.** `storm_markers()`가 `telemetry-backend`만 봤는데,
   member id가 리셋되는 건 **정지됐다 돌아온 `storage-1`**이다.
2. **표식이 표식이 아니었다.** `already rebalancing`을 폭풍 신호에 넣었는데
   그건 **정상 리밸런싱에서도 찍히는 줄**이다. 양쪽 12건이 전부 그 줄이었고,
   진짜 신호는 세는 대상에서 빠져 있었다.

2026-09-06에 "결과는 이벤트가 아니라 증거 파일에서 읽는다"고 규칙을 세웠다. 그때는
이벤트 스트림을 잘못 읽었고, 이번엔 **내가 만든 집계를 잘못 믿었다.** 형태만 바뀌었다.
규칙을 "집계가 아니라 증거 파일에서 읽는다"로 다시 적어야 할 것 같다.

#### 그래도 폭풍은 재현하지 못했다

예외 12건이 나왔지만 **전부 정상적으로 재가입에 성공했다.** soak test에서 본 갇히는
상태는 안 나왔다. 인스턴스 하나를 한 번 정지시키는 것으로는 그 연쇄가 안 만들어지는
모양이다.

그래서 결론은 이렇게 적었다 — **"위험한 경로를 탄다"까지가 확인된 것이고
"그래서 갇힌다"는 여전히 미재현이다.** 절반을 채웠고 절반은 그대로 남았다.
기본값은 켜짐 그대로 둔다.

### 하루를 닫으며

어제와 오늘 이틀에 걸쳐 값을 낸 문장을 세어보면 이렇다.

- "측정한 45초가 설정 어디에도 없었다" — 동작이 있는데 설정이 없던 것
- "파티션을 늘려도 컨슈머는 5분간 못 본다" — 순서를 바꾸니 드러난 것
- "소유자가 있다 ≠ 소비되고 있다" — 내 계측이 먼저 걸린 함정
- "끌 방법 자체가 없었다" — 대조군을 만들려다 안 것
- "rpm 2000.7이 조용히 잘린다", "dtc null이 문자열 null이 된다" — 안 고치기로 한 것들
- "같은 20초가 한쪽에서는 아무 일도 아니다" — 대가를 재고서야 유지 판단이 근거가 된 것
- "정리를 안 하는 실험 스크립트는 다음 실행을 오염시킨다" — 마무리하다 밟은 것
- "집계가 아니라 증거 파일에서 읽는다" — 내가 만든 요약이 차이를 지우고 있던 것

**전부 "된다"가 아니라 "이렇게 안 된다" 또는 "이건 내가 틀렸다" 쪽이다.**
결과 표에 남는 건 앞의 숫자들이지만, 다음 세션이 실제로 쓸 건 이 문장들이다.

### 같은 날 현재 상태를 다시 감사하고 문서 역할을 나눴다

두 저장소의 원격 `main`, 코드·테스트·CI·원본 evidence를 다시 대조했다. 채용 포트폴리오
관점의 점수보다 중요하게 본 것은 **다음 작업이 실제 위험 순서로 정렬돼 있는가**였다.

checksum이 달라지는 문제로 정했다. 확장자 없는 `.prev_offsets`가 LF 고정 규칙 밖에 있어,

두 번째는 strict telemetry schema다. `rpm: 2000.7`, DTC null/comma뿐 아니라 숫자 필드가

하나의 위험으로 묶었다.

종합 결과는 `docs/current-state-audit-2026-09-09.md`에 남겼다. README의 40단계 표와 9월 4일
기준 ML 다음 작업 목록은 포트폴리오 첫 화면에서 걷어내고, 검증 영역 7개와 현재 P0/P1로
압축했다. 전체 이력은 이 devlog와 roadmap에 그대로 남는다. 741줄이 된 `CLAUDE.md`도
작업 일지 역할을 멈추고 데스크탑 인수인계, 검증 명령, 다음 작업 순서만 담도록 줄였다.
상세 역사는 없어지지 않았고 역할에 맞는 문서로 이동했다.

| --- | --- | --- |
| 세 개 전부 | `76cdfe49` / `87da0f68` / `388dd7ca` | **동일** |

**저장된 증거는 처음부터 옳았고, 깨뜨린 건 checkout 단계뿐이었다.** 이걸 확인 안 했으면
manifest를 다시 쓰거나 파일을 지웠을 텐데, 그건 기록을 바꾸는 것이다.
규칙(`.gitattributes`)만 고치니 evidence는 한 바이트도 안 건드리고 해결됐다.

#### 고치면서 같은 함정을 한 번 밟았다

자체 검증 결과를 `metadata.txt`에 덧붙이도록 짰다. 그런데 **`metadata.txt`는 manifest
안에 있다.** 한 줄만 더해도 그 파일 해시가 어긋난다 — 방금 고친 문제를 그대로 다시
만드는 코드였다. 커밋 전에 봐서 `checksum_selfcheck.txt`로 분리했다.

#### 남는 것

`.gitattributes`에서 확장자를 나열하고 있었다. `*.txt`, `*.csv`, `*.json`, `*.log`.
그 목록은 **새 파일 형태가 하나 생기는 순간 조용히 뚫린다.** 어제 내가 `.prev_offsets`를
만들 때 아무 경고도 없었고 커밋도 통과했다. 목록 대신 디렉터리 통째로 걸었다.

그리고 이 프로젝트 규칙에 한 줄이 는다 —
**증거는 "남겼다"가 아니라 "제3자의 clean checkout에서 다시 계산된다"여야 한다.**
어제까지 나는 앞의 절반만 하고 있었다.

### 표를 재려고 만든 도구가 앱과 다른 것을 재고 있었다

감사 P0-2는 "구현 전에 결정표와 실패 fixture부터 만들라"였다. 좋은 순서다 —
어제 나는 `rpm: 2000.7`을 보고 그 자리에서 "안 고친다"고 판단했는데,
**옆 칸들을 안 보고 내린 판단**이었다.

fixture 15건을 짜서 돌렸다. 14개가 통과하고 하나가 실패했다 —
"모르는 필드는 조용히 버려진다"가 아니라 **예외를 던졌다.**

원인은 앱 코드가 아니라 **내 테스트**였다. `new ObjectMapper()`는
`FAIL_ON_UNKNOWN_PROPERTIES`가 켜져 있고, Spring Boot의 자동 구성 매퍼는 그걸 끈다.
**즉 나는 운영과 다른 매퍼로 표를 만들고 있었다.** 그 한 칸이 어긋나 준 덕에 알았지
안 어긋났으면 열네 칸도 같이 의심했어야 한다.

어제 `session.timeout.ms` 계약 테스트에서 "테스트에 값을 다시 적으면 운영 설정을 못 잡는다"를
배웠다. 오늘은 **매퍼 자체**가 같은 함정이었다. 형태가 또 바뀌었다.
`JacksonAutoConfiguration`에서 실제 빈을 꺼내 쓰도록 고쳤다.

#### 표를 다 재고 나니 어제 판단이 무너졌다

| 이상 입력 | MQTT | Kafka 직접 | 저장되는 값 |
| --- | :---: | :---: | --- |
| `speed` 없음 / `null` | 통과 | 통과 | **0.0** |
| `gps.lat` 없음 | 통과 | 통과 | **lat=0** |
| 필드명 오타 `sped` | 통과 | 통과 | **speed=0.0** |

어제 나는 `rpm: 2000.7`과 `dtc [null]`을 **"값이 사라지지 않고 눈에 띄니 안 고친다"**로
닫았다. 그 근거가 여기서 무너진다. `lat=0, lng=127.65`는 **인도네시아 앞바다의 실재하는
좌표**다. 눈에 안 띈다. 필드명 오타 하나면 속도가 0이 되는데 아무 신호도 없다.

**판단 자체가 틀렸다기보다 판단의 범위가 좁았다.** 한 칸만 보고 "이 칸은 티가 난다"고
했는데, 티가 안 나는 칸들이 바로 옆에 있었다. 감사가 "표를 먼저 만들라"고 한 이유가 이거다.

#### 정책에서 한 가지를 분명히 했다

검증 범위를 정하다 보니 이상 감지와 부딪혔다. 엔진 온도 105도 초과가 이상 감지 룰인데
검증이 100도에서 막으면 **이상 데이터가 저장되지 않아 감지가 무의미해진다.**

그래서 원칙을 하나 세웠다 — **검증은 "물리적으로 불가능"만 막고, "비정상"은 이상 감지의
몫이다.** 검증 범위는 이상 감지 임계값보다 반드시 넓어야 한다. 이 원칙이 있으니
범위 값이 임의의 숫자가 아니라 역산 가능한 값이 됐다.

### 범위를 "역산했다"고 썼는데 역산이 아니었다

결정표를 쓰면서 검증 범위를 제안했다. 속도 -50~500, 온도 -60~300, 전압 0~60V.
근거는 "물리적으로 불가능한 값만 막고, 이상 감지 임계값보다 넓게"였고,
**"이 원칙 덕에 범위 값이 임의의 숫자가 아니라 역산 가능한 값이 됐다"**고 적었다.

지적을 받았다. **감지 임계값만으로 물리적 한계를 역산할 수는 없다.**
맞는 말이다. 나는 임계값 위에 여유를 얹어 **고른** 것이지 역산한 게 아니다.
500km/h가 왜 500인지 설명할 수 없다. 근거처럼 보이는 문장을 쓴 것이 문제다.

기준을 **OBD-II PID 표현 범위**로 바꿨다. speed는 PID 0D가 1바이트라 `0~255`,
rpm은 PID 0C가 2바이트를 4로 나눠 `0~16383.75`, 냉각수 온도는 PID 05가 1바이트에서
40을 빼서 `-40~215`. **물리적 한계가 아니라 장치가 만들 수 있는 값의 범위**이고,
실제 OBD-II 연동을 목표로 하는 프로젝트에서는 이게 더 정확한 계약이다.

원칙 문장도 고쳤다 — "물리적으로 불가능한 값 거부"가 아니라
**"입력 계약 밖의 값 거부, 계약 안의 이상치는 감지"**다.

#### `rpm`을 `Integer`로 바꾸려던 게 틀렸다

더 아픈 지적은 이거였다. OBD-II RPM은 **0.25 단위**라 `2000.25`가 유효한 값이다.
`2000.7 → 2000`의 문제는 "소수라서"가 아니라 **조용히 잘랐다**는 것이었는데,
나는 그걸 "정수 필드에 소수가 들어왔다"로 읽고 `Integer + @NotNull`을 계획했다.
**같은 방향으로 한 번 더 자르는 설계였다.**

확인해보니 근거가 하나 더 나왔다. **파이프라인의 나머지는 이미 전부 double이다** —
`toPoint()`도 응답 DTO도 `(double) getRpm()`으로 캐스팅한다.
**DTO의 `int` 하나가 유일한 축소 지점이었고, 거기서 자른 값을 다시 double로 넓혀
저장하고 있었다.** `Double`로 바꾸는 건 확장이 아니라 없어도 될 축소를 없애는 것이다.

#### 받아들이기 전에 우리 도구부터 쟀다

범위를 좁히는 변경이라 기존 실험이 깨질 수 있었다. 시뮬레이터를 열어봤다.

| | 값 | 새 계약 |
| --- | --- | :---: |
| 정상 주행 | speed 0~160, rpm 800~4500, temp 20~103 | 통과 |
| **이상값 주입** | temp 106~115, rpm 6100~7000, speed 201~230 | 통과 |
| 부하 도구 | speed 60~99, rpm 2000~2499 | 통과 |

**이상 감지용 주입값이 전부 새 범위 안에 든다.** 검증이 감지를 막지 않는다는 것을
말이 아니라 우리 코드로 확인했다.

다만 **속도의 여유가 25km/h뿐**이다(주입 최대 230 vs 상한 255). 시뮬레이터의 주입
상한을 올리면 그 메시지는 거부되어 감지에 도달하지 못한다. 제약으로 적어뒀다.

#### 남는 것

오늘 두 번 다 **"근거처럼 보이는데 근거가 아닌 문장"**에서 틀렸다.
아침에는 "증거를 남겼다"(재계산은 안 해봤다), 저녁에는 "역산했다"(고른 것이다).
둘 다 스스로는 안 걸렸고 밖에서 지적이 들어와서 걸렸다.
