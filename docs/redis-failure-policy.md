## 요약 — 지금 무엇이 정해졌나

| 결정 항목 | 결정 | 상태 |
| --- | --- | --- |
| 1. timeout 축소 | **2초** | 적용(§7-1) |
| 2. 일반 조회 rate limit | **fail-open** | 적용(§8-1) |
| 3. 진단 rate limit | **fail-closed** | 적용(§8-2) |
| 4. 로그인 보호 | **fail-closed 확정** | 유지 + 회귀 테스트(§8-3) |
| 5. refresh 토큰 실패 표현 | **명시적 503** | 적용(§7-2) |
| 6. health 지표 | **liveness/readiness 분리** | 적용(§8-4) |

**2번과 4번이 반대 방향인 것이 이 표의 요점이다.** 하나로 묶으면 조회를 살리려다
brute force 방어를 끄게 되고, 반대로 묶으면 Redis 하나로 모든 조회가 멈춘다.

**남은 것은 결정이 아니라 측정이다** — 지속 장애, 부하 중 장애, 스레드 고갈 임계,
fail-open 중 실제 남용 피해, 회로 차단기 필요 여부(§8-6).

## 0. 왜 조사부터인가

감사 문서(§5)는 "Redis가 중단되면 rate limit/brute-force interceptor 예외로 API가 500이
되고 refresh도 중단된다"고 적었다. **틀린 말은 아닌데 범위와 성질이 다르다.**

정책을 정하려면 **어느 엔드포인트가 무엇에 의존하고 실제로 어떻게 되는지**를 먼저 알아야
한다. 그러지 않으면 "fail-open이 낫다" 같은 결론을 근거 없이 내리게 된다.

## 1. Redis에 의존하는 지점 — 코드 전수

| 컴포넌트 | 무엇을 하나 | 적용 범위 | Redis 예외 처리 |
| --- | --- | --- | --- |
| `RateLimitInterceptor` | IP당 분당 요청 수 `INCR` | **`/api/**` 전체** (`/api/auth/login`만 제외) | **없음** |
| `DiagnosisRateLimitInterceptor` | 사용자·차량당 시간당 진단 횟수 | `/api/vehicles/*/diagnosis` | **없음** |
| `LoginRateLimiter` | IP+사용자당 분당 로그인 시도 | `AuthController.login` | **없음** |
| `BruteForceDetector` | IP 차단 판정·실패 누적·성공 시 해제 | `AuthController.login` | **없음** |
| `RefreshTokenService` | refresh 토큰 발급·회전·폐기 | `login` / `refresh` / `logout` | **없음** |

**다섯 곳 모두 try/catch가 하나도 없다.** `RedisConnectionFailureException`이 그대로
컨트롤러 밖으로 나가 500이 된다.

**인터셉터가 `/api/**` 전체에 걸려 있다는 것이 핵심이다.** rate limit은 "부가 기능"인데
지금은 **모든 API의 필수 경로**에 있다.

## 2. 실측 — 읽은 것과 다른 점이 둘 있었다

각 1회 측정(`measurement.txt`).

| 요청 | Redis 정상 | Redis 중지 | 지연 |
| --- | --- | --- | --- |
| `GET /actuator/health` | 200 | **503** | 60초 |
| `GET /api/vehicles` (인증) | 200 | **500** | 60초 |
| `GET .../anomalies` | 200 | **500** | 60초 |
| `GET .../diagnosis` | 404(데이터 없음) | **500** | 60초 |
| `POST /api/auth/login` | 200 | **500** | 60초 |
| `POST /api/auth/login` (오답) | 401 | **500** | 60초 |
| `POST /api/auth/refresh` | 200 | **500** | 60초 |
| `POST /api/auth/logout` | — | **500** | 60초 |
| `GET /api/vehicles` (미인증) | 403 | 403 | **5ms** |

### 2-1. 500이 아니라 **60초 뒤 500**이다

감사 문서에 없던 것이다. `application.yml`에 Redis `timeout`이 **없어서**
Lettuce 기본 command timeout(60초)이 걸린다.

**이게 정책 판단을 바꾼다.** 500은 클라이언트가 즉시 재시도하거나 실패 처리할 수 있지만,
60초 매달림은 **클라이언트 타임아웃·재시도 폭주·스레드 점유**를 연쇄로 만든다.
"Redis가 죽으면 기능이 안 된다"와 "Redis가 죽으면 서버가 느려진다"는 다른 문제다.

### 2-2. **로그인도 죽는다**

`WebMvcConfig`에서 `/api/auth/login`을 rate limit 인터셉터에서 제외했는데,
`AuthController`가 `LoginRateLimiter`·`BruteForceDetector`를 **직접** 부른다.
즉 인터셉터를 피해도 Redis에 닿는다. **Redis가 죽으면 아무도 로그인할 수 없다.**

### 2-3. 미인증 403만 빠르다

Spring Security가 인터셉터보다 앞에서 거절해 Redis에 안 닿는다.
**즉 "서버가 살아 있는지" 확인용으로는 쓸 수 있지만, 그게 API가 동작한다는 뜻은 아니다.**

### 2-4. WebSocket 실시간 경로는 Redis에 의존하지 않는다 — **코드 확인, 실측 안 함**

`grep`으로 확인한 것이다:

- WebSocket 관련 클래스(`WebSocketConfig`, `WebSocketAuthChannelInterceptor`,
  `WebSocketSessionRegistry`) **어디도 `RedisTemplate`을 쓰지 않는다.**
- STOMP 엔드포인트는 `/ws`이고 rate limit 인터셉터는 `/api/**`에만 걸린다 —
  **핸드셰이크가 인터셉터를 안 탄다.**
- WebSocket 인증은 JWT 서명 검증이라 상태가 없다(refresh 토큰만 Redis다).

**즉 Redis가 죽어도 실시간 스트림은 계속 흐를 가능성이 높다.** 다만 **실측하지 않았다** —
STOMP 클라이언트를 붙여 확인해야 "동작한다"고 쓸 수 있다.

이게 정책에 중요한 이유: **끊기는 것은 REST이고 실시간 화면은 살아 있을 수 있다.**
운영자가 "앱은 데이터가 흐르는데 조회는 500"이라는 상태를 보게 된다.

### 2-5. 복구는 자동 — 다만 시간은 관측마다 달랐다

`docker start` 후 **8초** 만에 로그인 200. Lettuce `ConnectionWatchdog`이 재연결한다.
**재기동이 필요 없다.** 이건 좋은 소식이고, 정책을 "장애 중 견디기"에 집중하게 한다.

**다만 같은 날 오후 측정에서는 30초였다**(§8-6 ③). **왜 다른지 재지 않았다** —
각 1회씩의 서로 다른 두 관측이 있을 뿐이고 "8~30초"라는 범위 주장도 못 한다.

### 2-6. 스레드 고갈 — **재지 않았다**

40개 동시 요청을 매달아 둔 상태에서도 미인증 403은 5~6ms였고 JVM 스레드는 152개였다.
Tomcat 기본 `max-threads`가 200이므로 **계산상 200 동시에서 고갈**되지만
**측정하지 않았다.** 40에서는 막히지 않는다는 것만 확인했다.

**"Redis 장애가 서버 전체를 멈춘다"고 아직 말하면 안 된다.**

## 3. 결정표 — 정해야 할 것

### 3-1. 전제: 세 가지를 같은 정책으로 묶으면 안 된다

| 기능 | Redis가 없으면 무엇을 잃나 | 성질 |
| --- | --- | --- |
| **일반 조회 rate limit** | 남용 방어 | **부가 기능** — 없어도 데이터는 정확하다 |
| **로그인 보호**(brute force, 로그인 rate limit) | 무차별 대입 방어 | **보안 통제** — 없으면 공격 창이 열린다 |
| **refresh 토큰** | 세션 연장·폐기 | **인증 상태 자체** — 없으면 토큰 회전이 불가능하다 |

세 번째가 특히 다르다. rate limit은 "안 세면 그만"이지만 **refresh 토큰은 Redis가
저장소다.** Redis 없이 통과시키면 **폐기된 토큰도 받아들이는** 것이 된다.

### 3-2. 결정 항목

| # | 질문 | 선택지 | 대가 |
| ---: | --- | --- | --- |
| 1 | **Redis timeout을 줄일까** — **(b) 2초로 확정, 적용함** | (a) 60초 유지 / (b) 1~2초로 축소 | (b)면 실패가 빨라져 스레드 점유가 줄지만, **일시적 지연에도 더 자주 실패**한다 |
| 2 | **일반 조회 rate limit** | (a) fail-closed(현재, 500) / (b) **fail-open**(제한 없이 통과) | (b)면 장애 중 남용 방어가 사라진다. 다만 남용은 인증된 사용자에 한정된다 |
| 3 | **진단 rate limit** | (a) fail-closed / (b) fail-open | 진단은 **비용이 드는 호출**일 수 있다. fail-open이면 장애 중 비용 폭증 가능 |
| 4 | **로그인 보호**(brute force) | (a) **fail-closed**(로그인 거부) / (b) fail-open(보호 없이 로그인 허용) | (b)면 **Redis를 죽이는 것이 brute force 방어를 끄는 방법**이 된다 |
| 5 | **refresh 토큰** — **(b) 확정, 적용함** | (a) 현재(500) / (b) 명시적 503 + 재로그인 유도 | 통과시키는 선택지는 **없다** — 저장소가 없으면 검증 자체가 불가능하다 |
| 6 | **health 지표** | (a) Redis DOWN → 전체 503(현재) / (b) Redis는 별도 표시 | (a)면 Redis 하나로 인스턴스가 교체 대상이 된다 |

### 3-3. 내가 기울어진 쪽과 근거 — **확정 아님**

**1번(timeout 축소)은 다른 결정과 독립적으로 이득이다.** 60초는 우리가 고른 값이 아니라
라이브러리 기본값이고, 그 값 때문에 "기능 실패"가 "서버 지연"으로 번진다.
다만 **얼마로 줄일지는 정상 구간의 Redis 응답 시간을 재고 정해야 한다.**
→ **쟀고 2초로 정했다**(§7-1).

**2번은 fail-open 쪽으로 기운다.** rate limit은 남용 방어인데, 그것 때문에 **정상 사용자의
모든 조회가 막히는 것**은 비용이 더 크다. 다만 fail-open으로 하면 **그 사실이 보여야 한다** —
지표와 로그로 "지금 제한이 안 걸리고 있다"를 남겨야 한다.

**4번은 fail-closed 쪽으로 기운다.** brute force 방어를 fail-open으로 하면
**Redis를 죽이는 것이 곧 방어를 끄는 방법**이 된다. 다만 그러면 Redis 장애 중
아무도 로그인 못 하는 것이 **의도된 동작**이 되므로, 그 사실을 명시적 503과 문구로
알려야 한다(지금은 정체불명의 500이다).

**2번과 4번이 반대 방향인 것이 요점이다.** "Redis 장애 시 fail-open" 하나로 묶으면
보안 통제를 끄게 되고, "fail-closed" 하나로 묶으면 조회까지 막힌다.

### 3-4. 결정이 필요했던 것 — **전부 답을 받았다(2026-09-12)**

1. ~~**2번과 4번을 갈라도 되나?**~~ → **갈랐다.** 조회 fail-open / 로그인 보호 fail-closed.
2. ~~**3번(진단 rate limit)은 어느 쪽인가?**~~ → **fail-closed.** 비용이 드는 호출이다.
3. ~~**1번 timeout 값**~~ → 정상 구간을 재서 **2초**(§7-1).
4. ~~**6번(health 지표 분리)**~~ → **분리했다.** liveness/readiness(§8-4).

구현과 측정은 §8.

## 4. 하지 않기로 미리 정한 것

- **Redis를 없애거나 대체하지 않는다.** 지금 문제는 의존 자체가 아니라 **장애 처리가
  없다는 것**이다.
- **인터셉터를 `/api/**`에서 떼지 않는다.** rate limit이 필요한 것은 맞다.
- **fail-open을 조용히 하지 않는다.** 어느 선택이든 그 상태가 지표·로그에 남아야 한다.
  P0-2b에서 만든 것과 같은 원칙이다 — 조용한 성공이 제일 나쁘다.

## 6. 이 조사의 한계

- **각 측정 1회.** `docs/evidence-policy.md` 기준 "그 조건에서 관찰됨"이다.
- **스레드 고갈은 미측정**(§2-6). 40 동시에서 안 막힌다는 것만 안다.
- **장애 지속 시간별로 안 봤다.** 중지 직후 재고 바로 복구했다 — 30/90초 실험은 미실행.
- **부하가 없는 상태**다. 실제 트래픽 중 장애는 다를 수 있다.
- **mTLS 프로파일에서 안 봤다.**
- **WebSocket이 장애 중 실제로 흐르는지 실측하지 않았다.** 코드로는 Redis 의존이 없다(§2-4).

§2의 표는 **적용 전** 상태다. 적용 후 재측정은 §7-4에 있고, 한계는 거기서도 같다 —
여전히 각 1회, 무부하, dev 프로파일이다.

## 7. 적용한 것 (2026-09-12)

> 측정: `load-test/redis-outage/evidence/20260912-115730/`

**결정이 필요 없는 것만 골라서 했다.** 3-4절의 세 질문(조회 fail-open, 진단, health 분리)은
사용자 판단이 필요해 손대지 않았다. 여기서 바꾼 것은 **거부의 표현과 대기 시간뿐이고,
누가 통과하는지는 하나도 바꾸지 않았다.**

### 7-1. Redis timeout 2초 — `application.yml`

```yaml
timeout: ${REDIS_TIMEOUT:2s}
connect-timeout: ${REDIS_CONNECT_TIMEOUT:2s}
```

값의 근거는 **잰 것**이다(`redis-normal-latency.csv`): 같은 호스트 컨테이너에서
`redis-benchmark -n 10000` p50 0.167~0.175ms, **max 0.687ms**.
2초는 그 max의 약 3,000배이므로 정상 요청을 자르지 않는다.

**환경변수로 뺀 이유**는 이 숫자가 **이 환경의 측정치**라서다. 네트워크가 끼는 배포에서는
다시 재고 올려야 한다 — 코드를 고치지 않고 바꿀 수 있어야 한다.

### 7-2. Redis 전용 503 — `GlobalExceptionHandler`

`DataAccessResourceFailureException`·`QueryTimeoutException`을 잡아
503 + `REDIS_UNAVAILABLE`로 응답한다. 전에는 `handleGeneral`로 떨어져 **정체불명의 500**이었다.

**500과 503의 차이는 문구가 아니라 대응이다.** 500은 "우리 코드가 깨졌다"라서
배포를 되돌릴 일이고, 503은 "의존 서비스가 없다"라서 그 서비스를 살릴 일이다.

### 7-3. `telemetry.redis.unavailable{route}` 지표

**fail-open을 나중에 도입하든 안 하든, 막힌 경로가 보여야 한다**(§4의 원칙).

라벨은 **경로 템플릿**이다 — `/api/vehicles/{vehicleId}/anomalies`. 실제 URI를 쓰면
시계열이 차량 수만큼 늘고, **Prometheus 라벨은 보존 기간 내내 남아** 차량 ID가
`docs/data-retention.md` 정책 밖에 남는다. P0-2b에서 정한 것과 같은 원칙이다.

### 7-4. 재측정 결과

| | 적용 전 | 적용 후 |
| --- | --- | --- |
| `/api/**` (인증) | 500 / **60초** | 503 `REDIS_UNAVAILABLE` / **2.01초** |
| `/api/auth/login` | 500 / 60초 | 503 `REDIS_UNAVAILABLE` / 2.01초 |
| `/actuator/health` | 503 / 60초 | 503 / **2.10초** |
| 미인증 403 | 5ms | 12ms (Redis 미경유, 그대로) |
| 복구 | 8초 | **8초** (변화 없음) |

지표는 다섯 경로에서 각각 올랐고 `{vehicleId}` 템플릿이 유지됐다.

### 7-5. 여기서 한 번 잘못 쟀다 — 기록

`docker compose build backend`의 출력을 `>/dev/null 2>&1 && echo "빌드 완료"`로 가렸다.
**빌드는 실패했는데 "빌드 완료"가 찍혔고**, 그대로 낡은 이미지를 재서
"고쳤는데 여전히 60초/500"이라는 결론을 잠깐 믿었다.

P0-2에서 이미 한 번 겪은 **낡은 이미지 함정**이 다른 얼굴로 돌아왔다 —
그때는 빌드를 **빼먹은** 것이고 이번엔 빌드 **실패를 가린** 것이다.
`measurement.txt`에 이미지 ID와 컨테이너의 이미지 ID를 나란히 남긴 이유다.

실제 실패 원인은 `MeterRegistry`를 생성자 필수 의존으로 건 것이었다 —
`@WebMvcTest` 슬라이스에는 Micrometer 자동 구성이 없어 컨트롤러 테스트 컨텍스트가
통째로 못 떴다. `ObjectProvider`로 바꾸고, 없으면 경고 로그 후 버리는 registry를 쓴다.
**지표 하나 때문에 예외 처리 전체가 사라지는 것은 맞는 교환이 아니다.**

### 7-6. 이 변경이 **닫지 않은** 것

- Redis가 죽으면 여전히 **모든 `/api/**`가 거부된다.** 빠르게 거부될 뿐이다.
- **스레드 고갈은 여전히 미측정.** 매달림이 1/30로 줄었으니 같은 유입에서 점유가
  줄어드는 것은 맞지만 **그건 계산이고 측정이 아니다.**
- 2·3·4·6번 결정은 그대로 열려 있다.

## 8. fail 정책 분기 적용 (2026-09-12 오후)

> 측정: `load-test/redis-outage/evidence/20260912-123533/`
> 결정: 사용자 확인 — 조회 fail-open / 진단 fail-closed / 로그인 보호 fail-closed / health 분리

§7이 **거부의 표현**만 고쳤다면, 여기서 처음으로 **누가 통과하는지**를 바꿨다.

### 8-1. 일반 조회 — fail-open (`RateLimitInterceptor`)

Redis에 못 닿으면 **세지 못한 채로 통과시킨다.** 근거는 비대칭이다 —
rate limit은 남용 방어인데, 그것 때문에 **정상 사용자의 모든 조회가 막히는 비용**이 더 크다.

**조용히 열지 않는다.** `telemetry.ratelimit.failopen{route}`를 올리고 WARN을 남긴다.
§4에 미리 적어둔 원칙이 여기 적용된다 — 조용한 성공이 제일 나쁘다.

두 가지를 일부러 안 했다:

- **`X-RateLimit-Remaining` 헤더를 붙이지 않는다.** 남은 횟수를 모르는데 숫자를 적으면
  클라이언트에게 거짓말이 된다.
- **`DataAccessException`만 fail-open한다.** 우리 코드의 NPE까지 삼키면
  **버그가 "장애 중 정상 통과"로 위장된다.** 테스트로 고정했다(`RateLimitFailOpenTest`).

### 8-2. 진단 — fail-closed (`DiagnosisRateLimitInterceptor`)

바로 옆 인터셉터와 **반대**다. 진단은 비용이 드는 호출이라 장애 중 무제한 허용이
비용 폭증이 된다. 조회는 막으면 정상 사용자 전체를 잃지만 진단은 잃는 것이 적다.

구현은 "아무것도 안 하는 것"이다 — Redis 예외를 **잡지 않고** 올려보내면
`GlobalExceptionHandler`가 503 `REDIS_UNAVAILABLE`로 바꾼다.
**여기에 try/catch가 들어오는 순간 조용히 fail-open이 되므로** `FailClosedPathsTest`가 막는다.

**같이 고친 것**: 카운터가 `null`일 때 429를 돌려주고 있었다. 429는 "한도를 다 썼다"는
뜻인데 **사실이 아니다** — 저장소가 답을 안 준 것이다. 이제 503으로 간다.

### 8-3. 로그인 보호 — fail-closed 확정

동작은 이미 fail-closed였다(예외가 그대로 전파). 바꾼 것은 **그게 우연이 아니게 만든 것**이다.
`LoginRateLimiter`·`BruteForceDetector`가 Redis 예외를 삼키지 않는다는 회귀 테스트를 넣었다.

fail-open이면 **Redis를 죽이는 것이 곧 brute force 방어를 끄는 방법**이 된다.
`isBlocked`가 장애 중 `false`를 돌려주면 차단된 IP가 풀리고,
`recordFailure`가 조용히 실패하면 실패 횟수가 안 쌓여 무제한 시도가 된다.

### 8-4. health — liveness / readiness 분리

| 경로 | 무엇을 답하나 | Redis 중지 중 |
| --- | --- | --- |
| `/actuator/health/liveness` | 프로세스가 살아 있나 — **재시작 판단** | **200, 8ms** |
| `/actuator/health/readiness` | 트래픽을 온전히 받을 수 있나 — **라우팅 제외 판단** | 503 |
| `/actuator/health` | 종합. 사람이 보는 용도 | 503 |

전에는 Redis 하나가 DOWN이면 `/actuator/health`가 503이었고, 오케스트레이터는 그걸
"고장난 인스턴스"로 읽어 **재시작**했다. **재시작해도 Redis는 안 살아난다** —
멀쩡한 인스턴스만 계속 죽이는 셈이다.

`show-details: never`라서 세 경로 모두 status 한 줄만 나간다. 내부 구성은 안 샌다.

### 8-5. 측정 결과 — 정책이 실제로 갈렸다

| 요청 | Redis 중지 중 |
| --- | --- |
| `GET /api/vehicles`, `.../anomalies` | **200** (2.01s / 2.12s) — 통과 |
| `GET .../diagnosis` | **503 `REDIS_UNAVAILABLE`** (4.02s) — 거부 |
| `POST /api/auth/login` | **503 `REDIS_UNAVAILABLE`** (2.01s) — 거부 |
| `/actuator/health/liveness` | **200** (8ms) |

### 8-6. **여기서 틀리기 쉬운 것 셋** — 읽는 법

**① `failopen`은 "통과한 요청 수"가 아니다.**
진단 요청은 인터셉터를 둘 탄다 — 일반 rate limit이 fail-open으로 통과시키고,
그 다음 진단 rate limit이 fail-closed로 거부한다. 그래서 `/diagnosis`는
**두 지표에 동시에 오른다.** 버그가 아니다.
정확한 뜻은 **"일반 rate limit이 적용되지 않은 요청 수"**이고,
그 요청이 최종적으로 어떻게 끝났는지는 이 지표가 말하지 않는다.

**② fail-open은 "빠르다"를 사지 않았다.**
통과는 하지만 **2초 걸린다** — Redis 호출이 timeout까지 매달리기 때문이다.
진단은 인터셉터를 둘 타서 **4초**다. 이걸 없애려면 실패 후 일정 시간 Redis를 건너뛰는
**회로 차단기**가 필요한데 **이번 범위에 넣지 않았다.**
**부하 중에는 이 2초가 스레드 점유로 바뀔 수 있고, 그건 여전히 미측정이다.**

**③ 복구 시간이 오전 측정과 달랐고 원인을 모른다.**
오전 8초, 오후 **30초**. 컨테이너 재기동 시간·저장 파일 적재·재연결 주기 중
무엇인지 **재지 않았다.** 각 1회라 범위 주장도 못 한다 — 서로 다른 두 관측이 있을 뿐이다.

### 8-7. 판단이 갈린 곳 하나 — `MeterRegistry`

`RateLimitInterceptor`에 `MeterRegistry`를 넣자 `@WebMvcTest` 슬라이스가 또 깨졌다
(§7-5와 같은 증상). 그런데 이번엔 **반대로 고쳤다.**

`GlobalExceptionHandler`는 `ObjectProvider`로 물러서게 했다 —
예외 처리는 지표가 없어도 살아야 한다. 반면 **fail-open 카운터가 없는 fail-open은
만들면 안 되는 물건이다**(제한이 조용히 사라진 상태를 아무도 모른다).
그래서 인터셉터는 빈이 없으면 **기동 단계에서 실패하게** 두고, 테스트가 운영과 같은
자동 구성(`MetricsAutoConfiguration`)을 올리게 했다.

**같은 증상이라고 같은 처방이 아니다** — 무엇이 없어도 되는지가 다르다.
