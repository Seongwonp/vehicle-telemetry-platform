## 2. 완료한 것과 증거

### 2-1. 오전 — Redis 운영 일관성 (정책 §9)

- **readiness에서 redis 제거** — 넣으면 프록시 도입 순간 fail-open 경로를 라우팅이 닫는다. `HealthGroupPolicyTest`.
- **401과 503 구분, fail-open 중 인증 유지** — 테스트 + 실측. 30초·90초 1회씩 — `RESULT_20260913_sustained_outage.md`.

### 2-2. 알림 지연 — 조사·개선·검증·**정책 결정** (`load-test/redis-outage/RESULT_20260913_alert_timing.md`)

- **원인(TSDB 원본 분해)**: `for: 1m`(60s) + 경로별 카운터가 첫 실패에서 생겨 첫 증가 누락(15~30s) + `[5m]` 창(해제 약 300s).
- **변경**: 합계 카운터 기동 시 0 등록 + `[1m]` + `for: 1m` 유지.
- **검증(각 1회)**: 실패 1건 — firing 없음 / 30초 — firing 평가 1회, **발송 0건** / 90초 — 실패 중 firing(+70.6s), 해제 마지막 증가 뒤 53s.
- **결정(§7-4, 정책 §10-4)**:
  1. 짧은 장애(실패 1건·30초 수준) 미발송을 **수용**. 이력 알림 추가 안 함 — 카운터·대시보드·로그·`ALERTS` 이력으로 조회.
  2. 두 알림은 **"요청 처리에서 관찰한 Redis 영향" 알림**. Redis 가용성 감시·장애 지속 시간 측정으로 표현하지 않는다.
  3. **Alertmanager `group_wait`·`group_interval` 유지.**
- **90초 수신 시각 연결(§6-4, 기존 증거만)**: firing 수신 새 규칙 +115.5s / 기존 +152.5s·+119.7s — **세 번 모두 Redis PONG(+91.7~91.9s) 뒤**.
  앱 경로 회복(+124.3~124.4s)보다는 8.9s 전·4.6s 전·**28.1s 뒤**. 90초에서도 firing 수신이 앱 회복 뒤일 수 있다. resolved 수신은 회복 뒤 약 291~595s.

### 2-3. 회복 지연 반복 (`load-test/redis-outage/RESULT_20260913_recovery_repeat.md`)

- 30초·90초 **각 3회**(같은 이미지, 무부하). 앱 경로 회복: 30초 +4·+24·+6초, 90초 +25·+34·+34초. Redis는 매번 약 1.5초에 응답.
- **6회에서 앱 회복이 Lettuce `Reconnected` 로그와 겹쳤고, 재연결 대기가 지연의 주요 후보** — 원인 확정 아님.
- 재연결 간격 상한 30초 근거: runtimeClasspath `lettuce-core 6.3.2.RELEASE`의 `Delay.exponential()` 기본 상한 `Duration.ofSeconds(30)`(`javap`로 확인), 앱 설정 없음.
  컨테이너 안 jar는 직접 열지 않았다.
- DNS 실패는 **개별 시도의 실패 사유**로만 기록(6회 중 4회, 1회는 캐시 추정). 전체 지연 설명으로 일반화하지 않는다.

### 2-4. 감지기 DLQ 재처리 횟수 헤더 (`load-test/dlq-replay-count/RESULT_20260913_replay_count.md`)

- 실제 Kafka 전용 토픽·그룹: 수정 전 `(없음)×3`·차단 안 됨(FAIL) → 수정 후 `(없음)→1→2`·3회차 차단(PASS). 각 1회.
