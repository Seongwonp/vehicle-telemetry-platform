## 2. 실험 D3 요약 (1회, `docs/verification/2026-10-01-mqtt-ack-boundary.md`)

Kafka 76.5초 `pause` 중 연결 단절(dynsec), 연속 유입 약 2.7건/초 540건.
- 유실 0(PUBACK 540 = Kafka 고유 540 = InfluxDB 540), 중복 3. 재접속 단절 +11.9초(Kafka 정지 중), 대조 단절 1.30초.
- `MqttAckWaitStuck`은 **예측대로 안 떴다**(최대 elapsed 27.45초) — 첫 대기는 delivery timeout 30초로 spool에서 끝났고, 그 뒤엔 spool 백로그 경로라 대기가 1초 미만. 이 알림은 "producer 상한이 깨진 대기"를 잡는 것이지 D2식 늦은 단절 인지나 긴 Kafka 장애 자체를 잡지 않는다.

## 3. 결정 대기

1. **D3에서 찾은 결함 후보 — 연결 끊김 인터럽트가 동기 spool 쓰기에 닿는다.** 백로그 경로에서 Paho 콜백 스레드가 spool 파일을 쓰는 중에 인터럽트가 오면 `ClosedByInterruptException` → 그 메시지는 ACK 안 됨 → 재전달로 1회 저장(유실 없음). 타이머는 `interrupted`가 아니라 `failed`로 센다. `backend-spool` 볼륨에 **0바이트 `.tmp` 파일 1개**가 남았다(드레인은 `.json`만 읽어 무해, 정리 주체 없음, 증거라 지우지 않음). 선택지: (a) spool 쓰기를 인터럽트 불가 구간으로(인터럽트 플래그를 잠시 비우고 복원) (b) 실패 시 `.tmp` 삭제만 추가 (c) 수용·기록.
2. **D3 관찰** — producer가 "Expiring … 30007 ms"로 보고한 레코드가 실제로 Kafka에 써졌다(offset 3567) → spool 사본 2개와 합쳐 3중 기록, InfluxDB가 흡수. timeout은 "안 보냈다"가 아니다. 문서화만 했다.
3. **실험 데이터 삭제 범위** — `docs/experiment-data-inventory.md`를 보고 결정. 특기: MQTT 영속 세션 `telemetry-backend-g1`·`-g2`는 `vehicle/telemetry/#` 구독을 쥔 채 오프라인이라 **큐가 계속 자라는 것으로 추정**(상한 100,000). `-g1-sys`·`-g2-sys`도 남아 있다(문서에 없던 것). SESSLOSS-G2 행이 실험 기록(523)과 달리 지금 900. 오늘 추가된 행: `RECON-D3` 540·`RECON-D3Z` 5·`OPTF-E2E` 3(+알림 1).
4. **비활성 계정 처리** — `qa-admin`·`qa-user`는 삭제하지 않고 비활성. `qa-user`는 SIM-002 소유자라 FK 때문에 단독 삭제 불가.
5. **에이전트 도구 출력 노출 1건** — ① 에이전트가 백엔드 env 확인 중 필터 실수로 `MQTT_TLS_STORE_PASSWORD` 값을 자기 도구 출력에 한 번 찍었다(파일·증거엔 없음). dev 키스토어 기본값으로 보인다. 교체 여부 결정.
6. **atlas-dev 컨테이너가 `Exited (255)`** 상태다(이 세션 작업 시작 뒤 약 45분 전 시점, 다른 compose 프로젝트 `atlas_docker_env`). 건드리지 않았다 — 이 저장소 작업이 원인인지 확인하지 않았다.
