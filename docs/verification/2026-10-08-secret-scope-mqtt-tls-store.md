# `MQTT_TLS_STORE_PASSWORD` 사용 범위 확인 — 2026-10-08

계기: 2026-10-08 ① 작업 서브에이전트가 백엔드 컨테이너 env를 확인하다 필터 실수로 이 변수의 값을 **자기 도구 출력에 한 번** 찍었다(파일·증거·커밋엔 없음).
확인은 값을 출력하지 않고 **동일성 비교(예/아니오)와 참조 위치**로만 했다.

## 결론

**로컬 dev 전용 기본값이고, 저장소에 이미 공개된 문자열과 같다. 긴급 교체는 필요 없다**(근거와 단서는 아래 — 2차 리뷰로 보강). 보호 대상은 이 PC에서 자체 서명 CA로 만든 개발용 인증서·키이며
실제(공인·운영) 인증서가 아니다. 다만 같은 값이 공개 저장소의 기본값이므로 **이 keystore를 dev 밖에서 쓰면 안 된다**(아래 권고).

## 확인 항목

| 질문 | 확인 방법 | 결과 |
| --- | --- | --- |
| 실행 중이던 값은 어디서 왔나 | 컨테이너 env 값과 각 기본값을 셸 안에서 `=` 비교, 결과만 출력 | 루트 `.env`에 이 변수 **없음**(`grep -c` = 0). 컨테이너 값 = `docker-compose.yml`의 `${MQTT_TLS_STORE_PASSWORD:-…}` 기본값 = `broker/certs/generate-certs.sh` 기본값 = `application.yml`의 Spring 기본값(전부 같음). CI 값(`ci-mqtt-password`)과는 다름 |
| 다른 환경에서도 쓰나 | 저장소 전체 참조 검색 | 참조는 `docker-compose.yml`·`application.yml`·`MqttConfig`·`generate-certs.sh`·`.env.example`(같은 기본 문자열)·CI뿐. **배포 설정(k8s·클라우드·원격 호스트) 없음.** CI는 자기 값으로 인증서를 새로 만든다 → 이 값을 쓰는 곳은 로컬 dev 스택뿐 |
| 무엇을 보호하나 | `openssl x509 -noout -subject -issuer -dates`(공개 정보만) | `broker/certs/backend.p12`(백엔드 클라이언트 인증서 + 개인키, CN=telemetry-backend)와 `truststore.p12`(CA 인증서). 발급자 `CN=TelemetryCA`, **자체 서명 CA**, 2026-09-05 생성, 10년 유효 |
| keystore·개인키는 어디 있고 누가 접근하나 | `git ls-files`, `git check-ignore`, `git log --all`, 키 파일 첫 줄, compose 마운트 | `broker/certs/*.p12`·`*.key`는 `.gitignore` 대상이고 **커밋 이력에 한 번도 없다**(로컬 파일만). **같은 디렉터리의 개인키 103개(`ca.key`·`server.key`·`backend.key`·`vehicles/*.key`)는 전부 암호화되지 않은 PKCS#8**(`BEGIN PRIVATE KEY`)이다. ~~이 비밀번호는 사실상 아무것도 막지 않는다~~ — **정정(같은 날)**: 비밀번호는 `backend.p12`라는 **한 경로**의 보호이고, 평문 PEM은 그와 **별개의 읽기 경로**다. 같은 디렉터리를 읽을 수 있는 주체에게 PEM 경로가 열려 있었다는 뜻이지 비밀번호가 무의미하다는 뜻이 아니다. 그 디렉터리 노출이 문제였다. (확인 당시) `./broker/certs` 전체가(**CA 개인키 포함**) mosquitto·backend·backend-storage-1/2/3·simulator **6개 서비스**에 읽기 전용 마운트돼 있었다 → **같은 날 서비스별 필요 파일만 마운트하도록 바꿨다. `ca.key`를 읽을 수 있는 컨테이너는 0개**([`2026-10-08-cert-access-scope.md`](2026-10-08-cert-access-scope.md)). 이 PC 로컬 계정은 여전히 접근 가능 |
| 값 자체가 비밀이었나 | 위 동일성 비교 | 아니다 — 공개 저장소(GitHub `PUBLIC`)에 커밋된 기본값과 같은 **공개 문자열**이다. 노출 전후로 알려진 정보가 늘지 않았다 |

## 단서 — "로컬 dev 전용"의 실제 경계 (2차 리뷰 반영)

- **(확인 당시) 8883(mTLS)은 모든 인터페이스에 열렸다** — 같은 날 기본을 `127.0.0.1`로 바꾸고 `MQTT_TLS_BIND`로만 연다([`2026-10-08-cert-access-scope.md`](2026-10-08-cert-access-scope.md)). **정정: LAN에서 닿는다는 사실만으로는 키 유출의 근거도, 재발급의 근거도 아니다** — 이 리스너는 CA가 서명한 클라이언트 인증서 없이는 접속을 거부한다(같은 문서에서 인증서 없는 접속이 `peer did not return a certificate`로 끊기는 것을 확인). 노출 범위가 문제가 되는 것은 **키가 이미 새어 나갔을 때 그 키를 쓸 수 있는 곳이 넓어진다**는 점이다. 원문: `docker-compose.yml` 123행 `"${MQTT_TLS_PORT:-8883}:8883"` — dev 평문 1883은 `127.0.0.1`에만 묶이지만 8883은 아니다. 이 CA를 신뢰하는 브로커가 **같은 LAN에서 닿는다.** 공유망(학교·카페)에서 스택을 띄우면 dev 키를 가진 사람은 차량으로 접속할 수 있다.
- **도구 출력은 이 PC 밖으로 나간다**: 10-08 비밀번호(공개 기본값)와 10-07 차량 키 일부 줄은 에이전트 도구 출력에 찍혔고, 그 출력은 모델 API로 전송된다(학교 게이트웨이 운영자가 그 트래픽을 볼 수 있다는 메모가 있다). "파일로 복사되지 않았다"는 디스크 기준일 뿐이다.
- 10-07에 **완전한** 차량 키가 찍혔는지는 확인하지 못했다 — 그 에이전트의 대화 기록 파일을 이 세션에서 더 이상 읽을 수 없었다(크기 0). 보고는 "몇 줄"이었다.

## 관련 노출 (같은 범주)

- 2026-10-07 obd-bridge 서브에이전트가 범위 없는 grep으로 `broker/certs/vehicles/*.key` 일부 줄을 **자기 도구 출력에** 찍었다(10-07 보고). 이것도 같은 자체 서명 CA의 **개발용 차량 키**다. 디스크의 다른 파일로 복사되지는 않았다(도구 출력 전송은 위 단서).
- 이 확인 과정에서도 Spring 기본값 비교 줄이 그 공개 기본 문자열을 출력에 포함했다(`application.yml`에 이미 있는 값). 이후 출력은 설정 여부·참조 위치만 쓴다.
