# 검증 증거 정책

## 목적

Telemetrix에서 “검증했다”는 표현은 코드가 그럴듯하거나 테스트 명령을 적어둔 상태를
뜻하지 않는다. 실행 환경과 입력, 원본 결과가 남아 있고 다른 사람이 같은 판단을 다시
계산할 수 있을 때만 사용한다.

## 검증 상태

| 상태 | 사용할 수 있는 조건 |
| --- | --- |
| `미검증` | 코드·문서만 존재하거나 필요한 환경에서 실행하지 않음 |
| `컴파일 검증` | 컴파일 또는 정적 분석만 성공하고 동작은 실행하지 않음 |
| `부분 검증` | 한 조건·한 환경·1회 실행 등 제한된 범위에서 결과를 확인 |
| `검증 완료` | 미리 정한 범위와 성공 기준을 충족하고 재현 자료를 보존 |
| `회귀 검증` | 발견한 결함을 자동 테스트로 고정하고 CI에서 반복 실행 |

`검증 완료`는 모든 환경에서 안전하다는 뜻이 아니다. 문장에는 항상 부하, 장애 시간,
인스턴스 수, 실행 횟수 같은 적용 범위를 함께 쓴다.

## 필수 메타데이터

모든 검증 결과에는 다음을 기록한다.

- 실행 날짜와 timezone
- Git branch와 정확한 commit SHA
- OS, CPU/메모리처럼 결과에 영향을 주는 환경
- Java/Gradle, Python, Docker/Compose 등 주요 버전
- 실행한 명령 원문
- 입력 조건: 차량 수, 발행 간격, 실행·장애·복구 시간
- 변경한 설정과 기본값과의 차이
- 성공 기준과 실제 판정
- 알려진 한계와 이번 결과가 적용되지 않는 범위

## 원본 증거

요약 Markdown만으로 끝내지 않는다. 가능한 경우 아래 자료를 함께 보존한다.

- 테스트 XML 또는 JUnit/pytest 원문 출력
- 시뮬레이터의 queued/confirmed(PUBACK) 집계
- Kafka topic end offset, Consumer Group committed offset와 lag
- InfluxDB point 수와 PostgreSQL row/고유 event_id 수
- Prometheus query 결과와 핵심 메트릭 스냅샷
- 장애 주입 및 복구 시각이 포함된 서비스 로그
- 집계에 사용한 CSV/JSON과 계산 스크립트

대용량 로그를 Git에 그대로 넣지는 않는다. 필요한 구간을 비밀정보 제거 후 압축하거나,
외부 보관 위치와 checksum을 결과 문서에 기록한다. 토큰, 비밀번호, 개인 인증서와 `.env`
내용은 증거에 포함하지 않는다.

권장 디렉터리 형태:

```text
load-test/<scenario>/
├── README.md                    # 실행 방법
├── run_scenario.sh              # 자동화
├── RESULT_YYYYMMDD_<name>.md    # 판단과 한계
└── evidence/<run-id>/           # 작고 안전한 원본 자료
    ├── metadata.txt
    ├── metrics.json
    ├── counts.csv
    └── checksums.txt
```

## 정합성 검증 규칙

단일 카운터를 정답으로 사용하지 않는다. 실패 지점에 따라 독립적인 기준을 선택한다.

| 장애 위치 | 우선 기준 | 대조 대상 |
| --- | --- | --- |
| MQTT broker 이전/중단 | simulator PUBACK | broker 수신, backend 수신 |
| MQTT → Kafka | backend MQTT 수신 | Kafka topic end offset |
| Kafka → InfluxDB | Kafka 고유 원본 | InfluxDB 고유 point |
| anomaly detector | telemetry 입력·고유 event_id | alert topic과 detector lag |
| Kafka → PostgreSQL | alert topic 고유 event_id | PostgreSQL row와 duplicate 지표 |
| consumer 재시작 | 종료 시 committed offset | 재시작 처리량과 최종 저장량 |

카운터가 프로세스 재시작으로 초기화되는지, metric이 시도 시점인지 성공 시점인지 먼저
확인한다. `lag=0`만으로 저장 성공을 판단하지 않는다.

## 반복과 수치 표현

- 1회 실험은 “해당 조건에서 관찰됨”으로만 표현한다.
- 안정성 주장은 최소 3회 반복하고 각 회차 값을 공개한다.
- 평균과 함께 최소·최대, 실패 횟수와 최악값을 기록한다.
- 처리량은 측정 구간과 warm-up/drain 포함 여부를 적는다.
- `약`, 반올림, 추정값은 계산식과 원본 값을 함께 남긴다.
- 변경 전후 비교는 가능한 한 같은 부하·환경·측정 도구를 사용한다.

## 주장별 최소 증거

| 주장 | 최소 증거 |
| --- | --- |
| “유실이 없다” | 입력 고유 수와 최종 저장 고유 수 일치, DLQ/spool 잔여 대조 |
| “멱등하다” | 동일 event 재전달 후 저장 행 증가 0과 내용 일치 |
| “순서가 보장된다” | 차량별 sequence/timestamp 역전 수 측정과 적용 경계 |
| “장애가 격리된다” | 한 Consumer Group 장애 중 다른 경로의 처리량·lag·오류율 |
| “복구된다” | 장애 제거 후 lag/spool/DLQ가 정해진 절차로 해소되고 정합성 일치 |
| “성능이 개선됐다” | 동일 조건의 전후 처리량, p95/p99, 오류율, 자원 사용량 |
| “CI에서 검증된다” | 해당 commit의 workflow 링크와 실제 실행된 테스트 수·skip 수 |
| “고가용성이다” | 다중 인스턴스/복제 환경의 failover와 복구 목표 실측 |

## 결과 문서 검토 체크리스트

- [ ] 주장과 수치가 원본 자료에서 다시 계산된다.
- [ ] 실패와 skip을 성공 수에 포함하지 않았다.
- [ ] 측정 도구 자체의 병목과 파싱 오류를 확인했다.
- [ ] 재전달과 중복 저장을 구분했다.
- [ ] 저장 시도와 저장 성공을 구분했다.
- [ ] 정상 종료와 강제 종료를 구분했다.
- [ ] 결과를 단일 머신 밖으로 과장하지 않았다.
- [ ] 예상과 달랐던 결과와 실패한 튜닝도 남겼다.
- [ ] 비밀정보와 개인정보가 제거됐다.
- [ ] 남은 미검증 항목이 다음 Issue 또는 명시적 위험 수용으로 연결됐다.

## 포트폴리오 표현 원칙

“완벽히 보장”, “무손실 시스템”, “고가용성 아키텍처”처럼 범위를 숨기는 표현을 피한다.
대신 조건과 증거가 드러나는 문장을 사용한다.

- 피할 표현: “Kafka로 데이터 유실을 완전히 방지했다.”
- 권장 표현: “200대·약 1,700 msg/s의 단일 Docker Compose 환경에서 Kafka 180초
  중단 후 spool을 드레인했고, Kafka 원본 수와 InfluxDB 최종 point 수가 일치했다.”
- 피할 표현: “중복을 제거했다.”
- 권장 표현: “리밸런싱에서 40건이 재전달됐지만 `event_id` 고유 제약으로 PostgreSQL
  행은 증가하지 않았고 신규 저장에만 알림을 발행했다.”
