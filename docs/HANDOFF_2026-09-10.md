### 2-3. 다음 작업 후보 — **둘 다 조사부터 시작한다**

**후보 A. Redis 장애 정책** (감사 실행 순서 3번, P1)

- 현재 위험: Redis가 중단되면 rate limit / brute-force interceptor 예외로 **API가 500**이 되고
  refresh도 중단된다(감사 §5, README 장애 시나리오 5).
- **먼저 할 일은 정책 결정이 아니라 현재 동작 조사다.** 어느 endpoint가 Redis에 의존하고,
  Redis가 죽었을 때 각각 실제로 어떻게 되는지(500인지, 통과인지, 어디서 예외가 나는지)를
  **재서 표로 만든 뒤** 정책안을 쓴다. 그다음이 30/90초 장애 실험이다.
- 결정이 필요한 지점(조사 뒤에 사용자에게 물을 것):
  **인증·refresh와 일반 조회를 같은 정책으로 묶을지**, 그리고 rate limit이 못 도는 동안
  **열어둘지(fail-open, 가용성) 막을지(fail-closed, 보안)**.
  이건 가용성과 보안의 트레이드오프라 조사 결과를 놓고 정해야 한다.
- **"결정이 필요하다"는 이유로 뒤로 미룰 항목이 아니다.** 조사와 정책안 작성까지는
  결정 없이 진행할 수 있고, 오히려 그게 결정을 가능하게 만든다.

**후보 B. 이벤트 상관관계 (`event_id`)** (감사 실행 순서 4번, P1)

- 현재 위험: HTTP MDC traceId만으로는 MQTT→Kafka→InfluxDB/Python→PostgreSQL→WebSocket
  한 레코드를 잇기 어렵다(감사 §5).
- 이번 세션이 절반을 만들어뒀다 — DLQ 헤더에 `origin-topic/partition/offset`,
  `x-dlq-contract-reason`, `x-dlq-source-path`가 실리고, 이상 알림의 `event_id`가
  **원본 다섯 필드에서 결정적으로** 나온다는 것을 확인했다(`detected_at`은 키에 없다).
- **다만 텔레메트리 원본에는 식별자가 없다.**
- 먼저 할 일: 지금 어느 단계에 어떤 식별자가 있는지(HTTP traceId, `event_id`, DLQ 헤더,
  MQTT packet ID) 조사해 표로 만들고, 한 레코드를 5단계에서 이으려면 무엇이 빠졌는지 정리.

**추천을 하나로 확정하지 않는다.** 둘 다 조사부터 시작할 수 있고, 어느 쪽이든
"조사 → 결정표 → 정책 확정 → 구현" 순서다. 굳이 고르자면 **A(Redis)가 위험 등급이 높다** —
지금도 Redis가 죽으면 API가 500이 되는 상태이기 때문이다. B는 조사 재료가 더 쌓여 있다.
**사용자에게 어느 쪽을 할지 물어보고 시작하라.**

## 3. 이번 세션 보고에서 바로잡을 것

내가 보고에서 단정했다가 지적으로 고친 것들이다. **다음 세션이 이 문장들을 근거로
쓰지 않도록** 여기 남긴다.

### 3-1. `No data`는 "미발생"의 증거가 아니다

내가 "실패·불명이 `No data`인데 `status=success`이므로 그 기간에 실패가 없었다는 뜻"이라고
썼는데 **틀렸다.**

`No data`가 뜻하는 것은 **"해당 조회 조건에서 시계열/표본 없음"**뿐이다.
같은 결과가 나오는 원인이 여럿이다 — 실제 미발생, **수집 누락**(`up == 0`, 스크레이프 실패),
**시계열 미생성**(그 라벨 조합으로 한 번도 안 오름), **조회 구간 문제**
(`rate()` 창보다 표본이 적음, 시간 범위 밖), 인스턴스 재기동에 의한 초기화.

**미발생 여부는 수집 상태와 함께 확인해야 한다.**

고친 곳: 대시보드 패널의 `noValue` 문구와 "읽는 법" 패널,
`docs/rejection-metrics-design.md` §6-1.

**주의**: 이미 커밋된 증거 파일
`load-test/schema-contract/evidence/20260909-P0-2b-metrics/grafana-verification.txt`에는
"그 기간에 실패가 없었다는 뜻이다"라는 **옛 서술이 그대로 남아 있다.**
증거 파일은 지우거나 고치지 않는다(실험 규칙 7·8) — 대신 이 문단이 정정이다.
그 파일을 인용할 때는 이 §3-1을 같이 읽어라.

### 3-2. Grafana는 **쿼리 검증**만 했다 — 화면은 안 봤다

Grafana **데이터소스 프록시로 PromQL을 실행**해 결과를 받았고, 대시보드 프로비저닝과
패널의 datasource 해석을 API로 확인했다. **브라우저에서 화면을 열어본 것은 아니다.**

**"렌더링 검증 완료"라고 쓰지 마라.** 범례 겹침, 축 스케일, 색, 텍스트 패널의 마크다운
표시 같은 것은 **미확인**이다.

다만 이 확인이 값을 냈다 — 패널이 **존재하지 않는 datasource uid**(`"prometheus"`)를
지정하고 있던 것을 잡았다(실제 uid는 `PBFA97CFB590B2093`, 기존 패널들은 datasource를
생략해 기본값을 쓴다). JSON 문법 검사만으로는 안 걸렸을 결함이다.

### 3-3. 시도·성공 rate의 미세한 차이 — **원인 미확정**

`발행 시도` 0.04354 vs `성공 확인` 0.04358이었다. 내가 "rate 창 차이"라고 썼는데
**검증하지 않았다.** 그럴듯한 설명이지 측정이 아니다.

**원인 미확정으로 둔다.** 알아야 한다면 같은 시각의 raw counter
(`telemetry_kafka_dlq_publish_attempts_total`, `_published_total`)를 직접 비교해야 하고
그건 안 했다. **차이를 유실이나 미격리로 읽지 마라.**

### 3-4. `event_id` 도입은 MQTT 거부의 고유 식별을 **보장하지 않는다**

내가 "4번(이벤트 상관관계)을 하면 MQTT 고유 건수 한계가 닫힌다"고 썼는데 **과했다.**

payload에 `event_id`를 넣으면 **유효한 ID를 가진 메시지**의 상관관계는 좋아진다.
그러나 **모든 MQTT 거부 입력을 고유 식별할 수는 없다** —

- **JSON이 깨진 입력**은 애초에 파싱이 안 되므로 그 안의 ID를 읽을 수 없다.
- **`event_id` 자체가 누락되거나 형식이 틀린 입력**도 마찬가지다.
- 발행 측이 ID를 **중복**해서 보내는 경우도 우리가 막을 수 없다.

즉 `event_id`는 **개선**이지 완결이 아니다. 거부 입력 중 상당수는 성질상 식별자가 없다.

여전히 유효한 것: payload 해시(같은 차량이 같은 밀리초에 같은 값을 보내는 정상 상황을
하나로 접는다)와 MQTT packet ID(세션 안에서만 유일, 재연결 시 재사용)를 **고유 이벤트
ID로 쓰지 않는다**는 결정.

## 6. 이번 세션에서 반복해서 값을 낸 것

다음 세션이 같은 함정을 밟지 않도록.

- **검사를 추가한 뒤 그게 무는지 확인하지 않으면, 추가했다는 사실 자체가 미검증 주장이다.**
  이번에 네 번 걸렸다 — Gradle이 fixture를 입력으로 몰라 테스트를 건너뛴 것,
  Git Bash의 `python`이 스텁이라 빈 파일을 만든 것, 작업 트리만 보는 checksum 검사,
  존재하지 않는 Grafana datasource uid.
- **판정이 PASS를 돌려주는 것과 그 PASS가 옳은 것은 다르다.** E2E 2회차에서 15칸이
  PASS였는데 6칸이 거짓이었다(차량 ID 길이 때문에 거부됨).
- **읽은 것과 잰 것은 다르다.** offset 동작을 코드로 읽어 정리했다가 실제로 재보니
  기대가 틀렸다(실제가 더 안전했다).
- **실패를 주입할 때는 나머지가 운영과 같아야 한다.** 드라이버 producer에 직렬화기를
  빼먹었더니 `TypeError`가 "알림 발행 실패"로 잡혀 엉뚱한 경로를 쟀다.
