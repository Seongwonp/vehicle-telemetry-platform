# GitHub Issue 작성 가이드

## 목적

Issue는 기능 희망 목록이 아니라 문제 정의, 가설, 검증 결과를 연결하는 작업 기록이다.
한 Issue는 가능하면 하나의 질문만 다룬다. 구현이 끝났다는 이유만으로 닫지 않고 미리
정한 완료 조건과 증거가 충족됐을 때 닫는다.

## 권장 라벨

| 라벨 | 용도 |
| --- | --- |
| `reliability` | 유실, 중복, 순서, offset, 멱등성 |
| `experiment` | 부하, 장애 주입, 복구, soak test |
| `observability` | 로그, 메트릭, 대시보드, 알림 |
| `security` | 인증·인가, TLS, 비밀정보, 공격 시나리오 |
| `app` | Flutter UX, 연결 상태, 접근성, 앱 E2E |
| `docs` | README, ADR, Runbook, 검증 기록 |
| `blocked` | 외부 장비나 환경이 없어 진행할 수 없음 |

우선순위는 `P0`, `P1`, `P2` 중 하나만 붙인다. 기술 이름만으로 라벨을 과도하게
늘리지 않는다.

## 제목 규칙

결과를 미리 단정하지 말고 검증할 위험이나 질문을 쓴다.

- 좋은 예: `[Reliability] spool 복구 중 차량별 순서 역전 측정`
- 좋은 예: `[Experiment] storage consumer 강제 종료 정합성 3회 반복`
- 피할 예: `Kafka 고도화`
- 피할 예: `성능 개선`
- 피할 예: `MSA 적용`

## 본문 템플릿

```markdown
## 문제

무엇이 위험하거나 아직 검증되지 않았는가?

## 현재 증거

- 코드/설정:
- 기존 테스트/결과:
- 현재 수치:
- 검증 상태: 미검증 | 부분 검증 | 검증 완료

## 가설

어떤 조건에서 어떤 결과가 나올 것으로 예상하는가?

## 범위

- 포함:
- 제외:

## 실험 또는 구현 방법

1.
2.
3.

## 성공 기준

- 정합성 불변식:
- 허용 가능한 수치:
- 실패로 판정할 조건:

## 수집할 증거

- commit SHA와 실행 환경
- 실행 명령과 원본 로그
- Kafka offset/lag/topic count
- DB row 또는 point count
- p95/p99 지연과 복구 시간(해당하는 경우)

## 위험과 롤백

- 실험이 기존 데이터나 환경에 줄 수 있는 영향:
- 중단/원복 방법:

## 결과

작업 후 작성. 예상과 달랐던 점과 측정 도구의 오류도 포함한다.

## 남은 한계

이번 결과로 일반화할 수 없는 범위를 적는다.
```

## Issue 종료 조건

- 성공 기준이 실행 전에 작성돼 있다.
- 코드 변경이 있으면 자동 테스트 또는 재현 가능한 실험이 연결돼 있다.
- 결과에 commit SHA, 환경, 명령, 핵심 원본 증거 경로가 있다.
- 문서의 숫자를 원본 결과에서 다시 계산할 수 있다.
- 실패한 실험도 삭제하지 않고 원인과 다음 판단을 남겼다.
- README 또는 ADR을 바꿀 정도의 결정이면 해당 문서가 함께 갱신됐다.
- 남은 위험이 별도 이슈인지 의도적으로 수용한 것인지 명시돼 있다.

## 예시: 좋은 신뢰성 Issue

```markdown
# [Reliability] storage consumer 재시작 정합성 3회 반복

## 문제
현재 강제 종료 실험은 1회이며 재전달량의 변동 폭을 모른다.

## 현재 증거
- `load-test/storage-integrity/RESULT_20260904_kill_redelivery.md`
- 1회 결과: 재전달 68건, 최종 유실 0, 중복 저장 0
- 검증 상태: 부분 검증

## 가설
종료 순간에 따라 재전달량은 달라지지만 최종 저장 행은 매회 고유 이벤트 수와 일치한다.

## 성공 기준
- 3회 모두 `Kafka 고유 메시지 = InfluxDB 최종 point`
- 깨진 메시지 0
- 재전달량과 추가 저장 시도량의 차이 0

## 남은 한계
단일 백엔드 인스턴스와 로컬 Docker Compose 환경에만 적용된다.
```

## 외부 저장소 참고 원칙

- 그대로 복사하기보다 어떤 실패 모드를 해결하는 설계인지 확인한다.
- 버전, 라이선스, 운영 전제와 현재 Telemetrix의 차이를 기록한다.
- “유명 프로젝트가 사용한다”는 도입 근거가 아니다.
- offset commit 시점, idempotency key, retry/DLQ 소유자, 복구 절차와 관측 지표를
  우선 비교한다.
- 참고 링크는 Issue의 `현재 증거` 또는 ADR에 남긴다.
