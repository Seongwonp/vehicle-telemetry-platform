# Telemetrix 고도화 로드맵

## 목적

Telemetrix의 목표는 기술을 많이 붙이는 것이 아니라 차량 데이터 파이프라인의 유실,
중복, 순서, 장애 격리, 복구와 관측 가능성을 코드와 재현 가능한 실험으로 설명하는
것이다. 이 문서는 완료 이력이 아니라 **다음 작업을 선택하는 기준**이다. 완료된 실험과
수치는 `README.md`, `docs/devlog.md`, `docs/verification/`, `load-test/**/RESULT_*.md`에서
확인한다.

## 우선순위 원칙

1. 깨진 빌드와 조용한 데이터 유실을 가장 먼저 다룬다.
2. 기능 추가보다 기존 신뢰성 주장의 재현성과 증거 품질을 높인다.
3. 변경 전 가설과 성공 기준을 적고, 같은 조건으로 변경 전후를 비교한다.
4. 처리량 하나만 보지 않고 성공률, lag, p95/p99 지연, 복구 시간과 정합성을 함께 본다.
5. 결과가 예상과 다르면 실패를 지우지 않고 측정 도구의 한계까지 기록한다.

## P0 — 신뢰성 주장을 다시 검증할 수 있게 만들기

### P0-1. 실험 원본 증거 보존 — **checksum 이식성 복구 완료(2026-09-09)**

감사가 제기한 P0을 확인했고 **사실이었다.** 그리고 고쳤다.

전수 검사(`load-test/lib/verify_evidence.sh`)를 만들어 clean clone에서 돌리니
**39개 manifest 중 3개**가 깨져 있었다 — 전부 `.prev_offsets`이고 전부 CRLF다.
확장자 없는 숨김 파일이 `.gitattributes`의 `*.txt`/`*.csv`/`*.json`/`*.log` 목록 밖이라
`core.autocrlf=true`가 적용됐다. **작업 트리에서는 원본 LF 파일이 남아 있어 안 보이고,
새로 클론해야 드러난다.**

**증거 자체는 처음부터 옳았다.** git blob의 해시가 manifest와 정확히 일치한다
(`76cdfe49` / `87da0f68` / `388dd7ca`). 깨뜨린 것은 checkout 단계뿐이라,
manifest를 다시 쓰거나 파일을 지우지 않고 **규칙으로 살렸다.**

- `.gitattributes`: evidence 아래를 확장자별이 아니라 **통째로** LF 고정.
  확장자 목록은 새 파일이 생길 때마다 조용히 뚫린다.
- `verify_evidence.sh`: 전체 manifest 순회, 실패 시 경로·기대·실제 해시 출력,
  CR이 있으면 줄바꿈이 원인이라고 알려준다. 통과 0 / 실패 1.
- `evidence_finish`: 숨김 파일을 manifest에서 제외하고 **생성 직후 자체 검증**해
  결과를 `checksum_selfcheck.txt`에 남긴다.
- 실험 스크립트 둘: 작업 파일(`.prev_offsets`, `.current_phase`)을 evidence 밖으로.
  규칙으로도 막았지만 **작업 파일을 증거에 섞지 않는 것**이 근본 해결이다.
- CI에 검사 단계 추가.

결과: 수정 전 Windows clean clone **3 실패 / 39** → 수정 후 **0 실패 / 39**.
검증 기록: [`docs/verification/2026-09-09-evidence-checksum.md`](verification/2026-09-09-evidence-checksum.md).

**고치면서 같은 함정을 한 번 밟았다** — 자체 검증 결과를 `metadata.txt`에 덧붙이도록
짰는데, 그 파일은 manifest 안에 있어서 **한 줄만 더해도 해시가 어긋난다.**
`checksum_selfcheck.txt`로 분리했다.

**남은 것**: macOS 미확인. `verify_evidence.sh`는 manifest에 **적힌** 파일만 보므로
manifest에서 빠진 증거는 알려주지 않는다.
(Linux CI 통과는 `4142262` 푸시에서 확인됐다 — 39개 검사 / 0 실패.)

**기존 작업(2026-09-05)**:

`load-test/lib/evidence.sh`를 만들어 네 시나리오 스크립트에 붙였다. 실행마다
`evidence/<run-id>/`에 metadata(시각·git SHA·**작업 트리 dirty 여부**·명령·성공 기준·판정),
inputs/counts CSV, 콘솔 로그, Prometheus 스냅샷, Kafka offset/lag 원문, 로그 발췌,
checksums가 남는다(한 실행 약 30KB). 설계 근거는 `load-test/lib/README.md`.

붙이면서 스크립트 결함도 하나 고쳤다 — health 대기 루프에 **타임아웃이 없어서**
Docker Desktop이 죽은 채 20분을 대기하고도 로그에 아무 단서가 없었다.
`wait_until`로 바꿔 300초 후 컨테이너 상태와 함께 중단한다.

**남은 것**: 아래 대상의 과거 실행은 원본이 없다. 재수집은 P0-2(3회 반복)와 같이 한다.

- 대상: 현재 핵심 장애 실험의 로그, 메트릭 스냅샷, 집계 CSV/JSON.
- 범위: MQTT 브로커 장애, Kafka 장애와 spool, InfluxDB 장애, PostgreSQL 장애,
  consumer 강제 종료, anomaly detector 리밸런싱.
- 완료 조건:
  - 실행 commit SHA, 환경, 명령, 시작·종료 시각이 기록된다.
  - 결과 문서의 핵심 수치를 원본 파일에서 다시 계산할 수 있다.
  - 개인정보, 토큰, 인증서, 비밀번호는 저장하지 않는다.

### P0-2. 핵심 실험 반복성과 변동 폭 확인 — **완료(2026-09-05)**

세 실험을 각 3회 반복했다. 실패 0/9.

| 실험 | 불변식 | 흔들린 값 |
| --- | --- | --- |
| MQTT 90초 장애 | 유실 0 — **3/3** | 총 처리량 6.4% 폭, `시도−확인` 0/694/0 |
| 리밸런싱 3→1→3 | 행 증가 0 — **3/3** | **재전달 42/6/11 (7배)** |
| storage consumer SIGKILL | 브로커 확인==토픽==행 — **3/3** | kill 시점 offset 편차 874 |

**반복이 실제로 두 개의 잘못된 서술을 잡았다.**

1. 리밸런싱 "재전달 40건(0.100%)"을 이 실험의 성질처럼 적어뒀는데, 42/6/11로 7배
   흔들렸다. 대표값이 아니었다.
2. 강제 종료 "재전달 68건"은 **측정 자체가 불가능**했다. 3회 모두 음수가 나와
   `batch_size_sum`(프로세스 생명주기 카운터) 방식의 구조적 한계를 확인했다.
   판정 로직도 음수를 그대로 두고 PASS를 찍고 있어 함께 고쳤다.

결과: `load-test/*/RESULT_20260905_*repeat.md`, 회차별 원본은 각 `evidence/`.
도구: `load-test/lib/repeat.sh`, `load-test/lib/summarize.sh`.

**남은 것**: 재전달 수를 재려면 프로세스 밖 처리 카운터가 필요하다(미구현).
mTLS·300초 조건은 아직 1회다.

**집계 도구를 두 번 고쳤다(2026-09-07)** — 둘 다 **조용한 실패**였다.
(1) `summarize.sh`의 편차 계산이 bash 정수 산술(`$((mx - mn))`)이라 CPU %·쓰기 지연 같은
**소수 지표에서 문서 생성이 그 줄에서 끊겼다**(리다이렉트 안이라 에러도 안 보였다). awk로 교체.
(2) **중단된 실행이 완주와 구분되지 않았다** — 죽은 실행의 `evidence/<run-id>/`에도
metadata·counts·inputs가 다 있어서, 첫 집계가 "4회 반복 → 검증 완료"로 나왔다(진짜 완주 3회).

`summarize.sh`는 **완주만 세고 중단은 별도 표에 남긴다**(지우지 않는다 — 몇 번 시도해
몇 번 완주했는지도 결과다). `status.txt`가 없는 옛 실행은 완주로 본다.

## P1 — 채용 포트폴리오에 직접 도움이 되는 경계 검증

### P1-1. 순서 보장 범위 측정 — **완료(2026-09-05)**

정상 경로와 spool 드레인 경로를 나눠 차량별 타임스탬프 역전을 셌다.

| | 정상 | Kafka 90초 장애 후 드레인 |
| --- | ---: | ---: |
| 역전 | **0** | **924 (0.38%)** |
| 역전이 난 차량 | 0 | **200 (전부)** |
| 최대 되돌아간 시간 | — | **113,722 ms** |
| 차량당 역전 | 0 | 4~6 (중앙 5) |

**1분 미만 역전이 하나도 없다** — 잠깐 뒤섞인 게 아니라 1~2분 묵은 메시지가 뒤늦게
도착한다. `TelemetryProducer.retryPending()` 주석에 적혀만 있던 가설이 확인됐다.

정상 경로가 0인 것은 `enable.idempotence=true` + `max.in.flight ≤ 5` 덕분이다
(설정하지 않았는데 Kafka 3.0+ 기본값). 이 조합이 깨지면 정상 경로에서도 역전이
생기므로 `ProducerConfig` 블록을 증거로 남긴다.

**결정**: 역전은 허용하고 **표시 계층에서 막는다.** 저장(InfluxDB)·조회(REST `/latest`는
`sort(_time) |> limit(1)`)는 영향이 없고, 영향은 앱의 실시간 화면 하나뿐이다.
파이프라인에서 순서를 맞추려면 드레인과 신규 발행을 한 락으로 묶어야 하는데 그건
수집 처리량을 무너뜨린 예전 구조로 되돌아가는 것이다.
앱은 이미 가진 값보다 오래된 프레임을 버리도록 고쳤다(앱 저장소 `7f5002b`, 테스트 2건).

결과: `load-test/order-integrity/RESULT_20260905_order.md`.

**남은 것**: 각 모드 1회 실행, **ML 슬라이딩 윈도우에 묵은 샘플이 섞이는 영향 미측정**,

### P1-2. poison message와 DLQ 재처리 경계 — **1차 완료(2026-09-06)**

독성 5유형을 Kafka 토픽에 직접 주입하고, 유형마다 **같은 키의 정상 레코드 100건**을
함께 넣어 "정상 레코드가 함께 막히는가"를 셌다.

| 유형 | 대조군 | 독성의 종착지 |
| --- | ---: | --- |
| `malformed_json` | 100/100 | DLQ (`JsonParseException`) |
| `bad_timestamp` | 100/100 | DLQ (`DateTimeParseException`) |
| `wrong_schema` | 100/100 | DLQ (`NullPointerException`) |
| `huge_payload`(300KB) | 101/100 | 정상 저장 — 독성이 아니었다 |
| `infinity`(`1e309`) | 100/100 | **저장됐지만 `speed` 필드가 사라졌다** |

**정상 레코드가 함께 막힌 유형은 없다.** DLQ 4건은 전부 `permanent`로 분류되고
`x-dlq-*` 헤더로 원본 토픽·파티션·offset이 추적된다.

**발견**: `{"speed": 1e309}`는 유효한 JSON이고 Jackson이 `Infinity`로 파싱하는데,
InfluxDB 쓰기가 실패하지 않고 **그 필드만 조용히 빠진 채 저장된다.** DLQ 0, 에러 0,
카운터 변화 0 — 정합성 대조(토픽 수 = 행 수)로도 안 잡힌다(행은 있으므로).

결과: `load-test/poison-message/RESULT_20260906_poison.md`.

**남은 것**: 재처리 횟수 초과를 이번 `permanent` 레코드로 다시 밀지 않았다.
~~Infinity 부분 유실을 막을지 **미결정**~~ — P1.5-1에서 `toPoint()`에 유한값 검사를 넣어 닫았고,
2026-09-08에 음수·NaN까지 확인했다(아래).
MQTT 단계 경계(`max_packet_size` 초과)는 범위 밖.

**NaN과 음의 Infinity도 주입했다(2026-09-08)** — 2026-09-06에 남긴 미검증이다.
결과가 둘로 갈렸고, 그 갈림이 이 실험의 값이다.

| 유형 | 대조군 | 독성의 종착지 | 어디서 걸렸나 |
| --- | ---: | --- | --- |
| `speed: -1e309` | **100/100** | DLQ(`permanent`) | `toPoint()`의 `finite()` — 양수와 같은 예외·같은 분류 |
| `speed: NaN` | **100/100** | DLQ(`permanent`) | **역직렬화** — `finite()`에 도달 못 함 |

`NaN`은 JSON 리터럴이 아니고 Boot 기본 `ObjectMapper`가 `ALLOW_NON_NUMERIC_NUMBERS`를
꺼둔 채라 파싱 단계에서 거부된다. 즉 **`finite()`의 NaN 분기는 이 입구로는 도달할 수 없다.**
"검사가 있으니 안전하다"와 "그 경로로는 들어올 수 없다"는 다른 말이라 구분해 적어둔다 —
나중에 이 방어를 정리하려는 사람이 판단할 근거가 된다.
결과: `load-test/poison-message/RESULT_20260908_nan_neginf.md`.
**새로 생긴 미검증**: `ALLOW_NON_NUMERIC_NUMBERS`를 켰을 때의 동작(켤 이유가 없어 안 켜봤다),
MQTT 경로 주입(같은 `ObjectMapper`를 쓴다는 코드 근거만 있다).

**정수 필드(`rpm`)도 같은 날 봤고, 조용한 값 변형을 하나 더 찾았다(2026-09-08).**

| 유형 | 대조군 | 독성의 종착지 | 어디서 |
| --- | ---: | --- | --- |
| `rpm: 99999999999` | 100/100 | DLQ(`permanent`) | 역직렬화 — int 범위 초과 |
| `rpm: 1e309` | 100/100 | DLQ(`permanent`) | 역직렬화 — int 범위 초과 |
| **`rpm: 2000.7`** | **101/100** | **저장됨(2000으로 잘림)** | **아무 데서도 안 걸린다** |

같은 `1e309`가 `speed`(double)에서는 파싱에 성공해 `finite()`까지 가고,
`rpm`(int)에서는 **역직렬화에서** 잘린다 — 결과는 같아도 **막는 문이 다르다.**
`finite()`가 int 필드를 지켜준다고 생각하면 틀린 것이다.

`2000.7`은 `ACCEPT_FLOAT_AS_INT`(기본 활성)가 소수점을 잘라 **2000으로 저장**한다.
DLQ 0, 에러 0, 카운터 0, 행 수도 맞아서 정합성 대조로도 안 잡힌다.
**고치지 않기로 했다** — 손실이 1 rpm 미만이고, 스펙이 `rpm`을 정수로 정의하며,
**이상 감지는 원본 JSON을 Python에서 평가하므로 영향이 없다**(`rules.py`).
막으려면 `ACCEPT_FLOAT_AS_INT`를 꺼야 하는데 그러면 `"rpm": 2000.0`까지 DLQ로 간다.
**대신 기록**: 저장 데이터로 룰을 다시 돌리면 `6000.9`가 `6000`이라 안 걸린다 —
"감지 시점의 값"과 "저장된 값"이 다를 수 있고, 이건 `rpm`에만 해당한다.
결과: `load-test/poison-message/RESULT_20260908_rpm_int.md`.

**`dtc_codes`(배열)도 봤다 — 배열을 문자열로 접는 자리에서 둘이 샌다(2026-09-09).**

| 유형 | 대조군 | 종착지 | 저장된 값 |
| --- | ---: | --- | --- |
| `"dtc_codes": "P0301"`(배열 아님) | 100/100 | DLQ(`permanent`) | — |
| **`[null]`** | **101/100** | **저장됨** | **`null`**(네 글자 문자열) |
| **`["P0301,P0420"]`** | **101/100** | **저장됨** | `P0301,P0420` (코드 1개인지 2개인지 구분 불가) |

`toPoint()`의 `String.join(",", dtcCodes)`가 null을 `"null"` 글자로 만들고, 코드에 든 쉼표는
구분자와 충돌한다. **고치지 않기로 했다** — 값이 사라지지 않고(DTC 형식에 안 맞아 눈에 띈다),
쉼표는 스펙(`[PBCU]\d{4}`)을 지키는 입력에서 나올 수 없으며, 이상 감지는 원본 JSON을 본다.
구분자 변경은 **저장 포맷 계약**을 바꾸는 일이라 대가가 더 크다.
**다시 볼 조건**: 실제 장치에서 null 원소나 쉼표 포함 코드가 한 번이라도 관찰되면 뒤집는다.
결과: `load-test/poison-message/RESULT_20260909_dtc_codes.md`.
**남은 미검증**: 빈 문자열 원소(`[""]`), 아주 긴 코드, 중복 코드.

<details><summary>원래 항목</summary>

- 비정상적으로 큰 메시지, 다른 schema, 잘못된 timestamp, 영구 InfluxDB 필드 충돌,

   이미 저장돼 있었다(in-doubt). PostgreSQL 쪽은 복구가 필요한 알림이 하나도 없었다.
3. **DLQ 6,158건이 생겼는데 로그에 한 줄도 없었다** — 알림 경로는 배치 실패마다 ERROR를

   → `KafkaConfig` recoverer에 `[DLQ 이동]` WARN, `consumeForStorage`에 배치 실패 ERROR
   추가. 회귀 테스트 `KafkaDlqLoggingTest`.

결과: `load-test/long-outage/RESULT_20260906_influxdb.md`, `RESULT_20260906_postgres.md`.

### P1.5-1. Infinity 부분 유실 차단 — **완료(2026-09-06)**

`toPoint()`에 유한값 검사를 넣었다. P1-2에서 찾은 **필드만 조용히 사라지는 경로**다.

미결정으로 뒀던 이유는 "발생 가능성을 확인하지 않은 채 모든 메시지에 검사 비용을
물릴지"였는데, 비용을 따져보니 판단할 것이 없었다 — **포인트당 비교 8회**이고, 같은
포인트를 보내는 HTTP 요청 하나가 이 호스트에서 약 0.8초(요청당 고정비)다.

건너뛰지 않고 **던진다.** 그래야 컨슈머의 레코드 단위 catch가 그 레코드만 DLQ로 보내
유실이 **보이고 되돌릴 수 있는** 형태가 된다. 회귀 테스트는 `TelemetryRepositoryTest`
(speed=Infinity, engine_temp=NaN, gps.lat=-Infinity, 정상값 통과).

같은 시나리오를 다시 돌려 확인했다 — 독성 1건이 **저장(필드 소실)에서 DLQ 1건으로** 바뀌고
대조군 100건은 그대로 저장된다. 그 과정에서 **새 예외가 DLQ 분류에서 `unknown`으로
떨어지는 것**을 발견해 `dlq.py`의 `PERMANENT_MARKERS`에 추가했다(되돌려도 값은 그대로
Infinity라 영구다). 결과는 `load-test/poison-message/RESULT_20260906_poison.md`의 "후속" 절.

**후속 완료(2026-09-08)**: NaN과 음의 Infinity도 파이프라인 전 구간에 주입했다.
`-1e309`는 `finite()`에서 DLQ로 갔고, `NaN`은 그보다 앞선 Jackson 역직렬화 단계에서
거부됐다. 대조군은 각 유형 100/100 저장됐다. 결과는
`load-test/poison-message/RESULT_20260908_nan_neginf.md`.

### P1.5-2. 리밸런싱이 왜 안 도는지 구분 — **완료(2026-09-06)**

P1-3에서 재시도가 `max.poll.interval.ms`(300초)를 두 배 넘게 초과했는데도 리밸런싱이
0이었다. 정적 멤버십(`group.instance.id`) 덕인지, 리스너가 컨슈머를 살려두는 것인지
**구분하지 못한 채** 닫았다.

**답: 에러 핸들러가 컨슈머를 살려둔다.** 리스너 로거를 DEBUG로 올리니 재시도 주체가
`FallbackBatchErrorHandler`로 찍혔고, 그 클래스가 부르는
`ErrorHandlingUtils.retryBatch`가 **파티션을 pause한 채 `poll(Duration.ZERO)`를 계속
호출한다**(spring-kafka 3.1.4 바이트코드로 확인 — `Consumer.pause` / `Consumer.poll` ×2 /
`Consumer.resume` ×3). poll이 계속 불리므로 poll 간격이 만료되지 않는다.
파티션 할당 로그도 기동 시 한 번뿐이고 12분간 재할당이 없다.

`KafkaConfig.buildBackOff`의 "리스너가 오래 붙잡히면 리밸런싱이 돌 수 있다"는 서술을
정정했다.

**같은 조건 2회차를 겸했다**(P1.5-5): 첫 DLQ 220 → **222초**, DLQ 6,158 → **6,185**(0.4%),
리밸런싱 0 → 0. **in-doubt 건수만 47 → 23으로 흔들린다** — `docker stop` 순간 서버까지
닿은 쓰기가 몇 건이냐는 타이밍 문제라 성질처럼 인용하면 안 된다.

결과: `load-test/long-outage/RESULT_20260906_influxdb_repeat.md`.

**후속 완료(2026-09-09)**: 빈 값이면 `group.instance.id` 속성을 제거하는 설정을 추가하고
정적 멤버십 OFF 대조군을 실행했다. ON은 부하 중 스케일다운 3회에서 46/52/54초,
OFF는 1회에서 9초였다. 다만 OFF 반복 3회와 리밸런싱 폭풍의 갇힘 상태 재현은 남아 있다.
결과는 `load-test/storage-scale/RESULT_20260909_static_membership_control.md`와
`RESULT_20260909_static_membership_stress.md`.

### P1.5-3. 장애 중 엔드투엔드 추적 — **완료(2026-09-06)**

| ---: | ---: | ---: | ---: | ---: |
| 20/20 | **20/20** | **0/20** | **0/20** | **0/20** |

**남은 것**: 끊는 지점이 InfluxDB 하나뿐이다(도구는 `FAULT=telemetry-kafka` 등도 지원).
복구 후 뒤늦게 도착하는지는 안 봤다. 1회 실행.

  (멤버 9 / 정적 id 9 / 호스트 3 / 할당 9, fencing 0), dev 오버레이가 저장 인스턴스에도
  먹는 것(`MQTT_PORT=1883`, `MQTT_TLS_ENABLED=false`)을 확인했다.
  **그 과정에서 새로 본 것**: 파티션을 늘려도 **이미 떠 있는 컨슈머는 최대
  `metadata.max.age.ms`(기본 5분)까지 새 파티션을 못 본다.** 그 전에 인스턴스를 늘리면
  리밸런싱은 도는데 할당이 안 늘어 "늘렸는데 처리량이 그대로"로 보인다(실측 약 4분 30초).
  Runbook에 순서와 대기 시간을 넣었다.
  스케일 다운은 **dev 프로파일 3회를 채웠다** — 46/48/47초(폭 2초). mTLS 1회는 44초다.
  이 프로젝트 기준(3회)을 채웠으므로 "약 45~48초"까지는 말할 수 있다.
  다만 네 회차 모두 **부하 없는 상태**다.
  **부하를 걸고도 쟀다(2026-09-08, 2회)** — Runbook의 "부하 중에 내리면 지연이 튄다"는
  추론이었다. 파티션 9 · 인스턴스 3 · 프로듀서 2로 재보니:
  **제거된 인스턴스가 쥔 6개 파티션이 완전히 정지**하고(평균 lag 7,137 → 177,952),
  **살아있는 backend의 3개는 평평하다**(2,244 → 1,324, 2회차 기준). 장애 격리는 성립한다.
  재할당은 다운 후 **46초/52초**로 무부하 때와 같은 자리다.
  **유실 0**(토픽 8,180,533 = 행 8,180,533 / 8,083,729 = 8,083,729).
  **계측 결함을 하나 잡았다**: "무소유 파티션 수"는 끝까지 0이었다 —
  정적 멤버십에서는 **죽은 멤버가 세션 만료까지 소유권을 유지**하기 때문이다.
  `--describe`만 보면 9개 다 주인이 있어 멀쩡해 보인다.
  **"소유자가 있다"는 "소비되고 있다"를 뜻하지 않는다.**
  지표를 `current_offset` 정지로 바꾸니 2회차에서 정확히 6개가 잡혔다.
  결과: `load-test/storage-scale/RESULT_20260908_scaledown_under_load.md`.
  **3회를 채웠다(2026-09-09)** — 재할당 46/52/54초, 정지 파티션 6개(2·3회차),
  **유실 0은 3/3**이다.
  **그리고 정적 멤버십을 끈 대조군을 처음 돌렸다.** 끄니 멤버가 **다운 후 9초**에
  3으로 돌아오고 **정지 파티션이 0개**다 — 스케일 다운의 45초는 정적 멤버십의 대가가 맞다.
  끄려면 설정이 필요해서 `KafkaConfig`에 **빈 값이면 속성을 제거**하는 커스터마이저를
  넣었다(ADR-024). Kafka가 빈 문자열을 거부해서 그전에는 **끌 방법 자체가 없었다.**
  **⚠ 이 대조군은 끄는 것의 이득만 봤다** — 정적 멤버십을 켠 이유(리밸런싱 폭풍)는
  재현하지 않았다. 기본값은 켜짐을 유지한다.
  결과: `load-test/storage-scale/RESULT_20260909_static_membership_control.md`.
  **끄는 것의 대가도 같은 날 잰 만큼은 쟀다** — 330초 정지(`max.poll.interval.ms` 초과)에서
  정지됐다 돌아온 인스턴스의 `MemberIdRequiredException`이 **ON 0건 / OFF 12건**이다
  (12시간 soak test에서 본 그 예외). 끄면 컨슈머 12개가 각각 member id를 재발급받는다.
  **폭풍 자체(갇히는 상태)는 재현 못 했다** — 전부 정상 재가입했다.
  결과: `load-test/storage-scale/RESULT_20260909_static_membership_stress.md`.
  **이 실험에서 집계가 한 번 틀렸다**: 정지시키지 않은 컨테이너를 세고 `already rebalancing`
  (정상 리밸런싱에도 찍히는 줄)을 표식에 넣어 "차이 없음"이 나왔다. 원본 로그를 열어 잡았다.
  **남은 것**: 폭풍(갇히는 상태) 재현, 각 조건 1회, 그룹 세대 수로는 차이가 안 보인다는 점.
  결과: `docs/verification/2026-09-08-dev-profile-scale.md`.
  **남은 미검증**:
  파티션 확장이 키 해싱을 바꿔 같은 `vehicle_id`가 다른 파티션으로 갈 때의 영향 미검증,
  **처리량 이득은 이 변경으로 재지 않았다**(같은 날 회차 간 비교가 깨져 지금 재는 것은 값이 없다).
- naive의 중복·유실 수치는 **무효**다(연결 경합이 QoS 1 재전송을 유발해 총량에서
  중복과 유실이 상쇄된다). 실패 양상만 유효하다.
- Kafka `replication-factor`는 여전히 1이다. **브로커가 1대라 상향 자체가 지금은 의미 없다.**

### 데이터 보존·삭제와 개인정보 — **1차 완료(2026-09-06)**

설정을 확인해보니 **InfluxDB 버킷 보존이 무기한**이었다(`DOCKER_INFLUXDB_INIT_RETENTION`
미설정 → InfluxDB 2.x 기본이 무제한). 거기에 GPS(`lat`/`lng`)가 담긴 텔레메트리가 계속
쌓이고 있었다.

정한 것: 버킷 보존 **90일**(`INFLUXDB_RETENTION`, 90일 넘겨 조회하는 기능이 하나도 없다),
`backend` 컨테이너 로그 로테이션(50m × 3 — 요청 로그에 `clientIp`가 들어간다),
Kafka 리텐션 1시간 유지, 차량 삭제는 소프트 삭제 유지 + 즉시 삭제는 수동 절차.

문서: `docs/data-retention.md`(저장소별 데이터 목록·성격·보존, 수동 삭제 명령 포함).

**남은 것**: ~~기존 환경 마이그레이션 절차가 없다~~ — **만들고 실측했다(2026-09-07)**:
[`docs/runbook/influxdb-retention-change.md`](runbook/influxdb-retention-change.md).
삭제는 **즉시가 아니라 검사 주기마다**(운영 기본 30분), 삭제 중 **쓰기는 안 막히고**
(실패 0건), **되돌릴 수 없다**(무기한으로 되돌려도 0행).
도구가 네 번 조용히 죽었던 것도 결과에 남겼다 — `bucket update`는 `--org`를 안 받고
`--name`은 대상 선택이 아니며, Git Bash 경로 변환과 `| head`의 SIGPIPE가 각각 `pipefail`과
겹쳐 **로그 없이** 끝난다. 결과: `load-test/retention-migration/RESULT_20260907_migration.md`.
**새로 생긴 미검증**: 수억 행 규모에서의 삭제 소요·쓰기 영향, shard 경계 동작,
운영 기본값(30분)에서의 실제 지연.
`anomaly_alerts` 보존 기간
미정(무기한). 삭제 요청 API와 권한 모델 미정. 로그의 **기간 기준** 보존 미정.
`vehicles.owner`가 자유 입력이라 실명이 들어갈 수 있는데 안내·마스킹이 없다.
