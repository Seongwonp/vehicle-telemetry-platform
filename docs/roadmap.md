# Telemetrix 고도화 로드맵

## 목적

Telemetrix의 목표는 기술을 많이 붙이는 것이 아니라 차량 데이터 파이프라인의 유실,
중복, 순서, 장애 격리, 복구와 관측 가능성을 코드와 재현 가능한 실험으로 설명하는
것이다. 이 문서는 완료 이력이 아니라 **다음 작업을 선택하는 기준**이다. 완료된 실험과
수치는 `README.md`, `docs/devlog.md`, `docs/verification/`, `load-test/**/RESULT_*.md`에서
확인한다.

## 우선순위 원칙

1. 깨진 빌드와 조용한 데이터 유실을 가장 먼저 다룬다.
2. 기능 추가보다 기존 신뢰성 주장의 재현성과 증거 품질을 높인다.
3. 변경 전 가설과 성공 기준을 적고, 같은 조건으로 변경 전후를 비교한다.
4. 처리량 하나만 보지 않고 성공률, lag, p95/p99 지연, 복구 시간과 정합성을 함께 본다.
5. 결과가 예상과 다르면 실패를 지우지 않고 측정 도구의 한계까지 기록한다.

## P0 — 신뢰성 주장을 다시 검증할 수 있게 만들기

### P0-1. 실험 원본 증거 보존 — **도구 완료, 과거 실행 재수집은 남음(2026-09-05)**

`load-test/lib/evidence.sh`를 만들어 네 시나리오 스크립트에 붙였다. 실행마다
`evidence/<run-id>/`에 metadata(시각·git SHA·**작업 트리 dirty 여부**·명령·성공 기준·판정),
inputs/counts CSV, 콘솔 로그, Prometheus 스냅샷, Kafka offset/lag 원문, 로그 발췌,
checksums가 남는다(한 실행 약 30KB). 설계 근거는 `load-test/lib/README.md`.

붙이면서 스크립트 결함도 하나 고쳤다 — health 대기 루프에 **타임아웃이 없어서**
Docker Desktop이 죽은 채 20분을 대기하고도 로그에 아무 단서가 없었다.
`wait_until`로 바꿔 300초 후 컨테이너 상태와 함께 중단한다.

**남은 것**: 아래 대상의 과거 실행은 원본이 없다. 재수집은 P0-2(3회 반복)와 같이 한다.

- 대상: 현재 핵심 장애 실험의 로그, 메트릭 스냅샷, 집계 CSV/JSON.
- 범위: MQTT 브로커 장애, Kafka 장애와 spool, InfluxDB 장애, PostgreSQL 장애,
  consumer 강제 종료, anomaly detector 리밸런싱.
- 완료 조건:
  - 실행 commit SHA, 환경, 명령, 시작·종료 시각이 기록된다.
  - 결과 문서의 핵심 수치를 원본 파일에서 다시 계산할 수 있다.
  - 개인정보, 토큰, 인증서, 비밀번호는 저장하지 않는다.

### P0-2. 핵심 실험 반복성과 변동 폭 확인

- 우선 MQTT 90초 장애, storage consumer 강제 종료, anomaly detector 리밸런싱을
  각각 3회 반복한다.
- 평균만 쓰지 않고 최소·최대, 실패 횟수, 재전달률과 복구 시간을 남긴다.
- 완료 조건: 3회 모두 정합성 불변식이 성립하거나, 실패 조건과 재현 절차가 이슈에
  남는다.

### P0-3. 문서와 구현의 계약 드리프트 제거

- Kafka listener 방식, retry 의미, topic·Consumer Group, 앱 테스트 상태를 코드와
  대조한다.
- 완료 조건: 같은 동작을 설명하는 README, ADR, Runbook, 설정 주석 사이에 상충하는
  문장이 없고, 미실행 테스트를 `검증 완료`라고 표현하지 않는다.

## P1 — 채용 포트폴리오에 직접 도움이 되는 경계 검증

### P1-1. 순서 보장 범위 측정

- 정상 Kafka 경로와 Kafka 장애 후 spool drain 경로를 나눠 차량별 timestamp/sequence
  역전을 센다.
- 성공 기준을 “역전 0”으로 미리 단정하지 않는다. 역전이 발생하면 범위, 사용자 영향,
  허용 또는 보정 정책을 결정한다.

### P1-2. poison message와 DLQ 재처리 경계

- 비정상적으로 큰 메시지, 다른 schema, 잘못된 timestamp, 영구 InfluxDB 필드 충돌,
  재처리 횟수 초과를 검증한다.
- 정상 레코드는 함께 막히지 않고, 실패 원인과 원본 위치를 추적할 수 있어야 한다.
- DLQ 재처리 실패가 원본 삭제나 무한 반복으로 이어지지 않아야 한다.

### P1-3. 장기 장애와 retry/rebalance 경계

- 현재 retry budget은 벽시계 시간이 아니라 백오프 대기 합이다.
- 8분 이상 의존성 장애에서 실제 poll 간격, 리밸런싱, DLQ 이동, 복구 시간을 측정한다.
- 설정 변경은 측정 후에만 결정한다.

### P1-4. 앱 자동 검증과 실제 기기 확인

- 앱 저장소에 format, analyze, unit/widget test CI를 추가한다.
- 320/360/400px, 글자 1.3/1.5배, 라이트/다크, 오류·빈 상태를 확인한다.
- 실제 기기에서 스크롤, 터치, 키보드, 네트워크 재연결을 확인하고 앱·백엔드 SHA를
  함께 기록한다.

### P1-5. MQTT → Kafka → DB → 앱 E2E

- 한 차량의 고유 테스트 이벤트를 발행하고 Kafka, 저장소, REST/WebSocket 앱 표시까지
  같은 식별자로 추적한다.
- 완료 조건: 단계별 도착 여부와 지연을 자동 집계하고 실패 지점을 구분한다.

## P2 — P0/P1 이후 필요성이 확인되면 수행

- schema 버전과 호환성 정책
- 데이터 보존·삭제와 개인정보 처리 정책
- 성능 회귀 기준선 및 정기 soak test
- 배포 롤백 자동화
- 실제 OBD-II 장치 연동과 장치 timestamp 정밀도 검증
- 다중 백엔드 인스턴스와 Kafka replication factor 상향
- 문제와 측정 근거가 있는 경우에만 수평 확장 또는 서비스 추가 분리

## 지금 하지 않는 것

- Kubernetes 도입 자체를 목표로 삼지 않는다.
- 현재 병목을 측정하지 않은 채 데이터베이스나 메시지 브로커를 추가하지 않는다.
- 처리 경계와 장애 격리 이유가 없는 마이크로서비스 분리를 하지 않는다.
- 단일 머신 결과를 운영 규모의 고가용성 또는 무제한 확장성으로 표현하지 않는다.
- 새로운 기능 때문에 기존 장애 실험의 재현성이 깨지는 변경을 우선하지 않는다.
